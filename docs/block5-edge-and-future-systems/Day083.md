---

## 📖 Theory

Since **Linux 6.1** (Dec 2022), Rust is officially the second kernel language alongside C. The first subsystems (ACPI, NVMe driver parts, PHY drivers) are already written in Rust. Why? **Memory safety without GC** — the top-3 bug classes in kernel C (use-after-free, buffer overflow, null deref) are ruled out by the compiler.

### Three paths for Rust into the kernel

| Path | Status | Effort today |
|------|--------|--------------|
| `rust-for-linux` (in-tree) | stable for drivers (since 6.1), growing | needs patched kernel + nightly Rust |
| **eBPF** with `aya`/`aya-rs` | production-ready, no kernel patch | recommended entry point |
| Out-of-tree modules via `linux-kernel-module-rs` | experimental, only old kernels | deprecated |

For a learning day, **eBPF via Aya** is the realistic path: no custom kernel, no reboot risk, runs sandboxed in the kernel and is compilable from user space.

### Aya — Rust eBPF

```rust
// Cargo.toml: [dependencies] aya = "0.13"; aya-log = "0.2"
// Kernel-side eBPF program (XDP, kprobe, tracepoint)
```

```rust
// Aya-bpf: kprobe that fires on every `do_unlinkat` and counts
#![no_std]
#![no_main]
use aya_bpf::{macros::kprobe, programs::KProbeContext};
use aya_bpf_cty::c_int;

#[kprobe(name="my_kprobe")]
pub fn my_kprobe(ctx: KProbeContext) -> c_int {
    if let Ok(_pid) = ctx.pid() {
        // increment counter map
    }
    0
}
```

The whole thing is loaded and controlled by a user-space program via the `aya::Ebpf` loader, without you having to patch the kernel.

### Alternative: rust-for-linux (real kernel module)

For a *real* char-device module you need:
- Kernel sources with `CONFIG_RUST=y` (custom build) — or a preconfigured `rust-for-linux` kernel package.
- `rustc nightly` with a matching `LLVM` backend.
- Build via `make M=... LLVM=1` — not via `cargo`.

```rust
// kernel-side, simplified (rust-for-linux)
use kernel::prelude::*;
use kernel::Module;

module! {
    type: HelloModule,
    name: "hello_rust",
    author: "100days",
    description: "minimal rust module",
    license: "GPL",
}

struct HelloModule;
impl Module for HelloModule {
    fn init(_module: &'static ThisModule) -> Result<Self> {
        pr_info!("Hello from Rust kernel module\n");
        Ok(HelloModule)
    }
}
```

The setup effort (custom kernel with Rust) is **several hours** — for one day the eBPF path is realistic.

### Why this matters

Kernel development in Rust is the flagship project of language adoption — it proves that Rust is not just an "app language" but works down to the lowest system level. Polyglot engineers will write kernel drivers or eBPF programs (observability, security, networking) in Rust. Day 84 builds the network stack on this; Day 85 the high-performance server that can use eBPF for routing.

### Pitfalls

- **Rust kernel bindings are nightly + version-locked** — kernel 6.1 only matches certain `rustc` nightlies. Version mismatch → build fails.
- **`unsafe` is allowed everywhere, but kernel subsystems abstract it away** — you rarely write raw pointers; use `Module`/`Device` wrappers.
- **`dmesg` output is the only console** — there is no `println!`; `pr_info!` is the counterpart.
- **Panic in the kernel = system halt** — Rust panics in the kernel are handled in a controlled way (via `BUG()`), but a driver panic is fatal.
- **License:** kernel modules **must** be GPL-compatible, otherwise linker conflict. Use `license: "GPL"`.

## 🛠️ Practice

**Task (recommended Aya path):** Build an eBPF kprobe program with Aya that counts every `do_unlinkat` syscall and writes the counter to a map — load it from user space and read the counter.

**Step by step:**

1. Install the Aya template:
   ```bash
   cargo install bpf-linker
   cargo generate --git https://github.com/aya-rs/aya-template myproject
   ```
2. Choose `kprobe` as the program type.
3. Adapt `myproject-ebpf/src/main.rs` (counter map `aya_bpf::maps::HashMap` with key 0).
4. Build:
   ```bash
   cargo build --release -p myproject-ebpf --target bpfel-unknown-none
   ```
5. User-space loader `myproject/src/main.rs`: load BPF, attach to `do_unlinkat`, poll the map every 2 seconds, print the counter.
6. Run (root): `sudo ./target/release/myproject`
7. Trigger `unlink`s (in a 2nd terminal `rm /tmp/x` 10×) — observe the counter growth.

**Alternative (rust-for-linux path, several hours):** If you have a custom kernel:
1. Checkout `linux.git`, `make LLVM=1 defconfig && make LLVM=1 menuconfig` → `CONFIG_RUST=y`.
2. Build the kernel + boot it in QEMU.
3. Write the hello module shown above under `samples/rust/hello_rust.rs`.
4. `make LLVM=1 M=samples/rust/hello_rust modules`.
5. `insmod hello_rust.ko` + `dmesg | tail`.

**Definition of Done (DoD):**

- [ ] `bpf-linker` is installed and `cargo build --target bpfel-unknown-none` works.
- [ ] Your eBPF program compiles and loads via Aya (no `dmesg` error on attach).
- [ ] After 10 `rm` calls the user-space counter increases by ~10 (proof: kernel hook fires).
- [ ] You can explain in 2 sentences why Rust brings memory safety to the kernel, *even though* kernel code uses `unsafe` blocks by nature.
- [ ] You know the difference between rust-for-linux (in-tree, custom kernel) and Aya (eBPF, sandboxed) and when to pick which.
- [ ] Commit: `git commit -m "day83: aya ebpf kprobe unlink counter"`.

**Extension (optional):** Extend to an XDP program that counts packets on a network interface (`aya-bpf::programs::Xdp`). Bench with `iperf3` — packet rate vs. drop rate.
