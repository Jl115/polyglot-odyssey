# Day 84: Network Stack Deep Dive

**Block:** Block 5: Edge & Future Systems · Networking Internals

> **Goal of the day:** You walk the Linux network stack from the NIC interrupt to the user-space `read()`, and you build a minimal io_uring network routine that handles TCP connections without a syscall per call.

---

## 📖 Theory

Every "simple" TCP `read()` passes through ~10 layers. Knowing them is the difference between an app developer and a systems engineer.

### The stack path (RX, receiving)

```
[ NIC interrupt ]
    ↓  NAPI poll
[ Device driver (e1000/igb/...)]
    ↓  skb_alloc (sk_buff)
[ Netfilter (iptables/nft) hooks: PRE_ROUTING ]
    ↓  route decision
[ IP layer: fragmentation, conntrack ]
    ↓  TCP layer: seq/ack, congestion control (cubic/BBR)
[ Socket buffer queue ]
    ↓  wake_up epoll_wait
[ User space: read() syscall ]
```

Every step has tuning knobs: `net.core.netdev_max_backlog`, `tcp_congestion_control`, `net.ipv4.tcp_rmem`, `net.core.somaxconn`. High performance = fitting these knobs to the application.

### io_uring — the syscall killer

Classic network calls: `socket()` → `bind()` → `listen()` → `accept()` → `read()` → `write()`. Every call is **2 mode switches** (user→kernel→user) → microsecond overhead × thousands/s.

**io_uring** (Linux 5.1+, stable since 5.10) replaces this with a **shared ring buffer** between user and kernel:

```rust
// With the `io-uring` crate (Tokio uses io_uring for Linux backends)
use io_uring::IoUring;
use io_uring::opcode::{Accept, Read};

let mut ring = IoUring::new(256)?;
let accept_e = Accept::new(FD, ptr::null_mut(), 0).build();
ring.submission().push(&accept_e)?;
ring.submit()?;
// Wait in the reaping loop, no further syscall per op
let cqes = ring.completion();
for cqe in cqes { ... }
```

One `submit()` can push **many operations at once** into the kernel — and reaping happens in user memory (mapped). → latency under 1 µs, throughput in the millions of ops/s range.

### Tokio uses io_uring

Tokio's `tokio-uring` (separate crate) and Tokio's `fs` (since 1.x) use io_uring internally. On Linux 5.10+ it is the recommended path for high-perf file I/O and IO.

### Congestion control

Default `cubic`; for high bandwidth/RTT modern: `bbr` (Google, since 4.9):

```bash
sysctl -w net.ipv4.tcp_congestion_control=bbr
# persistent: in /etc/sysctl.conf
```

BBR models bottleneck bandwidth + RTT instead of being loss-based; in WANs often 2-10× throughput vs cubic.

### Why this matters

The high-performance server (Day 85) and the polyglot runtime (Day 90) hang on the network. Anyone who knows the stack layers and io_uring can *fundamentally* tune p99 latency, conn rate, and bandwidth — instead of mystically cranking up `somaxconn`.

### Pitfalls

- **io_uring is not portable** — Linux only; macOS/Windows have equivalent but different APIs (`kqueue`, `IOCP`, `iouring-on-mac` via emulation only for dev).
- **Ring size:** too small → `ENOMEM`-EAGAIN; too large → memory overhead. 256–1024 is the sweet spot.
- **Buffer lifetime:** with `io_uring` the buffer must live until the CQE — drop = UB. Use `fixed buffers` (`io_uring_register_buffers`).
- **conntrack with NAT** — high-conn servers blow through `nf_conntrack_max`; for pure server sockets disable conntrack for inbound rules.
- **`tcp_tw_reuse=1` is often a myth** — on the server side `SO_REUSEADDR` is usually the right tool.

## 🛠️ Practice

**Task:** Build a minimal io_uring TCP acceptor (via `tokio-uring`) that accepts 1000 connections and answers each with "hi". Compare conn rate with the blocking `std::net` equivalent.

**Step by step:**

1. `cargo new day84 --bin`, `cargo add tokio-uring`.
2. In `src/main.rs`, implement the io_uring acceptor:

   > **Hints:**
   > - Entry point is `fn main() -> std::io::Result<()>` that calls `tokio_uring::start(async { … })`.
   > - Bind a `tokio_uring::net::TcpListener` to `127.0.0.1:9100`.
   > - In a loop, `accept().await` each connection and `tokio_uring::spawn` a task that writes `b"hi\n"` via `write_all`.
   > - Use `?` for error propagation (the async block returns `io::Result`).
3. Run: `cargo run --release`.
4. Benchmark in a 2nd terminal (ApacheBench): `ab -n 10000 -c 100 http://127.0.0.1:9100/` — note `Requests per second`.
5. Compare with `std::net::TcpListener` + thread-per-conn (or a `rayon` pool).
6. Inspect your stack with `ss -tin` under load — you see `cubic`/`bbr`, recv-Q, conn statistics.
7. (Optional) Set `sysctl -w net.ipv4.tcp_congestion_control=bbr` and compare again (loopback → no effect, but the mechanism becomes clear).

**Definition of Done (DoD):**

- [ ] Server runs on `:9100` and answers `hi` to connections.
- [ ] `ab -n 10000 -c 100` prints a concrete `Requests per second` number.
- [ ] You can name the 7 stack layers from NIC interrupt to user `read()`.
- [ ] You compared io_uring vs. blocking and noted requests/s for both.
- [ ] You can explain why io_uring is only *minimally* faster than blocking on loopback (syscalls are not the bottleneck on loopback — the kernel stack is), but becomes significant in the WAN.
- [ ] Commit: `git commit -m "day84: io_uring acceptor + stack walkthrough"`.

**Extension (optional):** Use `perf` or `bpftrace` to count the top-5 kernel functions in your server. Build an eBPF trace (with Aya from Day 83) for `tcp_recvmsg` and compare call counts before/after io_uring.
