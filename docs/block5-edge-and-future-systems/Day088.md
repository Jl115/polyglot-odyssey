# Day 88: Cross-Language Benchmarking

**Block:** Block 5: Edge & Future Systems · Performance Engineering

> **Goal of the day:** You implement the same task (e.g. SHA-256 over 10 MB) in Rust, C, Zig, Python, Dart, and JavaScript — measure with `criterion.rs` (Rust-internal) and `hyperfine` (cross-language) — and record the numbers in a comparative table.

---

## 📖 Theory

Comparative benchmarks are **notoriously error-prone** — small mistakes distort the result massively. Three rules for *credible* benchmarks:

### Rule 1: same algorithm, same input

Not "Rust `sha2` crate vs. Python `hashlib`" (those are different implementations) — but the same algorithm source. Ideal: call the same C code from Rust, Zig, Dart via FFI; that measures *FFI overhead*, not the algorithm. For a *language comparison* use native idiomatic implementations and label them as such.

### Rule 2: the right metrics

- **Wall-clock** (total, incl. I/O, memory).
- **CPU time** (only compute time, excl. sleep/page-faults).
- **Throughput** (bytes/s, ops/s) — more meaningful than time.
- **p50/p99 latency** for interactive workloads.
- **Memory peak** (RSS) — often neglected, but edge-relevant.

### Rule 3: statistically valid

A single run is worthless. Use:
- **`criterion.rs`** for Rust-internal microbenches — statistically robust (100+ samples, outlier detection).
- **`hyperfine`** for external processes — warmup runs, multiple runs, p50/p99.
- **`perf stat`** for hardware counters (cache-misses, branch-misses).

```bash
hyperfine --warmup 3 --runs 20 \
  "./sha_rust" "./sha_c" "./sha_zig" "./sha_python" \
  --export-json results.json
```

### The `criterion.rs` API

```rust
// Cargo.toml: [dev-dependencies] criterion = { version = "0.5", features = ["html_reports"] }
use criterion::{criterion_group, criterion_main, Criterion};

fn bench_sha(c: &mut Criterion) {
    let data = vec![0u8; 10 * 1024 * 1024];  // 10 MB
    c.bench_function("sha256_10mb", |b| {
        b.iter(|| sha2::Sha256::digest(&data));
    });
}
criterion_group!(benches, bench_sha);
criterion_main!(benches);
```

### Cross-language trap: binary vs. interpreted

| Language | What is measured |
|---------|-------------------|
| Rust/C/Zig | binary + libc startup (~1-5 ms) |
| Go | binary + runtime init (~5-10 ms) |
| Python | interpreter + import overhead (~50-200 ms) |
| Node.js | V8 startup (~30-100 ms) |
| Dart | AOT binary or JIT VM |

For short tasks, startup dominates the number. Solution: large inputs (≥10 MB SHA, ≥1 M iterations) or embedded mode (library call instead of CLI).

### Why this matters

The "Language Choice Matrix" (Day 89) *needs* these numbers. Polyglot engineers choose languages not by belief, but by measured tradeoffs. Day 90 (Multi-Language System) optimizes exactly the bottlenecks this day identifies.

### Pitfalls

- **Cold-start distortion** — Python without warmup looks 10× slower than after warmup (JIT bytecode). Use `--warmup 3` minimum.
- **Debug builds** — Rust `cargo build` (without `--release`) is 10-100× slower. Verify: `file target/release/x` shows `stripped`, and `Cargo.toml` `[profile.release] opt-level = 3`.
- **LTO & codegen units** — `[profile.release] lto = "fat" codegen-units = 1` brings 5-20% on final release; without it the comparison is unfair.
- **CPU scaling** — turbo boost, thermal throttling. Use `powerprofilesctl` or measure at a fixed frequency.
- **malloc** — a C-Rust comparison often compares not the language, but `glibc malloc` vs. `mimalloc`. Set `LD_PRELOAD=libmimalloc.so` for the same allocator.
- **Branch prediction traps** — a microbench with predictable input makes branch prediction shine; with random input it collapses.

## 🛠️ Practice

**Task:** Implement SHA-256 over 10 MB of random input in Rust, C, Zig, Python, and Dart. Measure with `hyperfine` and `criterion.rs`. Record in a Markdown table.

**Step by step:**

1. Generate identical input: `dd if=/dev/urandom of=input.bin bs=1M count=10`.
2. **Rust:** `cargo new sha_rust`, `cargo add sha2`. Read `input.bin`, hash, write hex to stdout. `cargo build --release` with `[profile.release] lto = "fat" codegen-units = 1`.
3. **C:** Use OpenSSL `EVP_Digest`. `gcc sha.c -O3 -lcrypto -o sha_c`.
4. **Zig:** Use `std.crypto.hash.sha2.Sha256`. `zig build-exe sha.zig -O ReleaseFast`.
5. **Python:** `python -c "import hashlib; print(hashlib.sha256(open('input.bin','rb').read()).hexdigest())"`.
6. **Dart:** `dart sha.dart` with the `crypto` package.
7. Bench:
   ```bash
   hyperfine --warmup 3 --runs 20 \
     "./sha_rust/target/release/sha_rust" \
     "./sha_c" "./sha_zig" \
     "python -c '...'" \
     "dart sha.dart" \
     --export-json results.json
   ```
8. Rust-internal bench with criterion: separate `bench` binary, `cargo bench`.
9. Record the `hyperfine` mean ± stddev in a Markdown table, add memory peak via `/usr/bin/time -v` or `valgrind --tool=massif`.

**Definition of Done (DoD):**

- [ ] All 5 implementations produce the same SHA-256 output (proof: `diff` of outputs).
- [ ] `hyperfine` run with ≥20 runs and warmup; JSON export exists.
- [ ] Markdown table in `results.md` with columns: language, mean (ms), stddev, throughput (MB/s), memory peak (MB).
- [ ] Rust criterion bench compiles and yields a p99 latency number.
- [ ] You can identify and explain at least one distortion (e.g. Python startup overhead) by comparing the Python bench with and without warmup.
- [ ] You set `lto="fat" codegen-units=1` in the Rust release profile and can prove the impact (+/- %).
- [ ] Commit: `git commit -m "day88: cross-lang sha256 bench + table"`.

**Extension (optional):** Repeat the bench with `LD_PRELOAD=libmimalloc.so.2` for all native languages — compare whether the allocator is the dominant factor. Second extension: bench on a **different architecture** (RISC-V QEMU from Day 77, or ARM via Docker) and compare the relative language ranking (does it change?).
