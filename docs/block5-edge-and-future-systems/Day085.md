# Day 85: Mini-Capstone: High-Performance Server

**Block:** Block 5: Edge & Future Systems · Capstone

> **Goal of the day:** You build an HTTP server that combines io_uring (network), Tokio (scheduler), and a lock-free queue (conn tracking) — and passes a benchmark under load with concrete p99 latency numbers.

---

## 📖 Theory

The high-performance server combines everything from Block 5 part 2:

- **io_uring** for syscall-free I/O (Day 84)
- **Tokio** as the scheduler for tasks (Day 81)
- **lock-free queue** for conn tracking / metrics counters (Day 82)
- **eBPF** (optional) for observability (Day 83)

### Architecture

```
         ┌──────────────────────────────────┐
NIC ───► │ io_uring accept → tokio task     │  (1 task per conn)
         │   read → parse → handler → write│
         │   metrics → SegQueue (lock-free) │
         └──────────────────────────────────┘
```

Every connection becomes a Tokio task (bytes/task overhead ~100 B → 100k conns = ~10 MB task state, no problem). Metrics are written by every task to a lock-free `SegQueue`, read by a metrics-drainer thread.

### Minimal HTTP server (Hyper + Tokio)

```rust
use std::convert::Infallible;
use hyper::{Body, Request, Response, Server};
use hyper::service::service_fn;

async fn hello(_req: Request<Body>) -> Result<Response<Body>, Infallible> {
    Ok(Response::new(Body::from("hi\n")))
}

#[tokio::main(flavor = "multi_thread", worker_threads = 4)]
async fn main() {
    let addr = ([127,0,0,1], 9200).into();
    let make_svc = hyper::service::make_service_fn(|_conn| async {
        Ok::<_, Infallible>(service_fn(hello))
    });
    Server::bind(&addr).serve(make_svc).await.unwrap();
}
```

Hyper uses Tokio + (on Linux 5.10+) io_uring for file I/O internally; for networking Hyper currently uses `mio`-epoll — direct io_uring networking is available via `tokio-uring` (Day 84), Hyper-io_uring PRs are in progress.

### Latency vs. throughput tradeoff

High throughput (RPS) and low latency (p99) are *opposing*: more worker threads = more throughput, but context-switching latency. Empirical sweet spot: `worker_threads = CPU cores`, `conn-queue = 2× backlog`. For p99 fairness: insert `tokio::task::yield_now` periodically to smooth tail latency.

### Why this matters

This capstone proves you can compose Day 81–84. The result is a server that can keep up with Cloudflare-/Fastly-style edge functions — that is the building block of the edge-to-cloud pipeline (Day 80) and the polyglot runtime (Day 90).

### Pitfalls

- **Hyper versions**: `hyper = "1"` with `hyper-util` server — API different from `hyper = "0.14"`. Use `axum` (builds on hyper 1) if you don't need a custom HTTP engine.
- **Backlog:** set `somaxconn` kernel-side to ≥ `conn-queue`, otherwise `accept()` drops.
- **Nagle + delayed ack:** for small responses `TCP_NODELAY` is essential (`hyper` sets it by default).
- **`ulimit -n`** — default 256 open files; for 10k conns: `ulimit -n 65535`.
- **Benchmarking sin:** don't measure on the same CPU as the server; use a different machine or pin cores.

## 🛠️ Practice

**Task:** Build a minimal HTTP "hi" server with Axum + Tokio + crossbeam `SegQueue` for a request counter. Benchmark with `wrk` and reach p99 < 5 ms at 1000 concurrent connections.

**Step by step:**

1. `cargo new day85 --bin`, `cargo add axum tokio crossbeam-queue -F tokio/full`.
2. In `src/main.rs`, implement the Axum server:

   > **Hints:**
   > - Wrap a `crossbeam_queue::SegQueue<u64>` in an `Arc` inside a `Clone` state struct (e.g. `struct C(Arc<SegQueue<u64>>)`) so it can be shared as Axum state.
   > - Write an async handler `hi(c: C) -> String` that pushes a value onto the queue and returns `"hi\n"`.
   > - Build a `Router::new().route("/", get(hi)).with_state(c)` and serve it with `axum::serve` bound to `127.0.0.1:9200`.
   > - Use `#[tokio::main]` as the entry point.
3. `ulimit -n 65535 && cargo run --release`.
4. Benchmark in a 2nd terminal (`brew install wrk`):

   ```bash
   wrk -t4 -c1000 -d10s http://127.0.0.1:9200/
   # note Requests/sec, Latency p50/p75/p90/p99
   ```

5. Vary `worker_threads` and backlog; record 3 configurations in a table.
6. Verify lock-free metrics: after the bench, count `SegQueue::len()` and compare with `wrk` reports.

**Definition of Done (DoD):**

- [ ] Server compiles with `axum` + `crossbeam-queue` and runs on `:9200`.
- [ ] `wrk -t4 -c1000 -d10s` shows ≥ 30 000 requests/s (loopback, modern laptop) and p99 < 5 ms.
- [ ] Lock-free counter: after 10 000 requests → `SegQueue::len()` = 10 000 (or close, race-tolerant count).
- [ ] You have a table with ≥3 configurations (worker_threads × backlog) and can explain the p99 trend.
- [ ] You can name the 3 layers combined here (io_uring network/Tokio scheduler/lock-free queue) and which day delivered each.
- [ ] Commit: `git commit -m "day85: high-perf http server (axum + tokio + segqueue)"`.

**Extension (optional):** Replace Axum with a pure `tokio-uring` acceptor and a hand-written HTTP parser — measure the RPS difference (you see the Hyper-Axum overhead). Alternative: build an Aya eBPF trace for `tcp_recvmsg` and correlate conn rate with kernel function call rate.
