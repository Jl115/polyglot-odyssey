# Day 90: Block-Capstone: Multi-Language System

**Block:** Block 5: Edge & Future Systems · Capstone

> **Goal of the day:** You build a polyglot system that extends the edge-to-cloud pipeline (Day 80) with language interoperability: Rust core + WASM edge + Python ML processor + Dart dashboard, connected via FFI and HTTP.

---

## 📖 Theory

The block capstone synthesizes Day 76–89 into a *real polyglot system*. The central lesson: **different languages for different layers**, connected over **stable ABI boundaries** (`extern "C"`, HTTP, Protobuf), not over "one language everywhere".

### The architecture

```
┌─────────────────────────────────────────────────────────────┐
│                     Multi-Language System                    │
├─────────────────────────────────────────────────────────────┤
│  Edge (WASM, Day 79)        │  Cloud (Rust + Tokio, Day 81) │
│  ┌──────────────────────┐  │  ┌─────────────────────────┐  │
│  │ Rust→wasm32-wasip1   │──┼─>│ Axum HTTP API           │  │
│  │ Sensor aggregation   │  │  │  + Python via FFI       │  │
│  └──────────────────────┘  │  │   (Day 86 ctypes/PyO3)  │  │
│                            │  │  + Metrics-SegQueue     │  │
│                            │  │   (Day 82 lock-free)    │  │
│                            │  └──────────┬──────────────┘  │
│  Dart Desktop Dashboard    │             │                │
│  (Day 87 dart:ffi)         │             ▼                │
│  ┌──────────────────────┐  │  ┌─────────────────────────┐  │
│  │ Flutter UI + Rust FFI│<─┼──│ HTTP /ingest /metrics   │  │
│  └──────────────────────┘  │  └─────────────────────────┘  │

```

### The language choice (from Day 89)

| Subsystem | Language | Reason |
|-----------|---------|-----------|
| Edge aggregation | Rust + WASM | start < 1 ms, sandbox, portable (Day 79/80) |
| Cloud HTTP API | Rust + Axum | p99 < 5 ms, memory-safe, io_uring (Day 85) |
| ML postprocessing | Python | ecosystem, ML libraries, FFI binding (Day 86) |
| Dashboard | Dart + Flutter | cross-platform UI, dart:ffi for Rust calls (Day 87) |
| Metrics pipeline | Rust + crossbeam | lock-free under high conn load (Day 82) |

The **seams** are the critical spots: HTTP (Axum↔Dart), FFI (Rust↔Python), WASM capabilities (edge↔cloud). That is where the bugs happen.

### Concrete specification

**Data flow:**
1. **Edge (WASM):** reads `/data/sensor.txt` (simulated), aggregates to `{"avg":..,"n":..,"ts":..}`, POSTs to cloud.
2. **Cloud (Axum):** `POST /ingest` receives JSON, puts it on a `SegQueue`, a background task pulls and calls **Python FFI** (e.g. an anomaly score via `numpy`).
3. **Python (via ctypes):** gets raw values, returns a score (0-1); Rust writes it to a `metrics` map.
4. **Dashboard (Dart):** polls `GET /metrics`, shows a time series; for complex computation it calls a Rust lib via `dart:ffi` (e.g. a statistics function).

### Seam contracts

**HTTP contract (cloud ↔ Dart):**
```
GET /metrics → [{ts, avg, score}, ...]   (JSON)
POST /ingest ({"avg":..,"n":..,"ts":..}) → "ok"
```

**FFI contract (Rust ↔ Python):**
```rust
#[no_mangle]
pub extern "C" fn anomaly_score(values: *const f64, len: usize) -> f64;
```
Python via `ctypes` — caller-owned buffer, scalar return value.

**FFI contract (Rust ↔ Dart):** analogous to Day 87, a `stats` function.

### Why this matters

This is the outcome proof of the entire Block 5. Whoever builds this capstone has proven they can *architecturally think through* polyglot systems and *securely connect them at the seams*. It is the precursor to the final capstone (Block 6) and the practical exam of the Language Choice Matrix (Day 89).

### Pitfalls

- **Scope control** — this is *one* day. Not every subsystem will be perfect. Prioritize: edge→cloud pipeline first (Day 80 refinement), then Python FFI, then Dart UI; the Dart UI can also be a simple `curl` CLI client if time is tight.
- **Python FFI panic trap** — Rust `panic!` across FFI = UB. Wrap with `catch_unwind`.
- **WASM HTTP capability** — `wasi-http` is still in flux; use stdout piping as in Day 80 as a fallback.
- **Dart path lookup** — copy the Rust `cdylib` next to the Flutter binary or use absolute paths via `Platform.resolvedExecutable`.
- **Async vs. FFI** — a Python FFI call is synchronous and blocks a Tokio worker; use `tokio::task::spawn_blocking`.
- **Memory cleanup** — every FFI fn that allocates needs a `free_*` counterpart.

## 🛠️ Practice

**Task:** Build the Multi-Language System from four subsystems (edge-WASM, cloud-Axum+Python-FFI, Dart dashboard). Prove end-to-end: 5 sensor values → pipeline → dashboard shows aggregated metric.

**Step by step:**

1. **Reusing Day 80:** edge-WASM module + Axum cloud as the base. Add a `/metrics` endpoint that outputs the `SegQueue` contents as JSON.
2. **Python FFI:** extend the Rust lib from Day 86 with `anomaly_score(*const f64, usize) -> f64` (e.g. a simple stddev-based anomaly). Build as `cdylib`.
3. **Python binding:** `ctypes.CDLL("./libday90core.so")`, `anomaly_score.argtypes = [POINTER(c_double), c_size_t]`, `restype = c_double`. Test standalone with `[1.0, 1.1, 1.0, 5.0]` → should give a high score.
4. **Cloud calls Python:** *instead of* Python calling Rust via FFI (possible via `PyO3`), the easier variant is: Rust calls *its own `cdylib`*, which in turn is tested via Python `ctypes` — or the reverse: Python calls the Rust `cdylib` and writes the score back to the cloud via HTTP. Pick one variant and document it.
5. **Dart dashboard:** minimal Flutter UI (or a CLI Dart script if time is short) that polls `GET /metrics` and shows the last 5 values. Optional: Rust `stats` via `dart:ffi` for local aggregation.
6. **End-to-end:** generate 5 sensor values, trigger the edge, observe the cloud log + Dart dashboard.

**Definition of Done (DoD):**

- [ ] All four subsystems (edge-WASM, cloud-Axum, Python-FFI lib, Dart client) compile and run.
- [ ] End-to-end: 5 sensor values → dashboard shows at least 3 aggregated metrics.
- [ ] The language-choice table from Day 89 is cited in the capstone README with reasoning per subsystem.
- [ ] At least one FFI contract is documented (`anomaly_score` signature + ownership rule).
- [ ] A provoked failure pipeline (cloud down → edge behavior; Python panic across FFI → clean error return) is tested and documented.
- [ ] `architecture.md` in the repo root shows the diagram from the theory section (adapted to your reality).
- [ ] Commit: `git commit -m "day90: polyglot capstone (rust+wasm+python+dart)"`.

**Extension (optional):** Replace stdout piping with a real `wasi-http` component. Alternative: deploy the cloud part in a `kind` cluster (Block 3, Day 41) with a Helm chart — proves DevOps integration. Third variant: build an eBPF observability layer (Day 83) that shows conn rates.
