# Day 79: WASM on Edge

**Block:** Block 5: Edge & Future Systems · WebAssembly Runtime

> **Goal of the day:** You compile a Rust module to `wasm32-wasip1` and run it in `wasmtime` — with a defined memory limit, a precompiled module, and real sandboxing.

---

## 📖 Theory

**WebAssembly (WASM)** is a portable, sandboxed bytecode VM originally developed for the browser — but via WASI (WebAssembly System Interface) it also runs server-side and at the edge. For edge compute, WASM is attractive because modules cold-start in **milliseconds** (no container boot time) and are isolated (capability-based security).

### WASM vs. containers at the edge

| Property | Container (Docker) | WASM (Wasmtime/WasmEdge) |
|----------|--------------------|-----------------------|
| Cold start | 100ms–seconds | **< 1 ms** |
| Size | MB–GB | **KB–MB** |
| Isolation | Namespaces/seccomp | **Memory sandbox + capabilities** |
| Portability | architecture-dependent | **arch-independent (bytecode)** |
| Performance | native | ~near-native (JIT/AOT) |

This is why WASM is the standard for edge functions (Cloudflare Workers, Fastly Compute, Shopify Functions).

### The WASI model

WASI (currently `wasip1` aka "preview1", `wasip2` in development) is the POSIX-like API. WASM has *no* direct syscall access — every host call goes through a capability gate. So an edge module can, for example, only read files the host has explicitly mounted.

```rust
// Cargo.toml
// [dependencies] wasi = "0.13"   (or std with wasip1)
```

```rust
use std::fs;
fn main() {
    // only reads files the host released via --dir
    if let Ok(s) = fs::read_to_string("/data/in.txt") {
        println!("{}", s.len());
    }
}
```

### Compile + run

```bash
# 1. Add the Rust target
rustup target add wasm32-wasip1

# 2. Compile
cargo build --release --target wasm32-wasip1

# 3. Run in wasmtime (with capability: only read /tmp)
wasmtime --dir=/tmp::/data target/wasm32-wasip1/release/myapp.wasm
```

### Precompile for cold starts

Edge workloads benefit from AOT compilation. `wasmtime` can precompile a `.wasm`:

```bash
wasmtime compile module.wasm -o module.cwasm
# Run the precompiled module (cache-warm, ~0 cold-start cost):
wasmtime run module.cwasm
```

### Why this matters

The edge-to-cloud pipeline benefits from WASM in two ways: (1) edge functions (filter, aggregation, inference) start fast and run isolated; (2) ML code (via TVM `wasm` target or `wasmtime`-ML) is portable between edge devices and the cloud. Capabilities also make WASM a secure sandbox for AI agents (see Block 3, Day 43).

### Pitfalls

- **WASI preview1 vs. preview2:** `wasm32-wasip1` is stable; `wasm32-wasip2` (component model) is new, API-different, not all crates compatible.
- **Threads:** `wasm32-wasip1` is single-threaded; shared memory/threads need `wasm32-wasip1-threads` or `wasm64`.
- **Networking:** raw sockets are not exposed in WASI (security) — for HTTP use `wasi-http` (via a host implementation).
- **Filesystem capability:** `--dir=host::guest` maps only the released paths; `fs::read_to_string("/etc/passwd")` fails without `--dir=/etc`.

## 🛠️ Practice

**Task:** Write a Rust program that reads a file `/data/in.txt` and returns the line count; compile to `wasm32-wasip1` and run it isolated in `wasmtime`.

**Step by step:**

1. Install Wasmtime: `cargo install wasmtime-cli` or `brew install wasmtime`.
2. `cargo new --bin day79` and in `src/main.rs`:

   > **Hints:**
   > - Open `/data/in.txt` with `std::fs::File::open` and handle the `Result` (`.expect` is fine for now).
   > - Wrap the file in a `std::io::BufReader` and use the `BufRead` trait's `.lines()` iterator.
   > - Count the lines (`.count()`) and print the result with `println!`.
3. Add the target and build:

   ```bash
   rustup target add wasm32-wasip1
   cargo build --release --target wasm32-wasip1
   ```

4. Run without a capability → provoke the error:

   ```bash
   wasmtime target/wasm32-wasip1/release/day79.wasm
   # expected: panic "open" — capability missing
   ```

5. Run with the capability:

   ```bash
   echo -e "a\nb\nc" > /tmp/in.txt
   wasmtime --dir=/tmp::/data target/wasm32-wasip1/release/day79.wasm
   # expected: lines: 3
   ```

6. Precompile and run:

   ```bash
   wasmtime compile target/wasm32-wasip1/release/day79.wasm -o day79.cwasm
   wasmtime --dir=/tmp::/data day79.cwasm
   ```

7. Measure cold start: `hyperfine --warmup 1 'wasmtime --dir=/tmp::/data day79.cwasm'` — compare `.wasm` vs. `.cwasm`.

**Definition of Done (DoD):**

- [ ] `cargo build --target wasm32-wasip1` compiles without errors.
- [ ] Run without `--dir` fails with `Permission denied`/panic (capability proof).
- [ ] Run with `--dir=/tmp::/data` prints `lines: 3`.
- [ ] `wasmtime compile` produces a `.cwasm`; `file day79.cwasm` shows an ELF-like magic.
- [ ] You can explain in 2 sentences why WASM sandboxing is *capability-based* and not *namespace-based*.
- [ ] Commit: `git commit -m "day79: wasi module + wasmtime sandbox + precompile"`.

**Extension (optional):** Build the same module as a `wasi-http` handler (with `wasmtime` + `wasi:http/incoming-handler` interface) and deploy it as a local HTTP service. Measure: requests/s via `wrk`.
