# Day 86: FFI & Language Interop

**Block:** Block 5: Edge & Future Systems · Cross-Language Boundaries

> **Goal of the day:** You build a Rust library with a C ABI (`extern "C"`), bind it from C **and** from Python (a `PyO3`-free path via `ctypes`), and measure the FFI call overhead per call.

---

## 📖 Theory

**FFI (Foreign Function Interface)** is the bridge between languages over a shared ABI. Rust's standard ABI is not stable; but **`extern "C"`** uses the C ABI, which *every* language speaks (C, C++, Python via ctypes, Node via napi, Zig, Swift, …). This makes Rust the *shared library* language for polyglot systems.

### The two sides

**Rust side (export):**

```rust
// src/lib.rs
#[no_mangle]
pub extern "C" fn add(a: u64, b: u64) -> u64 { a + b }

#[repr(C)]
pub struct Stats { pub mean: f64, pub n: u64 }

#[no_mangle]
pub extern "C" fn stats(values: *const f64, len: usize) -> Stats {
    if values.is_null() { return Stats { mean: 0.0, n: 0 }; }
    let s = unsafe { std::slice::from_raw_parts(values, len) };
    let mean = s.iter().sum::<f64>() / len as f64;
    Stats { mean, n: len as u64 }
}
```

Important:

- `#[no_mangle]` — no name mangling, the symbol is named exactly `add`.
- `#[repr(C)]` — struct layout like in C (default Rust layout is undefined).
- `extern "C"` — C calling convention.
- Pointer + `unsafe` — the caller is responsible for lifetime/validity.

**C side (import):**

```c
// main.c
#include <stdint.h>
typedef struct { double mean; uint64_t n; } Stats;
extern Stats stats(const double* values, size_t len);

int main() {
    double v[] = {1.0, 2.0, 3.0};
    Stats s = stats(v, 3);
    printf("mean=%f n=%zu\n", s.mean, s.n);
}
```

**Python side (via ctypes, without PyO3):**

```python
import ctypes
lib = ctypes.CDLL("./libday86.so")
lib.stats.restype = ctypes.c_double * 2  # simplified
lib.add.argtypes = [ctypes.c_uint64, ctypes.c_uint64]
print(lib.add(3, 4))   # 7
```

### FFI overhead

Every FFI call costs ~10-50 ns (stack switch + ABI convention). At 1M calls/s that is negligible; at 1B calls/s (e.g. per pixel) it dominates. Solution: **batch APIs** (pointer + length instead of scalar calls).

### Memory ownership rules of thumb

| Who allocates | Who frees | Pattern |
|--------------|----------|---------|
| Rust via `Box` | Rust via `extern "C" fn free_X(*mut T)` | **Rust owns** — standard |
| Caller via C `malloc` | Caller | Caller owns; Rust borrows |
| Rust string to C | C must call `free_rust_string` | string-marshal helper |

**Never** return raw Rust strings — `String`'s layout is not C-stable. Convert to `*mut c_char` (CString) and pass ownership + a free function.

### Why this matters

Polyglot systems (Day 90) need a shared ABI. Rust as "performance core" + Python/JS/Dart as "app layer" is the standard pattern of modern tech stacks (e.g. cryptography, ML codecs, parsers). FFI is the seam — and building it wrong is the most common source of use-after-free in otherwise safe codebases.

### Pitfalls

- **Panic across FFI = UB.** A Rust panic across an `extern "C"` boundary is undefined. Use `catch_unwind` and make an error return.
- **`String`/`Vec`/`HashMap` not across FFI** — layout not stable. Always convert to `#[repr(C)]` structs or raw pointers.
- **Lifetime on the pointer** — Rust cannot check it. `unsafe` contract on the caller.
- **`Drop` across FFI** — a Rust type with drop logic must not be treated as opaque in C if C does not free it via a Rust free function.
- **ABI stability** — Rust occasionally changes its internal calling convention; `extern "C"` stays stable.
- **Macros/templates** — C++ templates and Rust generics are ABI-incompatible; only concretely instantiated `extern "C"` fns are stable.

## 🛠️ Practice

**Task:** Build a Rust shared library with `add` and `stats` (mean), compile as `.so/.dylib`, and call both from C and Python. Measure overhead with 10 M `add()` calls.

**Step by step:**

1. `cargo new --lib day86`. In `Cargo.toml`:

   ```toml
   [lib]
   crate-type = ["cdylib"]   # shared library for FFI
   ```

2. Code from the example above into `src/lib.rs`.
3. Build: `cargo build --release` → `target/release/libday86.so` (Linux) or `libday86.dylib` (macOS).
4. **C binding:** `main.c` from example → `gcc main.c -L target/release -lday86 -o ctest && ./ctest` (possibly `DYLD_LIBRARY_PATH=target/release`).
5. **Python binding:** script from example (adjust `.so`/`.dylib` name). Run it.
6. **Overhead bench (Python)** — write a script that:

   > **Hints:**
   > - Load the `cdylib` via `ctypes.CDLL`, call `add(1, 2)` in a loop of 10 million iterations.
   > - Time the loop with `time.perf_counter()` and print the average ns/call.
   > - Compare with the same loop doing pure Python `1 + 2` to see the FFI overhead.
7. Compare with pure Python `1+2` in the same loop — the FFI overhead becomes visible.

**Definition of Done (DoD):**

- [ ] `cargo build` produces a `cdylib` (`file target/release/libday86.*` shows shared library).
- [ ] C program prints `mean=2.000000 n=3`.
- [ ] Python program prints `7` (via `ctypes`).
- [ ] Bench shows a concrete ns/call number (typ. 20-80 ns/call).
- [ ] You tested a panic trap: a Rust fn that `panic!`s, called from C → observe crash/UB. Then add a `catch_unwind` wrapper that returns an error code — observe clean return.
- [ ] You can explain in 2 sentences why `String` cannot go directly across FFI and what the alternative is.
- [ ] Commit: `git commit -m "day86: rust cdylib + C + ctypes binding + bench"`.

**Extension (optional):** Build a second variant with `PyO3` (proper Python extension). Compare call overhead: `PyO3` (~50 ns) vs `ctypes` (~30 ns) — and the comfort tradeoff. Third variant: Node.js via `node-addon-api` (napi).
