# Day 39: Observability & Tracing

**Block:** Block 3: AI-Native Development · LLM Observability

> **Goal of the day:** You instrument a LangGraph run with LangSmith (or OpenTelemetry) and read a trace that shows every LLM call, every tool invocation, and the token cost per node.

---

## 📖 Theory

LLM applications are **non-deterministic and distributed**: a single agent run can contain 5–50 LLM calls, tool invocations, and DB queries. Without tracing, "why is the answer wrong?" is unanswerable. Three pillars of observability:

1. **Traces** — hierarchical trees of *spans*: an agent span contains Researcher spans, which contain LLM spans and tool spans. Per span: inputs, outputs, duration, cost, token counts.
2. **Metrics** — aggregated across runs: p50/p95 latency, error rate, cost per request, tool usage rate.
3. **Logs** — structured JSON logging, correlated by `trace_id`.

### LangSmith: the de-facto standard

LangSmith is LangChain's cloud observability for LangGraph. Setup is two environment variables, then every `app.invoke`/`astream` is traced automatically.

```bash
export LANGSMITH_API_KEY="ls__..."
export LANGSMITH_TRACING=true
export LANGSMITH_PROJECT="day39"
```

### OpenTelemetry alternative (vendor-neutral)

For self-hosted / vendor-lock-in-free setups: the OpenTelemetry LangChain instrumentation package.

```python
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.instrumentation.langchain import LangchainInstrumentor

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(
    OTLPSpanExporter(endpoint="http://localhost:4318/v1/traces")))
LangchainInstrumentor().instrument()   # all LLM/tool calls become spans
```

### Key metrics extracted from traces

| Metric | Meaning | Alert when |
|---|---|---|
| `tokens_in / tokens_out` per span | context usage | `tokens_in` > 80% of model limit |
| `span_duration_ms` p95 | latency per node | p50 rises > 2× over 24h |
| `total_cost_usd` per trace | cost per request | daily cost > budget |
| `tool_error_rate` | fraction of failed tool calls | > 5% |
| `retrieval_hit_rate` | fraction of RAG hits with a source | < 70% on factual questions |

### Why this matters

Without tracing, a multi-agent system (Day 37) is a black box: you see the final answer but don't know *which* node introduced the hallucination or *which* tool was too slow. For the block capstone (an AI dev tool running on real PRs) observability is not a nice-to-have, it is a prerequisite for making debugging possible at all.

### Pitfalls

- **PII leak:** traces contain raw inputs — API keys, emails, source code with secrets. LangSmith has data masking; OTel needs a `SpanProcessor` filter.
- **Sampling:** at high traffic, 100% tracing = cost explosion. `LANGSMITH_SAMPLING_RATE` or OTel `ParentBased(TraceIdRatio(0.1))`.
- **Orphaned async spans:** when an `asyncio.gather()` spawns sub-tasks without propagating the parent span, they land as root traces. Check `contextvars` propagation.
- **Wrong cost aggregation:** on multi-model runs (e.g. Haiku tool + Opus answer) the model prices must be summed separately, otherwise the "cost-per-trace" metric is worthless.

## 🛠️ Practice

**Task:** Instrument your Day 37 multi-agent run with LangSmith (or OTel + Jaeger) and identify the most expensive and slowest node.

**Step by step:**

1. LangSmith account (free tier is enough) → API key in `.env`.
2. Before the Day 37 script, load your `.env` and enable LangSmith tracing
   via environment variables:

   > **Hints:**
   > - Use `python-dotenv`'s `load_dotenv()` to pull `LANGSMITH_API_KEY` from `.env`.
   > - Set `os.environ["LANGSMITH_TRACING"] = "true"` and `os.environ["LANGSMITH_PROJECT"] = "day39"`.
   > - Once these are set, every `app.invoke(...)` / `app.astream(...)` call is traced automatically — no manual span code needed.
3. Run a known request: `python -c "from multi import app; app.invoke({'messages':['Write qsort in Rust'],'next':''})"`.
4. Open the LangSmith UI → `day39` project → latest trace.
5. Read the trace tree view: identify (a) the most expensive LLM span, (b) the slowest node, (c) the tool usage rate.
6. Add a custom traced function so your quality gate shows up as its own span
   in the LangSmith trace:

   > **Hints:**
   > - Import `traceable` from the `langsmith` package and decorate your quality-gate function with `@traceable(name="quality_check")`.
   > - The function reads `state.get("draft", "")` and returns `"ok"` or `"rewrite"` based on a length threshold.
   > - The decorated function appears as a named child span in the trace tree, separate from the LLM call spans.
7. Write a `metrics.json` containing `total_tokens`, `total_cost_usd`, `p95_latency_ms` per run.

**Definition of Done (DoD):**

- [ ] LangSmith UI shows a trace with ≥ 3 spans (supervisor + 2 workers).
- [ ] Per span, `input`, `output`, `tokens`, and `cost_usd` are visible.
- [ ] `metrics.json` contains `total_cost_usd` as a number with 4 decimal places.
- [ ] You can name *which* node has the highest latency — and a hypothesis why.
- [ ] A masking filter (e.g. regex for `sk-...` API keys) is active, or you proved no secrets land in the trace.
- [ ] Commit: `git commit -m "day39: langsmith tracing on multi-agent"`.

**Extension (optional):** Set an alert rule in LangSmith: "If `total_cost_usd > 0.05` for a trace, tag it as `high_cost`."
