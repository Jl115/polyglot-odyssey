## 📖 Theory

**Kubernetes** orchestrates containers across a cluster: the *API server* accepts desired-state manifests (YAML); *controllers* reconcile real state; the *scheduler* places pods on nodes. For AI workloads the interesting parts are **GPU scheduling**, **resource quotas**, and **init containers** (model download).

### Core resources

| Resource | Purpose | AI relevance |
|---|---|---|
| `Pod` | Run unit with containers | Requests/limits: CPU, memory, GPU |
| `Deployment` | Replica set, rolling updates | Stateless model serving |
| `Service` | Stable network IP + LB | Endpoint for vLLM (Day 42) |
| `ConfigMap` / `Secret` | Configs and secrets | API keys, model paths |
| `StatefulSet` | Persistent identity | Vector DB (Qdrant), checkpoints |
| `Job` / `CronJob` | Batch runs | Fine-tuning, eval pipelines |
| `HPA` | Horizontal Pod Autoscaler | Traffic-based scaling of the API |

### GPU scheduling

For a pod to get a GPU, the node needs NVIDIA GPU drivers + the `nvidia/k8s-device-plugin`. Then a pod can *request*:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

The scheduler reserves exactly one GPU; multiple pods share GPUs only via *Multi-Instance GPU (MIG)* or *time-slicing* (advanced). Without a GPU node the pod goes `Pending`.

### Manifest: simple HTTP server

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: echo
spec:
  replicas: 2
  selector:
    matchLabels: {app: echo}
  template:
    metadata:
      labels: {app: echo}
    spec:
      containers:
      - name: echo
        image: hashicorp/http-echo:1.0
        args: ["-listen=:8080", "-text=hello-from-k8s"]
        resources:
          requests: {cpu: "100m", memory: "64Mi"}
          limits:   {cpu: "200m", memory: "128Mi"}
---
apiVersion: v1
kind: Service
metadata:
  name: echo
spec:
  selector: {app: echo}
  ports:
  - port: 80
    targetPort: 8080
```

### Why this matters

An AI dev tool that comments on PRs is an HTTP service — and in production it will run on K8s (or similar). The infra topics GPU scarcity, memory OOM-kills during model loading, init-container downloads, zero-downtime rolling updates are *concrete* operational tasks of the capstone (Days 45/55). Anyone who has never operated K8s locally will fail in the cloud.

### Pitfalls

- **`Pending` pods:** no node satisfies the requests (too little CPU/GPU/memory). `kubectl describe pod <name>` shows the scheduling errors.
- **OOMKilled:** model loading often needs 2× the model weight in memory (framework overhead). Set limits high enough; init containers don't use GPU memory.
- **ImagePullPolicy `Always`** on large model images → 30s+ pull per pod start. Set `IfNotPresent` for releases.
- **No resource requests** → pods share CPU unfairly and one starves. Always specify `requests`, even without `limits`.

## 🛠️ Practice

**Task:** Start a local cluster with `kind`, deploy the echo server, scale to 4 replicas, and observe the service load balancer.

**Step by step:**

1. Install tools:
   ```bash
   brew install kind kubectl helm
   ```
2. Create the cluster:
   ```bash
   kind create cluster --name ai-dev
   kubectl cluster-info --context kind-ai-dev
   ```
3. Create the manifest `echo.yaml` (above), apply it:
   ```bash
   kubectl apply -f echo.yaml
   kubectl rollout status deployment/echo   # → "successfully rolled out"
   kubectl get pods -l app=echo
   ```
4. Port-forward to your machine:
   ```bash
   kubectl port-forward svc/echo 8080:80
   curl localhost:8080    # → "hello-from-k8s"
   ```
5. Scale and HPA demo (manual without a metrics server):
   ```bash
   kubectl scale deployment echo --replicas=4
   kubectl get pods -l app=echo -w   # 4 pods become Running
   ```
6. Set a resource quota (prevents chaos in the cluster):
   ```bash
   kubectl create quota ai-quota --hard=cpu=2,memory=2Gi,pods=10
   ```

**Definition of Done (DoD):**

- [ ] `kubectl get nodes` shows at least one `Ready` node.
- [ ] `kubectl get deployment echo` shows `2/2` replicas available.
- [ ] `curl localhost:8080` (during port-forward) returns `hello-from-k8s`.
- [ ] After `kubectl scale --replicas=4` there are 4 `Running` pods.
- [ ] `kubectl describe pod <pod>` shows CPU/memory requests.
- [ ] `kind delete cluster --name ai-dev` cleans up properly.
- [ ] Commit: `git commit -m "day41: local kind cluster + echo deployment"`.

**Extension (optional):** Install the `metrics-server` (`kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml`) and try `kubectl top pods`. Then HPA can work for real.
