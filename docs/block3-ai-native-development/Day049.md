# Day 49: Model Compression & Quantization

**Block:** Block 3: AI-Native Development · ML Engineering

> **Goal of the day:** You quantize a fine-tuned model to 4-bit (GGUF Q4_K_M or AWQ), measure VRAM/latency/quality loss versus the fp16 original, and make an informed decision about when 4-bit is good enough.

---

## 📖 Theory

LLMs are large: a 7B model in fp16 = 14 GB of weights. On edge laptops or 8 GB GPUs that doesn't fit. **Quantization** reduces the precision (16-bit → 4-bit) and thus the size to ~25%, with a measurable but small quality loss.

### Quantization methods

| Method | Mechanism | Use case |
|---|---|---|
| **PTQ (Post-Training)** | quantize weight buckets after the fact | standard, fast |
| **GGUF Q4_K_M** | llama.cpp format, K-quants, 4-bit mixed | CPU/edge serving |
| **AWQ** | activation-aware, only "salient" weights in 4-bit | GPU serving (vLLM) |
| **GPTQ** | quantization via inverse Hessian | GPU serving (legacy) |
| **BitsAndBytes NF4** | NF4 NormalFloat for QLoRA fine-tuning | fine-tuning on consumer GPU |
| **QLoRA** | 4-bit frozen base + LoRA adapter trainable | fine-tuning on an 8 GB GPU |

### QLoRA fine-tuning (4-bit base + LoRA)

```python
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
import torch

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
)
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct", quantization_config=bnb)
# then with a peft LoRA adapter as in Day 46
```

### Trade-off table (example 7B model)

| Format | Size | VRAM | Relative speed | Quality (BLEU vs fp16) |
|---|---|---|---|---|
| fp16 | 14 GB | 18 GB | 1.0× | 100% |
| Q8_0 | 7.5 GB | 9 GB | 1.1× | 99% |
| Q4_K_M | 4.4 GB | 6 GB | 1.3× | 95% |
| Q3_K_M | 3.5 GB | 5 GB | 1.4× | 90% |
| AWQ-4bit | 4.0 GB | 5.5 GB | 1.2× (GPU) | 94% |

### Why this matters

The capstone (Day 55) runs on a realistic host — possibly an 8 GB GPU or only CPU. Without quantization nothing works. Moreover, *cost per inference* is a production criterion: 4-bit costs ¼ of the VRAM → 4× throughput per GPU → directly in € savings.

### Pitfalls

- **Q4 for very small models (≤ 1B):** quality loss is noticeable. For 0.5B → prefer Q5 or Q8; 4-bit is only recommendable from ~3B+.
- **Tokenizer/EOS-token change** when converting to GGUF: format version incompatibility (llama.cpp vs HF). Always check `--vocab-type`.
- **AWQ models are not compatible with every vLLM version** — pin versions and freeze the Docker image.
- **The KV-cache is *not* quantized** — on long contexts the cache grows linearly; VRAM planning must account for weights + cache.
- **CUDA kernel fallback:** some quantizations have slow fallback paths on older GPUs (e.g. pre-Ampere). Benchmark instead of assuming.

## 🛠️ Practice

**Task:** Quantize Qwen2.5-1.5B (or your fine-tuned model from Day 46) to Q4_K_M GGUF, measure and compare to fp16 on size, speed, and quality.

**Step by step:**

1. Setup:
   ```bash
   pip install llama-cpp-python transformers
   brew install llama.cpp   # or from source for the latest
   ```
2. Measure the fp16 base model (via vLLM/transformers): VRAM peak, p50 latency, BLEU on the Day 48 eval set.
3. Download Q4_K_M GGUF (above) or convert yourself:
   ```bash
   python convert_hf_to_gguf.py ./base --outfile base-fp16.gguf
   ./llama-quantize base-fp16.gguf base-q4km.gguf q4_k_m
   ls -lh base-q4km.gguf  # → ~1 GB instead of 3 GB
   ```
4. Start the Q4 server: `llama-server -m base-q4km.gguf --port 8080`.
5. Run the Day 48 eval script against both servers (fp16 server + q4 server), compare BLEU+ROUGE.
6. Latency test: 20 requests, measure p50/p95.

**Definition of Done (DoD):**

- [ ] `base-q4km.gguf` exists; size ≤ 35% of the fp16 version.
- [ ] `eval.py` produces two metric dicts: `{"fp16": {...}, "q4_km": {...}}`.
- [ ] Quality difference (BLEU) ≤ 5% documented; if > 5%, comment on *why*.
- [ ] Latency difference: Q4 is not slower than fp16 on the target hardware (CPU or GPU), ideally faster.
- [ ] VRAM/RAM usage documented: `nvidia-smi` peak or `ps -o rss` on CPU.
- [ ] You write in `notes.md`: when Q4 is "good enough" and when Q8/fp16 is needed.
- [ ] Commit: `git commit -m "day49: gguf q4 quantization + eval vs fp16"`.

**Extension (optional):** QLoRA fine-tuning: load Qwen2.5-7B in 4-bit and train a LoRA adapter from Day 46 — demonstrate you can fine-tune without loading 7B in fp16.
