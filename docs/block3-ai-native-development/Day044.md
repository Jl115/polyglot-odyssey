## 📖 Theory

**Helm** is the package manager for Kubernetes: a *chart* is a set of parameterized manifest templates (`values.yaml` + `templates/*.yaml`). **GitOps** (ArgoCD, Flux) makes the Git repo the *single source of truth*: a controller polls the repo and reconciles the cluster — no more manual `kubectl apply`.

### Helm chart structure

```
mychart/
├── Chart.yaml          # name, version, description
├── values.yaml         # defaults: image, port, replicas, model
├── templates/
│   ├── deployment.yaml  # {{ .Values.image }} …
│   ├── service.yaml
│   └── _helpers.tpl
```

### `values.yaml` for vLLM

```yaml
image: vllm/vllm-openai:latest
replicas: 1
model: Qwen/Qwen2.5-7B-Instruct
gpu: 1
service:
  port: 8000
resources:
  limits:
    nvidia.com/gpu: "{{ .Values.gpu }}"
    memory: 24Gi
```

### Template `deployment.yaml`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-vllm
spec:
  replicas: {{ .Values.replicas }}
  selector:
    matchLabels: {app: {{ .Release.Name }}}
  template:
    metadata:
      labels: {app: {{ .Release.Name }}}
    spec:
      containers:
      - name: vllm
        image: {{ .Values.image }}
        args: ["--model", "{{ .Values.model }}", "--port", "{{ .Values.service.port }}"]
        resources: {{ .Values.resources | toYaml | nindent 8 }}
        ports: [{containerPort: {{ .Values.service.port }}}]
```

### GitOps model

```
Git repo (desired state) ──┐
                           │ poll
                           ▼
ArgoCD controller ─────────┐
                           │ diff vs cluster
                           ▼
                       kubectl apply (auto)
```

No manual cluster changes. Every change is a Git commit with author, reviewer, timestamp — audit trail included.

### ArgoCD installation (local on kind)

```bash
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl port-forward -n argocd svc/argocd-server 8081:443
# password: kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
```

### Application manifest

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: {name: vllm, namespace: argocd}
spec:
  source:
    repoURL: https://github.com/you/ai-infra
    path: charts/vllm
    targetRevision: HEAD
  destination:
    server: https://kubernetes.default.svc
    namespace: ai
  syncPolicy:
    automated: {prune: true, selfHeal: true}
```

### Why this matters

A dev tool with GitHub integration *is* GitOps by definition: PR → CI → image → GitOps controller → cluster. Manual `kubectl apply` is neither scalable nor auditable. Helm + ArgoCD are today's de-facto standard; the capstone (Day 55) will be deployed this way.

### Pitfalls

- **`selfHeal: true` vs. manual hotfixes:** if someone does `kubectl edit` in production, ArgoCD overwrites it immediately. Either practice real GitOps discipline or set `selfHeal: false` for critical workloads.
- **Chart version collision:** `helm upgrade` without `--version` jumps to `latest` — in prod the chart version should be pinned in the Git repo (`Chart.yaml` → `version:`).
- **Secret management:** never store API keys in plain `values.yaml` — use `ExternalSecrets` or `SealedSecrets`, otherwise the repo leaks keys.
- **Template syntax errors** show up only in `helm template` or as ArgoCD sync errors; run `helm lint` locally before committing.

## 🛠️ Practice

**Task:** Create a Helm chart `vllm` for the Day 42 deployment, deploy via `helm install`, then via an ArgoCD Application.

**Step by step:**

1. Chart scaffold:
   ```bash
   helm create charts/vllm
   cd charts/vllm
   ```
2. Insert `values.yaml` and `templates/deployment.yaml` (above); clean up the default `templates/` from `helm create` (Ingress, HPA for later).
3. Lint and render locally:
   ```bash
   helm lint .
   helm template myvllm . | head -30
   ```
4. Install on the running kind cluster (Day 41):
   ```bash
   helm install myvllm . --namespace ai --create-namespace
   kubectl -n ai get pods
   ```
5. Upgrade demo:
   ```bash
   helm upgrade myvllm . --set replicas=2
   kubectl -n ai get pods -w    # 2 replicas
   ```
6. Install ArgoCD (snippet above), then create the Application manifest `argocd-app.yaml` and `kubectl apply -f argocd-app.yaml`. ArgoCD UI at `localhost:8081` → Application syncs.
7. GitOps loop: change `replicas: 3` in `values.yaml` in the repo, commit → ArgoCD detects drift → sync → 3 replicas.

**Definition of Done (DoD):**

- [ ] `helm lint charts/vllm` shows `[OK]`.
- [ ] `helm install myvllm` creates a Deployment with the correct image name from `values.yaml`.
- [ ] `helm upgrade --set replicas=2` results in `2/2` replicas in `kubectl get pods`.
- [ ] ArgoCD UI shows Application `vllm` with status `Synced` and `Healthy`.
- [ ] A commit on `values.yaml` with `replicas: 3` leads (within ≤ 60s) to 3 replicas in the cluster — without manual `kubectl apply`.
- [ ] Commit: `git commit -m "day44: helm chart + argocd gitops for vllm"`.

**Extension (optional):** Integrate `SealedSecrets` for the `ANTHROPIC_API_KEY` secret — the key now lives only encrypted in the Git repo.
