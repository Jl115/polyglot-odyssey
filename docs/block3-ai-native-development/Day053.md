## 📖 Theory

A **feature store** is a central registry of features (preprocessed data) that supplies both *training* and *serving* with the same consistent features. Without a feature store, **train-serving skew** arises: training code computes feature X one way, serving code another → model performance in prod ≠ eval.

### Two layers

1. **Offline store** — batch history, large data volumes, for training. (Parquet, BigQuery, Snowflake, ClickHouse.)
2. **Online store** — low-latency lookup at inference (Redis, DynamoDB, Qdrant).

### Feature pipeline example

```
Raw events ──┬─→ offline store (Parquet)
            ├─→ online store (Redis/Qdrant)
            └─→ feature definitions (YAML/code)
                ↑
            training  ──→  model  ──→  serving (reads online store)
```

### Tooling landscape

| Tool | Style | ML integration |
|---|---|---|
| **Feast** | open-source feature store | HF, sklearn, vLLM-custom |
| **Hopsworks** | enterprise FS with training jobs | Spark, Python |
| **Tecton** | cloud-managed | production systems |
| **Qdrant** (local as a feature store) | vector DB with payload | embeddings + metadata |

### Pipeline orchestration

- **Airflow** — industry standard, DAG-based, Python operator.
- **Prefect** — modern, Python-native, simpler setup.
- **Dagster** — asset-centric (feature = asset).

```python
# Prefect: minimalist pipeline
from prefect import flow, task

@task
def extract(): return [{"q": "...", "embedding": [0.1, ...]}]
@task
def transform(rows): return [r | {"ts": "2026-01-01"} for r in rows]
@task
def load(rows):
    from qdrant_client import QdrantClient
    qd = QdrantClient("localhost", port=6333)
    for r in rows:
        qd.upsert("features", {"id": hash(r["q"]) & 0xFFFFFFFF,
                                "vector": r["embedding"],
                                "payload": {"ts": r["ts"]}})

@flow
def daily_features():
    raw = extract()
    rows = transform(raw)
    load(rows)

if __name__ == "__main__":
    daily_features.serve(name="daily-features", cron="0 2 * * *")
```

### Train-serving consistency

The *server* code at vLLM serving must use the same embedding model as the pipeline — otherwise the vectors are inconsistent. The feature store stores the *feature version* (`embedding-model: bge-small-v1.5`) and the server loads exactly that version.

### Why this matters

For the capstone (Day 55) the AI dev tool needs access to *current* repo data (embeddings of the code). When the codebase changes, embeddings must be regenerated — and the server must use the new version. A pipeline + feature store solves this *and* prevents train-serving skew.

### Pitfalls

- **Train-serving skew:** classic. Keep the embedding-version pin identical in both pipelines; the feature store enforces it.
- **Stale online store:** the pipeline breaks, the online store has old data, the model answers with outdated knowledge. Healthcheck: `last_updated_ts` and alert on > 24h.
- **Backfill pain:** a new feature definition → recompute all historical data. The offline store must be efficiently partitioned (e.g. by date).
- **Schema drift:** a new feature column in production but training knew nothing of it → model input dimensions mismatch. Use a schema registry (`protobuf` or `pydantic`).
- **Online store latency:** Redis p50 ~1ms, Qdrant p50 ~5–10ms. At 100+ feature lookups per inference that adds up → use batch-lookup APIs.

## 🛠️ Practice

**Task:** Build a Prefect pipeline that daily computes embeddings from your Block 1 docs (Day 47 output), stores them in Qdrant (online store), and tracks the date in the payload.

**Step by step:**

1. Setup:

   ```bash
   pip install prefect qdrant-client sentence-transformers
   prefect server start   # UI: localhost:4200
   ```

2. `features.py` with the tasks above; `transform` embeds:

   > **Hints:**
   > - Load `SentenceTransformer("BAAI/bge-small-en-v1.5")` once at module scope (384-dim embeddings, matching the Qdrant collection `size`).
   > - In `transform(rows)` encode each row's question (`emb.encode(...).tolist()`) and return dicts carrying `q`, `embedding`, and a `ts` date field.
   > - Expose the flow as a Prefect deployment with a daily cron schedule (`prefect deployment run daily-features/dev`).
3. Create the Qdrant collection (Day 38): `features` with `size: 384`.
4. Deploy:

   ```bash
   python features.py   # serve with cron
   prefect deployment run daily-features/dev
   ```

5. Server-side consistency: in `agent.py` (Day 40) load the embedding model via `payload.embedding_model`, not hard-coded.
6. Backfill demo: add a feature (e.g. `char_count`), run the pipeline with `--backfill` → all old rows get the new field.

**Definition of Done (DoD):**

- [ ] `prefect deployment ls` shows `daily-features`.
- [ ] The pipeline runs once via `prefect deployment run` and writes ≥ 5 points to Qdrant.
- [ ] The Qdrant payload contains `ts` (date) and an `embedding_model` version tag.
- [ ] The server (`agent.py`) loads the embedding model name from the feature-store payload, not hard-coded.
- [ ] The Prefect UI shows green flow runs; on a failed task a red run with logs.
- [ ] Commit: `git commit -m "day53: prefect feature pipeline into qdrant"`.

**Extension (optional):** Swap Prefect for Feast — define the same features in `feature_store.yaml` + `features.py` and build a `get_online_features()` call in the server. Compare complexity vs. the custom Prefect approach.
