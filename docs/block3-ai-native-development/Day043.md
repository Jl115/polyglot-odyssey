# Day 43: WASM Isolation for Agents

**Block:** Block 3: AI-Native Development · Sandbox & Isolation

> **Goal of the day:** You run an LLM-generated code snippet inside a WASM sandbox, the agent executes it, and you can explain why WASM is safer for *untrusted code execution* than raw subprocess calls.

---

## 📖 Theory

LLM agents that execute code (e.g. to see test results) need **isolation**. Three options:

1. **Subprocess** — simple, but the code has full access to filesystem/network; a hallucinated snippet can run `rm -rf /`.
2. **Container** — well isolated, but startup latency ~100ms–1s, large overhead.
3. **WASM sandbox** — starts in <1ms, filesystem/network completely disabled by default, capability-based. Ideal for *short*, *untrusted* code execution.

### WASM model: capability-based security

A WASM module has *by default* **no** access to host resources. Every resource (file, socket, env var) must be explicitly threaded through by the host. This is the opposite of containers/subprocesses, which are *default-on*.

### Extism: universal plugin interface

Extism is a WAI (WebAssembly Interfaces)-based plugin system. A Python host loads a WAT/WASM module and calls its exported functions.

```bash
pip install extism
# or the Python module directly via wasmtime
pip install wasmtime
```

### Rust plugin → WASM

```rust
// plugin.rs → compiles to plugin.wasm (target wasm32-wasip1)
#[no_mangle]
pub extern "C" fn add(a: i64, b: i64) -> i64 { a + b }
```

```bash
rustup target add wasm32-wasip1
rustc --target wasm32-wasip1 plugin.rs -o plugin.wasm
```

### Python host with wasmtime

```python
from wasmtime import Engine, Store, Module, Instance

engine = Engine()
store = Store(engine)
module = Module.from_file(engine, "plugin.wasm")
instance = Instance(store, module, [])
add = instance.exports(store)["add"]
result = add(store, 3, 4)   # → 7
# module can read NO file, open NO connection — capability-free
```

### WASI (WebAssembly System Interface)

WASI is the standardized POSIX-like API for WASM. `wasm32-wasip1` allows file access, but only on pre-opened directories (`--dir ./sandbox`). Without the `--dir` flag: no file operations are possible.

```bash
wasmtime --dir=./sandbox run untrusted.wasm
# module sees only ./sandbox, nothing else
```

### Why this matters

The capstone (Day 55) is an AI dev tool that analyzes PRs and possibly *tests suggested code changes*. Test execution means: unknown code runs. Without a sandbox the tool is a remote-code-execution vector. WASM is the production-realistic answer.

### Pitfalls

- **WASI file path leaks:** `--dir=./` gives the module access to the entire repo including `.env`. Use strict sub-directories.
- **Memory limits:** a malicious module can call `memory.grow` in a loop → host DoS. Use `Store::set_limits(...)`.
- **Network capability:** WASI preview 1 has *no* socket API — but with the `wasi-http` proposal or Extism HTTP host functions you can thread the network through. Caution: this breaks the default isolation.
- **WASM compiler bugs** are rare but possible. For truly critical isolation: add seccomp filters in the host process.

## 🛠️ Practice

**Task:** Write a Rust plugin `calc.wasm` (functions `add`, `mul`), load it from Python with wasmtime, and call the functions with values the LLM agent would supply.

**Step by step:**

1. Prepare Rust:

   ```bash
   rustup target add wasm32-wasip1
   mkdir day43 && cd day43
   ```

2. Write `plugin.rs` with two exported functions — `add` and `mul`:

   > **Hints:**
   > - Each function needs `#[no_mangle]` and `pub extern "C"` so the symbol name survives compilation and is callable from the Python host via wasmtime.
   > - Signature: `(a: i64, b: i64) -> i64` — WASM exports use C ABI integer types.
   > - Return `a + b` for `add` and `a * b` for `mul`; no `std` or imports required.
   > - The Theory section shows the pattern for a single `add` function — extend it with `mul`.
3. Compile:

   ```bash
   rustc --target wasm32-wasip1 plugin.rs -o plugin.wasm
   file plugin.wasm   # → "WebAssembly (wasm) binary module"
   ```

4. Extend host `run.py` (snippet above): load `plugin.wasm`, call `add(3,4)` and `mul(6,7)`, print results.
5. Sandbox test: try to call `std::fs::read_to_string("/etc/passwd")` from the plugin (fails — no WASI, no `--dir`).
6. LLM agent integration: `agent.py` calls the LLM, which returns `"add(3,4)"` as JSON; the host parses it and calls `add` in the WASM module — the LLM *cannot* smuggle in malicious code.

**Definition of Done (DoD):**

- [ ] `python run.py` prints `add(3,4)=7`, `mul(6,7)=42`.
- [ ] `plugin.wasm` is ≤ 20 KB.
- [ ] An attempt to read a file from the plugin fails with a compile error (no `--dir`).
- [ ] The host has a memory limit (`Store` limit set) — test with a module that loops `memory.grow`: abort instead of crash.
- [ ] You can justify in 2 sentences why WASM default-off is safer than subprocess default-on.
- [ ] Commit: `git commit -m "day43: wasm sandbox for llm-generated code"`.

**Extension (optional):** Create a second version with `--dir=./sandbox` and `wasi:filesystem`, in which the plugin may write exactly one file to `./sandbox/output.txt`. Demonstrate that `/etc/passwd` is still denied.
