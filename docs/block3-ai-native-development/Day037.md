**Block:** Block 3: AI-Native Development · Agents & LangGraph

> **Goal of the day:** You orchestrate two specialized agents (e.g. *Researcher* and *Coder*) in a shared graph and use a *Supervisor* agent that decides who goes next.

---

## 📖 Theory

A **multi-agent system** distributes a complex task across several LLM roles, each with its own prompt, tools, and slice of state. Three orchestration patterns dominate in LangGraph:

1. **Supervisor (hub-and-spoke):** a central agent sees the history and chooses the next worker via `conditional_edge`. Keeps full control over streaming.
2. **Hierarchical:** workers may delegate to sub-workers (supervisor-of-supervisors).
3. **Network / Swarm:** agents call each other; communication flows through the shared state. Powerful, but hard to debug.

### Supervisor pattern in code

Each worker is itself a compiled LangGraph (or a simple node). The supervisor decides which worker goes next based on the last message — until `"FINISH"`.

```python
from typing import TypedDict, Annotated, Literal
from operator import add
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    messages: Annotated[list, add]
    next: str

def supervisor(state) -> dict:
    last = state["messages"][-1]
    # real LLM: routing call; here a simple heuristic
    if "code" in last.lower():
        nxt = "coder"
    elif "fact" in last.lower():
        nxt = "researcher"
    else:
        nxt = "FINISH"
    return {"next": nxt}

def researcher(state) -> dict:
    return {"messages": ["fact: io_uring is a Linux async I/O API"]}

def coder(state) -> dict:
    return {"messages": ["code: int fd = io_uring_setup(...)"]}

g = StateGraph(State)
g.add_node("supervisor", supervisor)
g.add_node("researcher", researcher)
g.add_node("coder",     coder)
g.add_edge(START, "supervisor")
g.add_conditional_edges("supervisor",
    lambda s: s["next"],
    {"researcher": "researcher", "coder": "coder", "FINISH": END})
for w in ("researcher", "coder"):
    g.add_edge(w, "supervisor")      # workers return to the supervisor
app = g.compile()
```

### Channel-based state isolation

When workers need their own sub-states (e.g. private notes), use multiple states via `StateGraph(StateSchema)` with subgraphs. Otherwise all workers share the same `messages` channel — simple, but workers can confuse each other when they overwrite the same keys.

### Why this matters

Real dev agents are *not* monoliths: a PR-comment agent needs (a) a code reader, (b) a linter, (c) a rewriter, (d) a reviewer. A supervisor pattern lets you test, prompt, and replace each one separately — and it is exactly the foundation of the block capstone (Day 55).

### Pitfalls

- **Infinite cycle:** without a `"FINISH"` condition and without an iteration limit the supervisor bounces between workers forever. Always keep a `max_iterations` counter in state.
- **Token explosion:** every worker sees the full `messages` history. For long runs, summarize the state (e.g. "last 6 messages + summary"), otherwise the context window overflows.
- **Tool collision:** two workers registering the same tool name confuse routing. Name tools uniquely (`research_search` vs `code_run`).
- **Subgraph deadlock:** a worker graph using `interrupt_before` must have the interrupt threaded through by the supervisor graph as well.

## 🛠️ Practice

**Task:** Build a supervisor graph with two workers (*Researcher*, *Coder*) that analyzes a user request, delegates to a worker 0–2 times, then outputs `"FINISH"`.

**Step by step:**

1. Copy the Day 36 project: `cp -r day36 day37 && cd day37`.
2. New file `multi.py` with the supervisor pattern above.
3. Add an iteration limit: derive a counter from `state["messages"]` in `supervisor` and force `"FINISH"` at `>= 6`.
4. Replace the heuristic supervisor with real LLM routing — have the
   supervisor call an LLM to decide whether to route to `coder`,
   `researcher`, or `FINISH` based on the conversation so far:

   > **Hints:**
   > - Instantiate `ChatAnthropic` (or `ChatOpenAI`) and call `llm.invoke(...).content` inside `supervisor`.
   > - Craft a routing prompt that asks the model to return exactly one of `coder`, `researcher`, or `finish`.
   > - `.strip().lower()` the model's response and validate it against the allowed set — fall back to `"FINISH"` on anything unexpected.
   > - Map the string `"finish"` to `"FINISH"` in the returned `next` field so the conditional edge resolves to `END`.
5. Run it:

   ```bash
   python -c "from multi import app; print(app.invoke({'messages':['Write a sorting function','Explain qsort'],'next':''}))"
   ```

6. Inspect the trace output: the supervisor should route to `coder` once, then `researcher`, then `FINISH`.

**Definition of Done (DoD):**

- [ ] `python multi.py` terminates (iteration limit kicks in).
- [ ] `app.get_graph().draw_mermaid()` shows `supervisor --> researcher/coder --> supervisor` plus `supervisor --> END`.
- [ ] On the request "write code" the supervisor routes to `coder` at least once.
- [ ] When `max_iterations` is reached, `FINISH` is guaranteed (no deadlock).
- [ ] Commit: `git commit -m "day37: supervisor multi-agent orchestration"`.

**Extension (optional):** Turn *Researcher* into a sub-graph (its own state with tools) instead of a simple node — then the system is truly hierarchical.
