## 📖 Theory

"A model feels better" is not a metric. Three families of evaluation metrics for generative models:

### 1. Reference-based (classic)

Compare output to a reference answer (gold).

| Metric | Measures | Suited for |
|---|---|---|
| **BLEU** | n-gram precision (1–4) | translation, code generation against a reference |
| **ROUGE-L** | longest common subsequence | summaries, free generation |
| **METEOR** | precision + recall + stemming | translation |
| **Exact Match** | string equality | QA with short answers (e.g. "yes/no") |
| **F1 (Token)** | token-overlap P/R | extraction tasks |

```python
from sacrebleu import corpus_bleu
from rouge_score import rouge_scorer

bleu = corpus_bleu(predictions, [references]).score
scorer = rouge_scorer.RougeScorer(["rougeL"], use_stemmer=True)
rouge_l = scorer.score(ref, pred)["rougeL"].fmeasure
```

### 2. LLM-as-Judge

A strong model evaluates output against criteria. Honestly: *also deceivable*, but scales better than human grading.

```python
judge_prompt = """Rate the following answer on a scale 1–5.
Criteria: correctness, clarity, completeness.
Question: {question}
Gold: {gold}
Answer: {pred}
Answer as JSON: {{"score": int, "reason": str}}
"""
# call via Claude/GPT, parse JSON
```

Pitfall: *position bias* — judges prefer the first answer; *length bias* — longer answers score higher. Address both with randomization + length control.

### 3. Functional / task-specific

For code: does it compile? Do tests pass? Is linting ok? — *deterministic*, no LLM needed.

```python
import subprocess
def code_metric(pred):
    with open("tmp.py","w") as f: f.write(pred)
    r = subprocess.run(["python","tmp.py"], capture_output=True, timeout=10)
    return {"runs": r.returncode == 0, "stdout_match": "42" in r.stdout.decode()}
```

### Important distinction: eval on holdout vs. train

- **Train-set eval** → pointless, measures overfit.
- **Holdout (val)** → measures generalization within the domain.
- **Out-of-domain (OOD)** → whether the model "forgets". Important against catastrophic forgetting (Day 46).

### Why this matters

Day 46 reported loss — but loss is only a proxy. The real question is: "Does the model answer Rust questions better than the base?" Only a systematic eval answers that. For the capstone (Day 55) it is mandatory to have an evaluation set that runs on every commit.

### Pitfalls

- **BLEU is not invariant to synonyms** — a semantically correct answer with different wording scores low. Unsuitable for free generation.
- **ROUGE rewards length** — longer answer = more n-grams = higher score. Normalize by length or use a metric ensemble.
- **LLM judge inconsistency:** same input, second run → different score. At least 3 runs and average; or deterministic temperature 0.
- **Test set publication:** dataset in Git → model can memorize it (if pre-training saw it). Keep eval data secret.
- **Code tests too strict:** a missing `;` breaks everything. Track "compiles" vs. "all tests green" separately.

## 🛠️ Practice

**Task:** Build an eval set (≥ 30 examples with gold answers), evaluate the base model vs. the LoRA fine-tuned model (Day 46) with BLEU, ROUGE-L, and LLM-as-Judge, and compare.

**Step by step:**

1. Take the eval set from the Day 47 val split, or curate 30 gold pairs by hand (`eval.jsonl`).
2. Setup:

   ```bash
   pip install sacrebleu rouge-score jinja2
   ```

3. Inference for both models over the eval set:

   > **Hints:**
   > - Load the base model with `AutoModelForCausalLM.from_pretrained` and the fine-tuned one by wrapping it in `peft.PeftModel.from_pretrained(base, "./lora_adapter")`.
   > - Reuse the tokenizer from Day 46; generate predictions for every eval example into `base_preds[]` and `ft_preds[]` lists.
   > - Keep generation deterministic (`do_sample=False`, a fixed seed) so the metric comparison is fair.
4. Compute metrics:

   > **Hints:**
   > - Use `sacrebleu.corpus_bleu(preds, [golds]).score` for BLEU and `rouge_score.rouge_scorer.RougeScorer(["rougeL"])` for ROUGE-L (take the `.fmeasure`).
   > - Write one `metrics(preds, golds)` helper returning `{"bleu", "rouge_l"}` (mean of per-example ROUGE-L F1) and call it once for `base_preds` and once for `ft_preds`.
   > - Print both dicts so the DoD ("prints two metric dicts") is satisfied.
5. LLM-as-Judge: for 10 random examples via Claude; collect `score` + `reason`, average.
6. Functional code test (for code tasks): `python eval_code.py` compiles each prediction.

**Definition of Done (DoD):**

- [ ] `eval.jsonl` with ≥ 30 `{instruction, gold}` examples exists.
- [ ] `python eval.py` prints two metric dicts: `base` and `ft`, with `bleu` and `rouge_l` as numbers.
- [ ] LLM judge produces `{score, reason}` as JSON for ≥ 10 examples.
- [ ] You answer in writing: "In which examples does ft beat base, in which not? Hypothesis?"
- [ ] Out-of-domain eval: 5 examples outside the training domain (e.g. cooking recipes) — ft should not be significantly worse than base (no forgetting).
- [ ] Commit: `git commit -m "day48: eval metrics bleu rouge llm-judge base vs ft"`.

**Extension (optional):** Statistical significance: bootstrap resampling (1000×) of the score difference → 95% confidence interval. Is the "ft > base" effect real or chance?
