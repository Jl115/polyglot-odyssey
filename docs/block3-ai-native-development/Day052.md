# Day 52: Monitoring & Drift Detection

**Block:** Block 3: AI-Native Development · MLOps

> **Goal of the day:** You instrument a running model with metrics (latency, errors, token cost) and data-drift detection — and alarm automatically when the input distribution or model quality deviates significantly.

---

## 📖 Theory

Deployment is not the end; it is the beginning of the *real* ML problem. Models *degrade* in production: the input distribution shifts ("drift"), users ask different things, the world changes. Without monitoring you notice only when users complain.

### Three kinds of drift

1. **Covariate drift (input)** — feature distribution changes; `P(X)` differs, `P(Y|X)` stays the same. E.g. suddenly many JavaScript questions instead of Rust.
2. **Concept drift (label)** — `P(Y|X)` changes. E.g. "Rust idioms 2024" differ from 2026.
3. **Prediction drift (output)** — the model output distribution drifts; can follow cause 1 or 2.

### Metric pillars

| Metric | Source | Alert when |
|---|---|---|
| `request_latency_ms` p95 | server metric | rise > 2× over 24h |
| `error_rate` | server logs | > 1% |
| `token_cost_usd` per request | LLM API | rise > 50% |
| `output_length_tokens` mean | server | drift ±30% |
| `input_length_tokens` mean | server | drift ±30% |
| `eval_score` (cached) | sampled eval | < threshold |
| `psi` (Population Stability Index) | input features | > 0.2 (drift) |
| `ks_statistic` (Kolmogorov-Smirnov) | input vs. baseline | p < 0.01 |

### PSI (Population Stability Index)

```python
import numpy as np

def psi(expected, actual, bins=10):
    # compare bucket distributions
    breakpoints = np.percentile(expected, np.linspace(0,100,bins+1))
    exp_pct = np.histogram(expected, breakpoints)[0] / len(expected)
    act_pct = np.histogram(actual, breakpoints)[0] / len(actual)
    # 0.001 epsilon against log(0)
    exp_pct = np.clip(exp_pct, 0.0001, None)
    act_pct = np.clip(act_pct, 0.0001, None)
    return np.sum((act_pct - exp_pct) * np.log(act_pct / exp_pct))

# PSI > 0.2 → significant drift
```


### Architecture: metrics → store → alerting

```
vLLM server ──/metrics (Prometheus)──▶ Prometheus ──▶ Grafana

       └── sample outputs ─────────────► drift job (CronJob)
                                                │
                                          alert → Slack/PagerDuty
```

### Why this matters

The capstone (Day 55) deploys an AI dev tool. Without monitoring it becomes "bad" after 2 weeks and nobody knows why. Data drift is especially relevant for LLM-based tools: the underlying LLM behavior can change (a model-version bump in the vLLM image), user questions change (e.g. a new language). Drift detection is *not optional* in production.

### Pitfalls

- **Alert fatigue:** overly sensitive PSI thresholds fire constantly. Start with `psi > 0.2` as default, then calibrate per metric.
- **Baseline staleness:** when the "reference" data is old, every legitimate new question alarms as drift. Update the baseline quarterly.
- **Sample bias:** logging only failed requests → drift metrics show only problems. Log a random 1% sample of all requests.
- **PII in metrics:** `input_length_tokens` is fine, but `input_text` samples must be masked. Differential-privacy aggregation.
- **LLM cost alerting too late:** when the alert fires on daily cost, the damage is done. Set a per-request cost cap in the server.

## 🛠️ Practice

**Task:** Extend your vLLM server (Day 42 or 45) with Prometheus metrics and a CronJob that checks drift daily against a stored baseline and alarms when `psi > 0.2`.

**Step by step:**

1. Setup:

   ```bash
   pip install prometheus-client evidently pandas
   ```

2. Server instrumentation:

   > **Hints:**
   > - Expose a metrics endpoint with `prometheus_client.start_http_server(9100)` and register a `Counter` (`llm_requests_total`) plus two `Histogram`s: `llm_latency_seconds` and `llm_output_tokens` (pick sensible `buckets`).
   > - In your `/ask` handler, call `.inc()` on the counter and `.observe(elapsed)` / `.observe(tokens_out)` on the histograms per request.
   > - `curl localhost:9100/metrics` must then show all three metric families (matches the DoD).
3. Prometheus + Grafana locally:

   ```bash
   docker run -d -p 9090:9090 -v ./prometheus.yml:/etc/prometheus/prometheus.yml prom/prometheus
   docker run -d -p 3000:3000 grafana/grafana
   # Grafana → data source localhost:9090 → dashboard "LLM"
   ```

4. Collect baseline data: 100 requests via a script, save as `baseline.jsonl` (input_len, output_len, latency).
5. Drift CronJob (Python, daily):

   > **Hints:**
   > - In `drift_check.py` load `baseline.jsonl` and `today.jsonl` into pandas DataFrames.
   > - Build an Evidently `Report(metrics=[DataDriftPreset()])`, run it with `r.run(reference_data=base, current_data=today)` and `r.save_html("drift.html")`.
   > - Fire a Slack webhook alert when the per-feature PSI exceeds 0.2; ensure the report contains only aggregated lengths, no raw input text (PII filter per DoD).
6. Simulate drift: change the eval domain from "Rust" to "JavaScript" for 50 requests → the drift report must flag it.

**Definition of Done (DoD):**

- [ ] `curl localhost:9100/metrics` shows `llm_requests_total`, `llm_latency_seconds_*`, `llm_output_tokens_*`.
- [ ] The Grafana dashboard shows live latency over the last 5 min.
- [ ] `drift_check.py` produces `drift.html` with visible PSI values per feature.
- [ ] On simulated drift (JS instead of Rust) the report shows a `DATA DRIFT` flag and the Slack webhook fires.
- [ ] PII filter active: `drift.html` contains no raw input texts, only aggregated lengths.
- [ ] Commit: `git commit -m "day52: prometheus metrics + evidently drift detection"`.

**Extension (optional):** Eval-on-sample: pair 1% of all production requests with a gold answer (LLM judge) and plot the quality trend in Grafana — drift in *quality* becomes visible, not just input.
