# Day 51: CI/CD for ML

**Block:** Block 3: AI-Native Development · MLOps

> **Goal of the day:** You automate the ML pipeline (Day 50) in GitHub Actions: on a commit to `data/` or code → the pipeline runs in CI → the quantized model is uploaded as a release artifact — with caching, matrix builds, and honesty about GPU availability.

---

## 📖 Theory

CI/CD for ML differs from classic software CI through: larger artifacts (GB model weights), long runtimes (training 10 min–hours), hardware dependence (GPU), and *data* as a trigger. Three patterns:

1. **Software-style CI** — tests, lint, build → fast, CPU-only, on every PR. ~5 min.
2. **ML-pipeline CI** — train + eval + quant → slow, possibly GPU; only on `data/` or model-pin changes, never on every PR.
3. **Deploy CD** — successfully evaluated model → registry → K8s rollout via GitOps (Day 44).

### GitHub Actions scaffold

```yaml
# .github/workflows/ml-pipeline.yml
name: ML Pipeline
on:
  push:
    paths: [data/**, models/**, curate.py, train.py, eval.py, quant.py]
  workflow_dispatch:

jobs:
  pipeline:
    runs-on: ubuntu-latest    # CPU runner; GPU only via self-hosted or cloud
    timeout-minutes: 60
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with: {python-version: "3.12", cache: "pip"}
    - run: pip install -r requirements.txt
    - uses: actions/cache@v4
      with:
        path: |
          ~/.cache/huggingface
          lora_adapter/
        key: ml-${{ runner.os }}-${{ hashFiles('data/**', 'requirements.txt') }}
    - run: make pipeline
    - uses: actions/upload-artifact@v4
      with: {name: q4km-model, path: q4km.gguf, retention-days: 30}
    - uses: actions/upload-artifact@v4
      with: {name: metrics, path: metrics.json}
```

### Triggers & caching

- `paths:` filter prevents a 30-min pipeline from running on every README change.
- `cache:` with `key: hashFiles('data/**')` invalidates the cache only on data changes → massive speedups.
- `workflow_dispatch` for manual triggers (e.g. re-training despite unchanged data).

### GPU reality (honest)

GitHub-hosted runners are CPU-only. Three paths for GPU workloads:

1. **Self-hosted runner with your own GPU** — setup effort, but no recurring cloud cost.
2. **Cloud GPU job (Modal, Replicate, Lambda Labs)** — `modal run train.py` via a Modal action; ~$0.50–2/run.
3. **Colab-Pro action** — hacky, but works: trigger a notebook API via a `gcolab` wrapper.

### Multi-job pipeline with gates

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps: [- run: pytest tests/]
  pipeline:
    needs: test                    # only if tests pass
    runs-on: ubuntu-latest
    steps: [- run: make pipeline]
  release:
    needs: pipeline
    if: github.ref == 'refs/heads/main' && success()
    steps:
    - uses: softprops/action-gh-release@v2
      with: {files: q4km.gguf}
```

### Why this matters

In the capstone (Day 55) a pipeline must run on every PR commit to the `ai-infra` repo that rebuilds the model and — if metrics beat a threshold — deploys. Without CI/CD that's a manual bottleneck; with CI/CD the dev loop is 10× faster and *reproducible*.

### Pitfalls

- **Cache pollution:** `actions/cache` key too coarse → an old model gets reused despite train-code changes. Always include `hashFiles` of code *and* data in the `key`.
- **Artifact size limit** (10 GB per artifact on GH free) — a GGUF can approach that. Push large models via HF Hub directly from the pipeline, not via GH artifacts.
- **Secret leaks in logs:** `ANTHROPIC_API_KEY` always via `secrets.`, never echoed in `run:`; `::add-mask::` for dynamic values.
- **Workflow takes too long:** without caching the pipeline can take 30 min–hours → free tier limit (2000 min/month). Cache strictly, re-trigger only as needed.
- **GPU black market:** self-hosted GPU runners need maintenance; on crash no auto-recovery. Monitoring (Day 52) is *mandatory*, not optional.

## 🛠️ Practice

**Task:** Build a GitHub Actions workflow that runs the Day 50 pipeline on `data/` changes, uploads the quantized model as a release artifact, and posts metrics as a JSON PR comment.

**Step by step:**

1. Repo on GitHub with the Day 50 code; update `requirements.txt`.
2. Create `.github/workflows/ml-pipeline.yml` (above).
3. Cache verification: on unchanged data, `make pipeline` should take < 5 min instead of 20 min (cache hit).
4. PR test: change only `README.md` → pipeline must *not* trigger (check the `paths:` filter).
5. Change data: commit a new `raw.jsonl` → pipeline triggers, runs, leaves artifact `q4km-model`.
6. Release job: on push to `main` a GH release with `q4km.gguf` is created.
7. Metrics comment: the action posts `metrics.json` as a PR comment:

   > **Hints:**
   > - Use the `actions/github-script@v7` action with an inline `script` that reads `metrics.json` (`fs.readFileSync` + `JSON.parse`) and calls `github.rest.issues.createComment(...)`.
   > - Pull the PR number from `context.payload.pull_request.number` and owner/repo from `context.repo`; gate this step on `pull_request` events.
   > - Format the comment body as a fenced `json` block under a `## ML Metrics` heading so the metrics render nicely.

**Definition of Done (DoD):**

- [ ] On a `data/raw.jsonl` commit the workflow runs; on a `README.md` commit it does not.
- [ ] `make pipeline` runs in CI and leaves `q4km.gguf` + `metrics.json` as artifacts.
- [ ] Cache hit: a second workflow run on unchanged data is ≥ 3× faster than the first.
- [ ] On push to `main` a GH release with `q4km.gguf` is created.
- [ ] A PR comment shows `metrics.json` formatted.
- [ ] You comment in the workflow YAML *which* hardware (CPU/GPU) is used and why.
- [ ] Commit: `git commit -m "day51: github actions ml pipeline with caching"`.

**Extension (optional):** GPU path via Modal: `modal run train.py` in a separate job (`runs-on: ubuntu-latest`, calls Modal cloud GPU). Compare training time and cost.
