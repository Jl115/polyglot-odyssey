## 📖 Theory

### Architecture: polyglot pool

```
┌─────────────────────────────┐
│  Zig implementation (Pool)  │   export fn pool_alloc/free/reset with C ABI
└──────────────┬──────────────┘
               │ C ABI (shared library)
       ┌───────┴────────┐
       ▼                ▼
┌──────────────┐  ┌──────────────┐
│  C test &    │  │  Rust test    │  via extern "C" (extension)
│  benchmark   │  │               │
└──────────────┘  └──────────────┘
```

### API design (C-ABI-compatible)

```c
/* pool.h — the only header file needed for C/Rust */
typedef struct Pool Pool;                       // opaque handle
Pool *pool_create(size_t capacity);             // allocates pool (incl. backing buffer)
void   pool_destroy(Pool *p);
void  *pool_alloc(Pool *p, size_t size, size_t align);   // bump-style alloc
void   pool_reset(Pool *p);                     // offset = 0, reuse
size_t pool_used(Pool *p);
```

**Design decisions:**

- **Opaque handle** (`Pool *`) — C does not know the layout, must access through functions. Stable against ABI breaks.
- **Bump strategy** — fastest pattern, `reset()` for phase lifetime. Single-block `free` is a noop (document this!).
- **`align` as a parameter** — the C caller must supply alignment, because Zig `@typeInfo` is only internal.
- **Fixed capacity** — no auto-grow (capstone simplification; production needs resize).

### Why Zig for the implementation?

- `std.mem.Allocator` is first-class → the pool is a trivial BumpAllocator (Day 30).
- `export fn` makes C ABI trivial (Day 28/31).
- The `build.zig` build system compiles the C test and the library in one command (Day 28).

### Benchmark plan

Compare 4 scenarios at N = 100 000 allocations of size `64`:

1. C `malloc/free` (free per allocation)
2. Zig `gpa.alloc/free` (free per allocation)
3. Custom pool `pool_alloc` + a single `pool_reset` (bulk)
4. Custom pool with `@setRuntimeSafety(false)`

Expected order: (4) ≪ (3) < (2) < (1).

### Why this matters

This is the synthesis of the whole block: pointer understanding (Day 21/22), smart-pointer alternative (Day 23), allocator first-class (Day 27/30), bidirectional FFI (Day 31), language choice (Day 32). Anyone who passes this capstone has proven they can build polyglot memory systems — the block outcome "Polyglot Memory-Pool + Benchmarks".

### Pitfalls

- **`pool_alloc` after `pool_reset`** returns a pointer into valid memory — but old pointers became invalid on reset (semantic documentation is important).
- **Forgetting alignment in the C call** → UB in typed usage. Offer a helper macro `POOL_ALIGNOF(T)` or a default alignment of `8`.
- **Thread safety:** this pool is *not* thread-safe; add a mutex in production or use a per-thread pool.
- **`free` is a noop** — a caller expecting per-block free leaks (semantically). Header comment + DoD check.
- **`pool_destroy` vs `pool_reset`:** destroy frees the pool struct + backing buffer; reset only the offset. Do not confuse them.

## 🛠️ Practice

**Task:** Implement the pool in Zig, call it from C, measure the speedup vs. `malloc`.

**Step by step:**

1. `day34/build.zig`:

   > **Hints:**
   > - Static library `pool` from `src/pool.zig` with `linkLibC()`.
   > - Executable `bench` from `src/bench.c` via `addCSourceFile`; link the pool library + libc.
   > - A `run` step depending on `addRunArtifact(exe)`.

2. `day34/src/pool.zig`:

   > **Hints:**
   > - `pub const Pool = extern struct { backing: [*]u8, capacity: usize, offset: usize }`.
   > - `pool_create`: use `std.heap.c_allocator` to allocate the backing buffer and a `Pool` struct, return the pointer (null on failure).
   > - `pool_alloc`: `std.mem.alignForward` the offset, check bounds, advance offset, return `@ptrCast(&pool.backing[fwd])` (null on overflow).
   > - `pool_reset` zeroes the offset; `pool_destroy` frees the backing buffer and the Pool struct via the c_allocator; `pool_used` returns `pool.offset`.

3. `day34/src/bench.c`:

   > **Hints:**
   > - `extern`-declare all `pool_*` functions; `typedef struct Pool Pool;` (opaque handle).
   > - A `now_s()` helper using `clock_gettime(CLOCK_MONOTONIC)`.
   > - Time N=100000 `malloc(64)/free` loops, then time `pool_alloc` + a single `pool_reset`; print both times and the speedup ratio.

4. Build & run: `cd day34 && zig build run`.
5. ASan test: build the library with `-fsanitize=address` (via `lib.linkSystemLibrary("asan")` or externally) and test the C side clean.
6. Variation: build with `-Doptimize=ReleaseFast` → speedup should be maximized.

**Definition of Done (DoD):**

- [ ] `zig build run` compiles and runs; the benchmark prints `malloc/free`, `pool+reset`, `speedup`.
- [ ] Speedup ≥ 5× (pool clearly faster than malloc/free over 100k allocations).
- [ ] `pool_alloc` exceeding capacity → returns `NULL` (checked on the C side), no UB.
- [ ] ASan on the C side: 0 leaks, 0 errors (`pool_destroy` frees everything).
- [ ] `pool.h` with the opaque-handle pattern and comments on the `free`-noop semantics.
- [ ] You can explain: why is bump + reset faster than malloc/free? (No freelist search, no syscalls.)
- [ ] Commit: `git commit -m "day34: polyglot memory pool (zig impl, c bench)"`.

**Extension (optional, +1h):** Call the pool from Rust via `extern "C"`:

   > **Hints:**
   > - `#[repr(C)] struct Pool { _private: [u8; 0] }` opaque handle; an `extern "C"` block declaring `pool_create/destroy/alloc/reset`.
   > - In an `unsafe` block, create a 1 MiB pool, alloc 1000× 64 bytes, `pool_reset`, `pool_destroy`.
   > - Link the Zig `pool.a` via a `build.rs`.

Link the Zig library (`pool.a`) via `build.rs` and prove Rust → Zig pool FFI works.
