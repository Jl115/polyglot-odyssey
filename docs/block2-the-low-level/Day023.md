## 📖 Theory

C++ sits between C and Rust: it offers manual control (raw pointers), but automates release via **RAII** (Resource Acquisition Is Initialization). RAII = every object has a destructor that runs at end of scope. Smart pointers are RAII wrappers for heap memory.

### The smart-pointer family

| Pointer | Ownership | Cost | Rust equivalent |
| --- | --- | --- | --- |
| `unique_ptr<T>` | exclusive (move-only) | 0 overhead | `Box<T>` |
| `shared_ptr<T>` | shared, refcount | atomic inc/dec | `Arc<T>` (not `Rc` — not thread-safe) |
| `weak_ptr<T>` | non-owning observer | breaks cycles | `Weak<T>` |
| `T*` raw | no ownership, only observation | 0 | `&T` / `unsafe` |

```cpp
#include <memory>
std::unique_ptr<int> a = std::make_unique<int>(42);
// std::unique_ptr<int> b = a;            // ❌ copy deleted — move-only
std::unique_ptr<int> b = std::move(a);    // ✅ move: a is nullptr afterwards
```

### RAII: destructor instead of explicit `free`

In C (Day 22) you had to call `list_free` manually. With `unique_ptr` the destructor takes over:

```cpp
struct Node {
    int value;
    std::unique_ptr<Node> next;   // ownership: recursive destructor
};
// As soon as head leaves scope, →next →next... is freed automatically.
```

**Watch out for recursion:** a deep list → stack overflow in the destructor. Fix: iterative `clear()` or `std::vector<Node>`.

### Move semantics instead of copy

Rust knowledge transfers: move transfers ownership; the old owner is `nullptr`. `std::move(x)` is only a cast to `T&&` — it *does* nothing, it only enables move ctor/move assign.

```cpp
std::vector<int> v = {1,2,3};
std::vector<int> w = std::move(v);   // v is empty afterwards (valid but empty)
```

### Why this matters

C++11 smart pointers are the standard path to C++ memory safety without GC. Block 2 compares languages: here you see how much manual discipline C++ *still* needs despite RAII (refcount overhead, cycles, dangling `weak_ptr::lock`) — and why Rust takes the next step by making ownership a compile-time type.

### Pitfalls

- **Cycles in `shared_ptr`:** A→B and B→A → refcount never 0 → leak. Fix: `weak_ptr` for one edge.
- **`shared_ptr` is not free:** atomic refcount inc/dec on every copy, cache-line bouncing in multithreading.
- **Prefer `make_unique`/`make_shared`:** avoids separate allocation of control block + object; also exception-safe in function calls `f(unique_ptr<X>(new X), g())` — evaluation order is unspecified, can leak.
- **Raw pointers as non-owning views** are OK — but never `delete` a raw pointer when a smart owner exists.
- **`unique_ptr<T[]>`** for arrays — `unique_ptr<T>` calls `delete`, not `delete[]`.

## 🛠️ Practice

**Task:** Implement an `IntList` with `std::unique_ptr<Node>` as the next pointer, `push`/`print` and RAII destruction. Demonstrate that a leak is impossible — even on throw.

**Step by step:**

1. `day23/list.cpp`:

   > **Hints:**
   > - `struct Node` holds `int value` and `std::unique_ptr<Node> next` — the chain frees itself via the destructor.
   > - `IntList` keeps a `std::unique_ptr<Node> head_`; `push` makes a new node via `std::make_unique`, moves the old head into `n->next`, then reassigns `head_`.
   > - `print`: walk with a raw non-owning `Node *c = head_.get()` — never `delete` it.
   > - No `free`/`delete` anywhere: the destructor chain cleans up automatically — demonstrate by letting an `IntList` leave scope in `main`.

2. Build: `g++ -std=c++17 -Wall -Wextra -O2 -o day23 day23/list.cpp`.
3. Sanitize: `g++ -std=c++17 -fsanitize=address,undefined -g -o day23_asan day23/list.cpp && ./day23_asan`.
4. Leak check: `valgrind --leak-check=full ./day23` — should report "0 bytes in 0 blocks".
5. Provoke a cycle test with `shared_ptr` (separately): build two `shared_ptr<Node>` that point to each other → `valgrind` must report a leak, then fix it with `weak_ptr`.

**Definition of Done (DoD):**

- [ ] `g++ -std=c++17 -Wall -Wextra` compiles without warnings.
- [ ] No `new`/`delete` in the code (only `make_unique`).
- [ ] `./day23_asan` exit 0, **0 leaks**.
- [ ] `valgrind --leak-check=full ./day23` reports **0 errors, 0 leaks**.
- [ ] You can explain why `unique_ptr` is move-only (copy ctor `= delete`) and why that corresponds to Rust's `Box`.
- [ ] Commit: `git commit -m "day23: unique_ptr list with RAII (asan/valgrind clean)"`.

**Extension (optional):** Build a shared tree with `shared_ptr<Node>` + `weak_ptr` as parent pointer that avoids cycles. Demonstrate `weak_ptr::lock()` returning a valid `shared_ptr` or `nullptr`.
