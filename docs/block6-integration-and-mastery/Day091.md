# Day 91: Capstone Planning

**Block:** Block 6: Integration & Mastery · Capstone

> **Goal of the day:** You have a written, reviewed one-pager for a realistic capstone project that integrates skills from **all five previous blocks** — including MVP scope, a risk list, and a 4-day milestone plan for days 92–94.

---

## 📖 Theory

The capstone is the proof that the 90 previous days were not isolated exercises, but building blocks of *one* system. A good capstone project is **small enough to ship in 4 days**, and **broad enough to touch every discipline at least once**.

### Concept 1: The capstone constant — "Polyglot PQC Edge Agent CLI"

To make planning deterministic, we define a concrete reference project that touches all five blocks. You may adopt it 1:1 or adapt it — but only if you can justify which block skills you substitute and how.

| Block | Skill in the capstone | Concrete manifestation |
|---|---|---|
| 1 Memory-Safe | Rust ownership, error handling, CLI | `pqc-agent` binary in Rust, `clap` CLI, `anyhow` errors |
| 2 Low Level | Zig/C FFI, allocator awareness | Optional Zig build step for a hot loop (tokenizer) via FFI |
| 3 AI-Native | Agent + RAG | LLM call (local via `llama.cpp` FFI or API), minimal tool-use loop |
| 4 Security & PQC | PQC KEM, signature, SBOM | ML-KEM-768 key-wrap for local secrets store, Ed25519 signature of config, `cyclonedx` SBOM |
| 5 Edge & Future | Edge targets, polyglot build | Cross-compile to `aarch64-unknown-linux-gnu`, bench vs host |

**Product vision in one sentence:** A CLI that drives a local LLM agent with tool use and stores its secrets (API keys, agent state) encrypted on disk with ML-KEM-768, signs them, and makes them provable via SBOM — deployable on edge hardware.

### Concept 2: Scope mechanics — MVP vs "full run"

Scope creep is the #1 cause of death for capstones. Define three concentric rings:

- **MVP (must be shippable by day 94):** CLI starts, loads encrypted secrets store, runs an agent loop with one tool (e.g. "read file"), writes result. PQC wrap + signature + SBOM.
- **V1.1 (stretch, if time remains):** Second tool, RAG over a local document.
- **V2.0 (explicitly out of scope):** Multi-agent orchestration, vLLM serving, RISC-V bare metal — documented as "Future Work" in the README, **not** implemented.

The discipline of taking V2.0 *out of scope in writing* is more important than any line of code.

### Concept 3: Risk-first planning

Before you set milestones, list the top-5 risks and one *mitigation* per risk that is actionable within the 4 days. Examples:

1. **Risk:** PQC library does not compile on the edge target. **Mitigation:** Day 92 first task = cross-compile smoke test of the `pqcrypto` crates; fallback: host binary without cross-compile, edge as documentation.
2. **Risk:** LLM call needs API key / network. **Mitigation:** Offline mode with mock LLM (deterministic response) as default; real API call behind a feature flag.

### Why this matters

Engineers don't fail capstones on the code, they fail on scope. The ability to reduce an ambitious system to a *shippable* MVP and name risks *before* coding is exactly the ability that separates senior roles from junior roles. This planning is the transferable core skill — not the concrete product.

### Pitfalls

- "I'll just start and plan as I go" → guaranteed scope creep. One-pager *before* code, otherwise no commit on day 92.
- "Just quickly add" a V2.0 feature — never. Write it into the README under *Future Work*, that is the legitimate place.
- Capstone chosen too small (e.g. only a toy CLI without security relevance) → misses the integration proof. At least 3 of the 5 blocks must be visible *in the code*.

## 🛠️ Practice

**Task:** Write `docs/capstone/ONEPAGER.md` with the following required sections, commit it as `day91: capstone one-pager`.

**Step by step:**

1. Create the directory: `mkdir -p docs/capstone`.
2. Write `docs/capstone/ONEPAGER.md` — fill in every section, no blanks:

   > **Hints:**
   > - Required sections: **Problem** (2–3 sentences), **Solution** (2–3 sentences, no marketing), **Tech Stack** (table: component → language/lib → block reference), **MVP Scope** (checkbox bullets, shippable by day 94), **Explicitly out of scope** (V2.0 → Future Work), **Top-5 risks + mitigation**, **Milestones** (days 92/93/94), **Success criteria** (quantified).
   > - The Tech Stack table must map each component to the block it proves (≥ 3 of the 5 blocks visible in the *code*, not just the README).
   > - MVP scope ≤ 8 concrete bullets; every risk needs a mitigation actionable within days 92–94.
   > - Success criteria must be quantified (e.g. "cross-compiles to aarch64-linux", "secrets store is ML-KEM-wrapped", "`cargo test` green") — not "be good".

3. Validate the one-pager against the checklist:
   - [ ] MVP has ≤ 8 concrete bullets.
   - [ ] ≥ 3 of the 5 blocks are visible *in the code* (in the README is not enough).
   - [ ] V2.0 out-scope is *in writing*.
   - [ ] Every risk has a mitigation that is actionable within days 92–94.
4. Optional: peer review with `git show main:docs/capstone/ONEPAGER.md` and read it aloud — if a section does not become clear within 30 seconds, it is too vague.

**Definition of Done (DoD):**

- [ ] `docs/capstone/ONEPAGER.md` exists, is committed (`git ls-files docs/capstone/ONEPAGER.md` not empty).
- [ ] All required sections are filled in, no TODO placeholders.
- [ ] ≥ 3 block skills are visible *in the MVP code* (marked with block reference in the table).
- [ ] Top-5 risks each contain a mitigation.
- [ ] Milestones reference days 92/93/94 explicitly.
- [ ] Success criteria are quantified (numbers/tests, not "be good").
- [ ] Commit: `git commit -m "day91: capstone one-pager"`.

**Extension (optional):** Additionally write a `docs/capstone/ARCHITECTURE.md` with an ASCII block diagram (CLI → secrets store → PQC → agent loop → tool → result). This forces you to think through data flow and error paths before coding.
