# Day 95: Open Source Strategy

**Block:** Block 6: Integration & Mastery · Open Source

> **Goal of the day:** Your capstone has a chosen license, a CONTRIBUTING.md, a governance statement (Solo / BDFL / Meritocracy), and a documented threat-model appendix. You understand the legal differences between MIT, Apache-2.0, GPLv3, and AGPLv3 — and can justify why you chose a particular one.

---

## 📖 Theory

Open source is not a license file, it is a **governance system**. A license without governance is an invitation to fork chaos. This day makes the strategy decisions explicit that remain implicit in 90% of "open source" projects and then fail.

### Concept 1: The license spectrum and its tradeoff

| License | Allows commercial use | Copyleft (share-alike obligation) | Patent clause | Typical use |
|---|---|---|---|---|
| **MIT** | yes | no | no | maximum adoption, minimal control |
| **Apache-2.0** | yes | no | yes (PATENTS) | corporate-friendly, with patent protection |
| **GPLv3** | yes | yes (strong) | yes | copyleft, modified versions must stay open |
| **AGPLv3** | yes | yes (strong, **network-triggered**) | yes | SaaS loophole closed (for backend services) |

The most important decision: **Do you want to allow someone to take your work, modify it, and distribute it as proprietary?**

- Yes → MIT/Apache-2.0 (adoption-first).
- No, it should stay open → GPL/AGPL.
- For your PQC capstone: **Apache-2.0** is the usual choice for crypto libraries (patent clause relevant for PQC!), MIT is acceptable for the CLI shell.

### Concept 2: Governance models

Governance is the answer to "Who is allowed to merge, and who is not?":

- **Solo Maintainer:** 1 person, full control, single point of failure. Realistic for your capstone right now.
- **BDFL (Benevolent Dictator For Life):** You decide finally, but the community discusses publicly (Linus model). Scales to medium projects.
- **Meritocracy / Steering Committee:** Appointed maintainers with voting rights (Rust, Kubernetes). Scales, needs formal rules.

Document explicitly in `GOVERNANCE.md` which model applies, **before** the first external PR arrives. Implicit governance is the most common source of maintainer burnout.

### Concept 3: Contributor funnel & the CLA decision

The funnel: Stars → Forks → Issues → PRs → Maintainers. Every stage has a barrier:

- **CLA (Contributor License Agreement):** a legal document that grants the project a license to the contribution. Necessary for enterprise-grade governance, overhead for solo projects.
- **DCO (Developer Certificate of Origin):** lighter — a `Signed-off-by:` in every commit. Linux kernel model. Recommended for Solo/BDFL.

For your capstone: DCO via `commit -s`, no CLA. Documented in CONTRIBUTING.md.

### Concept 4: Security disclosure policy

A PQC project without a disclosure policy is irresponsible. Create a `SECURITY.md` with:

- Where to report vulnerabilities (private email, not a public issue).
- Expected response time (SLA, e.g. 72h acknowledgement, 30d patch).
- Scope (which versions are supported).
- GPG/SSH contact key.

### Why this matters

These documents are not "paperwork" — they are the **infrastructure** that enables strangers to contribute without you becoming the bottleneck. Anyone who has set up a project with a clear license + governance + disclosure policy once can set up every future project in hours instead of weeks. This is direct career value.

### Pitfalls

- "I'll take MIT, it's the easiest" — without justification. MIT has no patent clause; for PQC (patent-encumbered) Apache-2.0 is the safer choice.
- No SECURITY.md → researchers report a public issue, the vulnerability becomes a 0-day.
- CLA without legal review for a solo project → unnecessary barrier, deters contributors.
- "Governance sorts itself out later" — never. The first PR flame decides, and then it's too late.

## 🛠️ Practice

**Task:** Fill in the four required files: `LICENSE`, `CONTRIBUTING.md`, `GOVERNANCE.md`, `SECURITY.md`. Decide and justify the license.

**Step by step:**

1. **Choose & justify the license** — write the justification (3 sentences) into `docs/LICENSE_RATIONALE.md`:

   > **Hints:**
   > - State the chosen license and give 3 justification sentences: the patent-clause relevance for PQC, the commercial-adoption stance (copyleft vs permissive), and enterprise-readiness.
   > - For a PQC capstone, Apache-2.0 is the usual choice (patent clause); MIT is acceptable for the CLI shell. Justify *your* pick, don't copy a generic blurb.
2. `LICENSE` with the full Apache-2.0 text (`gh license apache-2.0` or copy from choosealicense.com).
3. `CONTRIBUTING.md`:

   > **Hints:**
   > - **Before the PR:** the local quality gate (`cargo fmt`, `cargo clippy -- -D clippy::unwrap_used`, `cargo test`) and the "one test per new functionality" rule.
   > - **DCO:** every commit carries `Signed-off-by: Name <email>` via `git commit -s`; no CLA required.
   > - **Branch model:** `main` is release-stable; feature branches `feat/<short>` / `fix/<short>`; squash-merge only.
4. `GOVERNANCE.md`:

   > **Hints:**
   > - Name the governance model (Solo Maintainer / BDFL / Meritocracy), the maintainer with final merge authority, and an inactivity clause (e.g. what happens after >90 days of inactivity).
5. `SECURITY.md`:

   > **Hints:**
   > - **Reporting:** a private channel (encrypted email with a GPG key), explicitly *not* a public issue.
   > - **SLA:** acknowledgement and patch/mitigation timeframes (e.g. 72h / 30d).
   > - **Supported Versions:** a table mapping each version range to yes/no.

**Definition of Done (DoD):**

- [ ] `LICENSE` exists with the full Apache-2.0 text (no placeholder).
- [ ] `docs/LICENSE_RATIONALE.md` has 3 justification sentences that mention the patent clause.
- [ ] `CONTRIBUTING.md` mentions DCO (`-s`) and the clippy gate.
- [ ] `GOVERNANCE.md` names the model + maintainer + inactivity clause.
- [ ] `SECURITY.md` has a private reporting address, SLA, supported-versions table.
- [ ] Read `choosealicense.com/licenses/apache-2.0/`; you can explain the patent clause in 2 sentences.
- [ ] Commit: `git commit -s -m "day95: oss strategy — apache-2.0 + governance + security policy"`.

**Extension (optional):** Enable GitHub's `SECURITY.md` detection (the file in the repo root is automatically linked as the report channel in the Security tab UI). And set up `dependabot.yml` (block 4, day 66 — dependency scanning) for automated dependency updates.
