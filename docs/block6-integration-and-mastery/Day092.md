## 📖 Theory

Day 92 builds the **immutable contract layers** first: persistence, crypto, build target. Why first? Because every later layer (agent loop, tools) consumes these contracts. If the foundation wobbles on day 94, everything wobbles. This is the inversion of the natural temptation ("quickly build the cool part first").

### Concept 1: Secrets store format — envelope encryption

Secrets are *not* encrypted directly with ML-KEM (a KEM only produces a shared secret, not a direct AEAD over arbitrary lengths). The correct pattern is a **hybrid encryption envelope**:

1. Generate a random 256-bit **DEK** (data encryption key) per write for XChaCha20-Poly1305.
2. Wrap the DEK with **ML-KEM-768** (KEM: produces shared secret + ciphertext). Derive the key-wrapping key from it via HKDF-SHA256.
3. Encrypt the payload with the DEK (AEAD).
4. Persist `(KEM-ciphertext, AEAD-ciphertext, DEK-wrapped, nonce)` as a binary envelope.
5. Sign the entire file with **Ed25519** (integrity + authenticity, not confidentiality).

```
+-----------------+      +-------------------+
|  ML-KEM-768     |----->| HKDF -> KW-DEK    |
| (pubkey recipient)|   +-------------------+
+-----------------+            |
        +-----------------------+
        v
+-----------------+      +-------------------+
| XChaCha20-Poly1305 | -> | Secrets payload   |
| (DEK, nonce)       |   | (encrypted blob)  |
+-----------------+      +-------------------+
        |
        v
+-----------------+
| Ed25519 signature |  over the entire envelope
+-----------------+
```

### Concept 2: Cross-compile smoke first

The most common capstone killer on day 94: "runs locally, but `cross` fails on aarch64". Run the smoke test **as the first task**, not the last. If a crate (often `pqcrypto-ml-kem`) does not build on the target, you still have day 93 for workarounds (e.g. C binding via `cc`, or host-only with documented edge target).

```bash
rustup target add aarch64-unknown-linux-gnu
cargo install cross   # uses Docker, avoids linker frustration
cross build --target aarch64-unknown-linux-gnu --release
```

### Concept 3: Error story instead of `unwrap()`

Capstone code without a thought-through error story is not release-ready. Use `anyhow` for the binary layer (main, CLI) and `thiserror` for the library layer (secrets store module). Never `unwrap()` in non-test code — `cargo clippy -D clippy::unwrap_used` as the CI default.

### Why this matters

These three concepts — envelope crypto, smoke-first build, error story — are exactly what separates toy projects from production code. They cost an extra hour on day 92 and save half a day of panic on day 94. The transferable lesson: ordering is *material*, not aesthetic.

### Pitfalls

- Running ML-KEM directly over the payload — KEM is **key encapsulation**, not a stream cipher. Always a hybrid envelope.
- `cross` needs Docker running. On macOS: Docker Desktop active, otherwise `cross` fails with a cryptic linker error.
- Ed25519 signs *bytes*, not strings — sign the canonical binary representation of the envelope, not a "JSON string layout" that drifts depending on the serializer.

## 🛠️ Practice

**Task:** Implement (1) CLI skeleton, (2) `secrets-store` module with envelope encryption + signature, (3) cross-compile smoke. No agent loop yet.

**Step by step:**

1. `cargo new --bin pqc-agent`, then in `Cargo.toml`:

   ```toml
   [dependencies]
   clap = { version = "4", features = ["derive"] }
   anyhow = "1"
   thiserror = "1"
   pqcrypto-ml-kem = "0.7"     # check version number
   chacha20poly1305 = "0.10"
   ed25519-dalek = "2"
   rand = "0.8"
   hkdf = "0.12"
   sha2 = "0.10"
   serde = { version = "1", features = ["derive"] }
   bincode = "1"
   ```

2. Cross-compile smoke **now**, before you write logic:

   ```bash
   rustup target add aarch64-unknown-linux-gnu
   cross build --target aarch64-unknown-linux-gnu
   ```

   If it fails: stop, note risks in the one-pager (risk #1 made tangible), adjust the stack (e.g. `pqcrypto` C fallback via `cc`), retry. **Do not** continue with logic until smoke is green.
3. Implement `src/secrets.rs` with a `SecretsStore` and an `Envelope`:

   > **Hints:**
   > - Define an `Envelope` struct (derive `Serialize`/`Deserialize` for bincode) holding the ML-KEM ciphertext, the XChaCha20-Poly1305 ciphertext, a 24-byte nonce, and a 64-byte Ed25519 signature. Add a `version: u8` field for future migrations.
   > - `SecretsStore` owns a `PathBuf` and an Ed25519 `SigningKey`; expose `write(&self, payload: &[u8], recipient_pk: &PublicKey) -> Result<()>` and `read(&self, recipient_sk: &SecretKey) -> Result<Vec<u8>>`.
   > - Use `anyhow` for the binary layer and `thiserror` for the store module; never `unwrap()`/`expect()`.
   - `write`: generate DEK, KEM-encapsulate, derive HKDF, wrap DEK, AEAD encrypt, bincode-serialize, Ed25519-sign, file write.
   - `read`: Ed25519-verify **before** decryption, KEM-decapsulate, unwrap DEK, AEAD-decrypt.
4. CLI skeleton with `clap` (derive):

   > **Hints:**
   > - Derive `clap::Parser` on a `Cli` struct holding a `--secrets <path>` argument and a `#[command(subcommand)]` field.
   > - Define a `Cmd` enum (derive `Subcommand`) with variants `Init`, `Put { key, val }`, `Get { key }`.
   > - Wire `main` to dispatch on the subcommand into `SecretsStore`.
5. Tests: `#[test] fn roundtrip()` — writes `"api_key=secret"`, reads, compares. `#[test] fn tamper_detected()` — flips 1 byte in the envelope, expects a verify error on `read`.

**Definition of Done (DoD):**

- [ ] `cross build --target aarch64-unknown-linux-gnu` produces a binary (smoke green).
- [ ] `cargo test roundtrip` green.
- [ ] `cargo test tamper_detected` green (signature verification fails on modification).
- [ ] `cargo clippy -- -D clippy::unwrap_used` without warnings.
- [ ] No `unwrap()`/`expect()` in `src/secrets.rs`.
- [ ] Envelope struct is versioned (a `version: u8` field, value `1`) for future migratability.
- [ ] Commit: `git commit -m "day92: secrets-store with mlkem768 + ed25519 + cross-compile smoke"`.

**Extension (optional):** Persist the Ed25519 verification public key separately in `secrets.pub` and load it in `read()` from the file instead of from the in-memory struct. Then the signature is *actually* a binding anchor to an identity, not just to the current process.
