# Day 94: Capstone Polish & Release

**Block:** Block 6: Integration & Mastery · Capstone

> **Goal of the day:** The capstone is released as `v0.1.0`: SBOM generated, README with install/build/bench sections, semver-compliant, GitHub release with signed artifacts. Today **nothing** new is implemented — only polished, measured, documented, released.

---

## 📖 Theory

The last implementation day is the day engineers most often fail — not on the code, but on release hygiene. "Works on my machine" is not a release. A release is a **reproducible, provable, versioned snapshot**.

### Concept 1: Semver & changelog — the contracts

Semantic Versioning `MAJOR.MINOR.PATCH`:

- **MAJOR:** breaking API change (for `0.x` everything is breaking; `0.1.0` is the first *claim* of a shape).
- **MINOR:** new feature, backwards-compatible.
- **PATCH:** bugfix.

For your capstone you release **`v0.1.0`** — the first version that publicly claims "this is how it should be". `v0.0.x` would be development chaos; `v1.0.0` would be a maturity claim you cannot substantiate after 4 days. `0.1.0` is honest.

The **changelog** follows [Keep a Changelog](https://keepachangelog.com/) — one entry per release with categories `Added/Changed/Fixed/Removed/Security`:

```markdown
## [0.1.0] - 2026-09-XX
### Added
- ML-KEM-768 envelope-encrypted secrets store.
- Single-tool agent loop with MockLlm and max-iteration bound.
- Ed25519-signed audit log.
### Security
- Secrets encrypted at rest via hybrid KEM+AEAD envelope.
- Audit log signed with Ed25519; tamper detection covered by tests.
```

### Concept 2: SBOM — proof instead of claim

An SBOM (Software Bill of Materials, SPDX or CycloneDX) lists every transitive dependency. For a Rust project:

```bash
cargo install cargo-cyclonedx
cargo cyclonedx --format json --output-pattern package
# produces bom.json in CycloneDX 1.5 format
```

The SBOM is part of the release artifact, not an add-on. It is the proof that you know what is in your binary — the bridge to block 4 (supply chain) and day 66 (SBOMs).

### Concept 3: Reproducible build & signed artifacts

A release without reproducibility is a claim. Three mechanisms:

1. **Pinned deps:** `Cargo.lock` committed (mandatory for binaries, optional for libraries — you release a binary).
2. **`--locked` build:** `cargo build --release --locked` refuses if the lockfile drifts.
3. **Signed artifacts:** binary + SBOM + changelog are signed with `cosign` (Sigstore) — the block-4 connection in the release process, not just in the code.

```bash
cosign sign-blob --key cosign.key target/aarch64-unknown-linux-gnu/release/pqc-agent \
    --output-signature pqc-agent-v0.1.0.sig
```

### Concept 4: Bench as a first-class citizen

A capstone without a measurement is an opinion. Use `criterion`:

```rust
// benches/secrets_bench.rs
use criterion::{criterion_group, criterion_main, Criterion};
fn bench_write(c: &mut Criterion) {
    c.bench_function("secrets_write_4kb", |b| b.iter(|| write_payload(4096)));
}
criterion_group!(benches, bench_write);
criterion_main!(benches);
```

Document the number in the README under "Performance". A number (`secrets_write_4kb: 1.2 ms ± 0.1`) is an anchor that can be cited — "fast" is not.

### Why this matters

This day is the *most transferable* day of the entire curriculum. Whether you later release a CLI, a microservice, or a library — semver, changelog, SBOM, reproducible build, signed artifacts are the universal release engine. Anyone who has done this once has a head start that most senior engineers only catch up to after years.

### Pitfalls

- "I'll release when it's done" — a release is never done. `0.1.0` is the claim *of a state*, not of completion.
- Dropping the SBOM "because it's just dependencies" — supply-chain attacks are the most common attack surface in 2025+. The SBOM is not optional.
- No signature on the binary — then anyone can replace the binary with a modified one, and your Ed25519 audit log is worthless because the binary itself is not trustworthy.
- "Benchmark later" — without a number the performance claim in the README is a lie. Later never comes.

## 🛠️ Practice

**Task:** Release `v0.1.0`: changelog, SBOM, bench in README, GitHub release with signed artifacts.

**Step by step:**

1. **Lock & build reproducibly:**

   ```bash
   git add Cargo.lock   # if not yet committed
   cargo build --release --locked
   cross build --target aarch64-unknown-linux-gnu --release --locked
   ```

2. **Generate the SBOM:**

   ```bash
   cargo install cargo-cyclonedx
   cargo cyclonedx --format json --output-pattern package
   ls bom.json   # must exist
   ```

3. **Write the changelog:** Create `CHANGELOG.md`, entry `[0.1.0]` as in the template above. Every `### Added/Changed/Security` line references a day commit (`day92`, `day93`).
4. **Extend the README** with required sections:

   > **Hints:**
   > - **Install:** the exact `cross build --target aarch64-unknown-linux-gnu --release --locked` command and where the resulting binary lives.
   > - **Performance:** a table (Operation × Latency-host × Latency-aarch64) filled with the real `cargo bench` numbers for `secrets_write_4kb` and `agent_loop_mock` — no `<number>` placeholders left.
   > - **Security:** one paragraph on the ML-KEM-768 hybrid envelope + Ed25519-signed audit log + SBOM-in-release, plus a link to `docs/THREAT_MODEL.md` (1 paragraph: what is protected, what is not).
5. **Run the benchmark:**

   ```bash
   cargo bench --bench secrets_bench
   # copy the stable numbers into the README table
   ```

6. **Signature:**

   ```bash
   cosign generate-key-pair    # if not yet present
   cosign sign-blob --key cosign.key \
     target/aarch64-unknown-linux-gnu/release/pqc-agent \
     --output-signature pqc-agent-v0.1.0-aarch64.sig
   cosign sign-blob --key cosign.key bom.json --output-signature bom.json.sig
   ```

7. **Tag & release:**

   ```bash
   git tag -s v0.1.0 -m "Capstone v0.1.0"   # signed tag
   git push origin v0.1.0
   gh release create v0.1.0 \
     target/aarch64-unknown-linux-gnu/release/pqc-agent \
     bom.json \
     pqc-agent-v0.1.0-aarch64.sig \
     bom.json.sig \
     --title "v0.1.0 — PQC Edge Agent CLI" \
     --notes-file CHANGELOG.md
   ```

**Definition of Done (DoD):**

- [ ] `cargo build --release --locked` green (Cargo.lock committed, no drift).
- [ ] `bom.json` exists, is valid CycloneDX (BOM-Link or `cyclonedx validate`).
- [ ] `CHANGELOG.md` has a `[0.1.0]` entry with `Added/Security`.
- [ ] README has `Install`, `Performance` (with numbers), `Security` sections.
- [ ] `cargo bench` produces numbers that are in the README table.
- [ ] `git tag -s v0.1.0` is signed; `git tag --verify v0.1.0` green.
- [ ] GitHub release `v0.1.0` is created with binary + SBOM + 2 signatures as assets.
- [ ] `cosign verify-blob` against the released binary is green.
- [ ] Commit (before tag): `git commit -m "day94: v0.1.0 release with sbom+signatures"`.

**Extension (optional):** Set up a minimal GitHub Action `release.yml` that on a `v*` tag automatically cross-compiles, generates the SBOM, signs, and creates a `gh release`. This makes the release reproducible instead of manual — and is a direct transfer of day 69 (CI/CD Zero Trust) into your own product.
