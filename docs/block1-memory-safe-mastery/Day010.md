## 📖 Theory

### Sync vs. async

- **Sync:** a thread blocks on I/O — the OS switches to another thread (context switch is expensive).
- **Async:** a task voluntarily yields control while waiting on I/O (`.await`) — the runtime schedules another task on the same thread. One runtime manages thousands of tasks per OS thread.

### `Future` — the trait

```rust
trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

A future is a **state machine**. `poll` returns `Poll::Pending` (not done yet, wake me again via a waker) or `Poll::Ready(output)`. You almost never write `poll` directly — `async`/`await` generates the machine.

### `async fn` & `.await`

```rust
async fn fetch(url: &str) -> Result<String, reqwest::Error> {
    reqwest::get(url).await?.text().await
}
```

`async fn` returns an *anonymous future* (not a direct value). The body only runs once the future is polled — typically via `.await` or a runtime `spawn`.

### Runtimes: `tokio`

```rust
#[tokio::main]
async fn main() {
    let h1 = tokio::spawn(async { 1 + 1 });
    let h2 = tokio::spawn(async { 2 + 2 });
    println!("{}", h1.await.unwrap() + h2.await.unwrap());   // 6
}
```

`#[tokio::main]` builds a multi-thread executor. `tokio::spawn` launches a task on the executor (lightweight, no OS thread).

### `select!` — concurrency over multiple futures

```rust
tokio::select! {
    Ok(v) = listener.accept() => println!("conn: {v:?}"),
    _ = tokio::time::sleep(Duration::from_secs(5)) => println!("timeout"),
}
```

### `Send` bound for `spawn`

`tokio::spawn` requires `F: Future + Send + 'static`. A `Send` violation is the most common async compile error — usually because you hold `Rc` or a non-`Send` mutex. Fix: `Arc` instead of `Rc`, `tokio::sync::Mutex` instead of `std::sync::Mutex` when held across `.await`.

### Why this matters

Async is the foundation for all network services in Rust (web servers, proxies, AI inference orchestration). In Block 3 (AI-Native) you will build agent orchestration asynchronously; in Block 5 a high-performance server.

### Pitfalls

- `.await` on a future that is never polled → silent no-op ("future is dropped"). You need `tokio::spawn` or `block_on`.
- Holding `std::sync::Mutex` across `.await` → can deadlock (another task waits). Instead: lock briefly, copy the value, then `.await`.
- `?` in `async fn` works because the return type is a future over `Result`.
- `tokio::main` without `features = ["full"]` → missing components.

## 🛠️ Practice

**Task:** Write a TCP echo server that serves multiple clients concurrently, and a client that opens 3 parallel connections and verifies the responses.

**Step by step:**

1. `Cargo.toml`:

   ```toml
   [dependencies]
   tokio = { version = "1", features = ["full"] }
   ```

2. Implement the following in `src/main.rs`:

   > **Hints:**
   > - Annotate `main` with `#[tokio::main]` and return `std::io::Result<()>`. Bind a `TcpListener` to `127.0.0.1:0` (OS-chosen port) and capture `listener.local_addr()?`.
   > - Spawn a server task that loops on `listener.accept().await` and **for each connection** spawns a new task that echoes using `tokio::io::copy(&mut sock, &mut sock)`.
   > - Spawn 3 client tasks in parallel: each `TcpStream::connect(addr).await`, `write_all(&[i])`, then `read_exact` into a 1-byte buffer and returns the echoed byte.
   > - Await all client handles, then `server.abort()` to stop the accept loop.
3. `cargo run`.
4. Compare: build the same echo logic with `std::thread` (Day 9) and measure how many tasks you can serve simultaneously (without RAM explosion).

**Definition of Done (DoD):**

- [ ] `cargo build` without warnings.
- [ ] Server accepts 3+ clients in parallel without blocking.
- [ ] `tokio::spawn` per connection (task, not thread).
- [ ] `copy(&mut sock, &mut sock)` correctly used as echo.
- [ ] You can explain `Poll::Pending` vs. `Poll::Ready`.
- [ ] Commit: `git commit -m "day10: async/await and tokio"`.

**Extension (optional):** Add `tokio::select!` to automatically shut the server down after 10s of inactivity.
