# Day 8: Closures & Higher-Order Functions

**Block:** Block 1: Memory-Safe Mastery · Rust Fundamentals

> **Goal of the day:** You write closures with the correct capture mode (`Fn`/`FnMut`/`FnOnce`), return closures from functions, and use `move` deliberately.

---

## 📖 Theory

### Closures — anonymous functions with capture

```rust
let add = |a, b| a + b;              // type inferred from usage
let greeting = String::from("hi");
let greet = || println!("{greeting}"); // captured by reference
greet();
```

Unlike normal `fn` items, closures can **capture** variables from the surrounding scope. The compiler automatically deduces the minimal capture mode.

### The three closure traits

| Trait  | Capture              | Callable           | Typical use |
|--------|----------------------|---------------------|--------------|
| `FnOnce` | by value (consumes) | once             | `thread::spawn` (move) |
| `FnMut`  | by mutable ref        | multiple times, mutating | `Iterator::for_each` |
| `Fn`     | by shared ref         | multiple times, parallel-safe | event handlers, maps |

Subtrait hierarchy: `Fn: FnMut: FnOnce`. Anything that is `Fn` is also `FnMut` and `FnOnce`.

### `move` — forcing capture

```rust
let s = String::from("hi");
let printer = move || println!("{s}");   // s is MOVED into the closure
// println!("{s}");  ❌ s is moved
```

`move` is mandatory when a closure outlives the scope where it was defined — e.g. `thread::spawn`.

### Returning closures

```rust
fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    move |x| x + n
}
let add5 = make_adder(5);
println!("{}", add5(10));   // 15
```

`impl Fn(...)` is the idiomatic return — the concrete closure type is unnameable. Because of lifetime restrictions you often need `move`.

### Higher-order functions

Functions that take or return functions:

```rust
fn compose<A, B, C, F, G>(f: F, g: G) -> impl Fn(A) -> C
where F: Fn(B) -> C, G: Fn(A) -> B
{
    move |a| f(g(a))
}
let parse_then_add = compose(|x: i32| x + 1, |s: &str| s.parse::<i32>().unwrap_or(0));
```

### Why this matters

Closures are the foundation for all iterator adapters (`map`, `filter`, `fold`), for threads, for event callbacks, for `?` propagation in async. Rust's capture model is the same ownership model from Day 1 — applied to code blocks.

### Pitfalls

- Forgetting `move` in `thread::spawn` → "may not live long enough". The classic beginner mistake.
- `Fn` vs `FnMut`: a closure that needs `&mut` cannot be stored as `Fn` (e.g. `&dyn Fn`).
- Closure types are **unnameable** — you cannot put them in struct fields without `Box<dyn Fn>` or `impl Trait`.
- Recursion via closures is hard (no direct self-reference); usually better to use a real recursive `fn`.

## 🛠️ Practice

**Task:** Write `make_multiplier(factor: i32) -> impl Fn(i32) -> i32` and a `compose(f, g)` function. Demonstrate both plus a `thread::spawn` move.

**Step by step:**

1. Implement the following in `src/main.rs`:

   > **Hints:**
   > - Write `fn make_multiplier(factor: i32) -> impl Fn(i32) -> i32` — it returns a `move` closure that multiplies its argument by `factor`. `move` is needed because `factor` must outlive the function scope.
   > - Write a generic `fn compose<A, B, C, F, G>(f: F, g: G) -> impl Fn(A) -> C` with a `where` clause (`F: Fn(B) -> C, G: Fn(A) -> B`) — the returned `move` closure applies `g` then `f`.
   > - In `main`, create a `double` and `triple` multiplier, then a `compose` that parses a `&str` to `i32` and adds 1 (should turn `"41"` into `42`).
   > - Demonstrate `move` with `std::thread::spawn`: move a `String` into a closure that prints it, then `.join().unwrap()`.
2. `cargo run`.
3. Remove `move` in the `thread::spawn` example — observe the "may not live long enough" error. That internalizes the `move` requirement.

**Definition of Done (DoD):**

- [ ] `cargo build` without warnings.

- [ ] `compose` is generic with three type parameters + a `where` clause.
- [ ] `thread::spawn` with `move` compiles; without `move` it produces a comprehensible error.
