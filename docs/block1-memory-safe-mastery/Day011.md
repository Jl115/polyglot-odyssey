## 📖 Theory

### Newtype pattern

A tuple-struct with one field that wraps an existing type to give it a new identity:

```rust
struct UserId(u64);           // newtype
struct OrderId(u64);
fn fetch_user(id: UserId) {}  // cannot accidentally pass an OrderId
```

It solves two problems: (1) type safety against confusing primitive types, (2) you can implement your own traits that would be denied for the wrapped type (orphan rule).

### PhantomData — type parameters without a runtime value

```rust
use std::marker::PhantomData;

struct DbConn<S> { conn: Connection, _marker: PhantomData<S> }

struct ReadOnly;
struct ReadWrite;
impl DbConn<ReadOnly>  { fn read(&self) {} }
impl DbConn<ReadWrite> { fn write(&self, x: i32) {} }
```

`PhantomData<S>` tells the compiler "behave as if I owned an `S`" — without consuming memory. Important for lifetime and variance tracking.

### Typestate pattern — states in the type

```rust
struct Builder<T> { config: Config, _s: PhantomData<T> }
struct Unconfigured;
struct Configured;
impl Builder<Unconfigured> {
    fn configure(self, c: Config) -> Builder<Configured> { Builder { config: c, _s: PhantomData } }
}
impl Builder<Configured> {
    fn build(self) -> App { App { config: self.config } }
}
// builder.build() without configure() → compile error (not on Unconfigured)
```

Illegal transitions are rejected *at compile time*. This is the pinnacle of type-driven design.

### `Pin` & `Unpin` — self-referential safety

`Pin<P>` is a pointer wrapper that prevents the pointee from being moved. Important for `async` futures, which can hold self-references.

- `Unpin`: the type can safely be moved even when held by `Pin` (most types).
- `!Unpin`: the type may have self-references (e.g. generated futures). A move would dangle the reference.

You usually only encounter `Pin` when writing low-level async code or your own futures.

### GATs — generic associated types

```rust
trait LendingIterator {
    type Item<'a> where Self: 'a;
    fn next(&mut self) -> Option<Self::Item<'_>>;
}
```

Before GATs, associated types could not themselves be generic. GATs (stable since Rust 1.65) allow *lending iterators*, where each `next` returns a reference with a fresh lifetime.

### Why this matters

These features are the backbone of safe low-level APIs: `Pin` for async, GATs for lending iterators (e.g. an `Iterator` over `&mut [T]` slices), typestate for compile-time state machines. In Block 2 (memory pool) and Block 4 (crypto APIs) you will use all of them.

### Pitfalls

- `PhantomData<T>` affects *variance* and *drop-check* — non-trivial. For example, `PhantomData<fn() -> T>` is invariant vs. covariant differently.
- Newtypes are "free" abstractions (zero-cost), but `Deref` impls are not automatically forwarded from the inner `&self` methods — you must forward explicitly or write methods by hand.
- Typestate often produces many type parameters and code bloat — consider whether a runtime validation would be more readable.

## 🛠️ Practice

**Task:** Implement a `RequestBuilder` with typestate: states `Empty → WithUrl → WithBody → Built`. Each transition compiles only in the correct order.

**Step by step:**

1. Implement the following in `src/main.rs`:

   > **Hints:**
   > - Define marker state structs `Empty`, `WithUrl`, `WithBody` (unit structs in a `state` module).
   > - Make `RequestBuilder<S>` generic over the state, holding `url: Option<String>`, `body: Option<String>`, and a `PhantomData<S>` marker.
   > - Each transition method (`url`, `body`) consumes `self` and returns a `RequestBuilder<NextState>` — put `url` in the `impl RequestBuilder<Empty>` block and `body` in the `impl RequestBuilder<WithUrl>` block, so wrong-order calls don't compile.
   > - Implement `build()` only on `RequestBuilder<WithBody>`; use `format!` to produce the request string and `.unwrap()` on the Options (guaranteed populated by the typestate).
   > - Put `new()` only on `RequestBuilder<Empty>`. Verify the typestate by attempting `RequestBuilder::new().build()` — it must be a **compile error**, not a runtime one.
2. `cargo run`.
3. Provoke an error: call `.build()` on a `RequestBuilder<state::Empty>` — compile error. That is the proof that typestate works.

**Definition of Done (DoD):**

- [ ] `cargo build` without warnings.
- [ ] Three states (`Empty`, `WithUrl`, `WithBody`) as marker structs.
- [ ] `PhantomData<S>` in `RequestBuilder<S>`.
- [ ] Wrong order (`new().build()`) produces a compile error, not a runtime error.
- [ ] You can explain `Pin`/`Unpin` in 2 sentences (self-references, move prohibition).
- [ ] Commit: `git commit -m "day11: advanced type system (typestate, phantomdata, pin)"`.

**Extension (optional):** Write your own `!Unpin` future via `async fn` (or manually) that holds a self-reference — and observe that `Pin` is needed to poll it.
