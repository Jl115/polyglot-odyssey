# Day 3: Enums, Pattern Matching & Option/Result

**Block:** Block 1: Memory-Safe Mastery · Rust Fundamentals

> **Goal of the day:** You model states with enums, match them exhaustively, and use `Option`/`Result` instead of null pointers or exceptions.

---

## 📖 Theory

### Enums as algebraic sum types

A Rust enum can carry multiple variants, *each with its own data*. This is a **sum type** (`A | B | C`), not a C enum (which is just integer aliases).

```rust
enum IpAddr {
    V4(u8, u8, u8, u8),
    V6(String),
}
let home = IpAddr::V4(127, 0, 0, 1);
```

### `Option<T>` — the absence of null pointers

```rust
enum Option<T> { Some(T), None }
```

Instead of having `null` (Tony Hoare's "billion dollar mistake"), Rust forces you to carry the "maybe-not-there" case in the type — and the `match` must handle it. **There is no null-pointer dereference in safe Rust.**

### `Result<T, E>` — errors as values, not exceptions

```rust
enum Result<T, E> { Ok(T), Err(E) }
```

Errors are normal values. The `?` operator propagates `Err` upward automatically, analogous to exceptions, but without stack-unwinding magic.

### Pattern matching — exhaustive & destructuring

```rust
match maybe {
    Some(x) if x > 0 => println!("pos: {x}"),
    Some(_)         => println!("zero/neg"),
    None           => println!("nothing"),
}
```

`match` must be **exhaustive** — every possible value covered. The compiler rejects incomplete matches. This is a powerful refactoring tool: add an enum variant and every `match` breaks, immediately showing you all the spots that need updating.

### `if let` / `let else` — slim match variants

```rust
if let Some(x) = maybe { println!("{x}"); }    // only one case matters
let Some(name) = config.name else { return }; // early-return pattern
```

### Why this matters

`Option` + `Result` + exhaustive `match` replace three of the most common bug classes in other languages: null derefs, forgotten catch blocks, incomplete switch cases. They are the core of Rust's "errors as values" philosophy.

### Pitfalls

- `unwrap()`/`expect()` panic on the `Err`/`None` case — only allowed in tests or invariant paths. Avoid in library code.
- `match` with `_ =>` (wildcard) breaks the exhaustiveness warning for new variants — use sparingly, better to list all variants explicitly.
- `?` only works when the enclosing function type returns `Result` (or `Option`) and the error type is compatible.

## 🛠️ Practice

**Task:** Write a safe integer parser that splits a string and returns `Result<Vec<i32>, ParseError>`, with your own `ParseError` enum and exhaustive `match`.

**Step by step:**

1. Implement the following in `src/main.rs`:

   > **Hints:**
   > - Define a `ParseError` enum with `#[derive(Debug)]` and at least two variants — e.g. `Empty` (no data) and `BadToken(String)` (carries the offending token).
   > - Write `fn parse_csv(input: &str) -> Result<Vec<i32>, ParseError>`: split on `','`, `trim()` each token, skip empty tokens, and `match` on `t.parse::<i32>()` — push on `Ok`, return `Err(BadToken(...))` on `Err`. Return `Err(Empty)` if the result vector is empty.
   > - Write `fn run(input: &str)` that `match`es on `parse_csv(input)` and handles **every** `ParseError` variant explicitly (no `_` wildcard) — `Ok` prints the vector, each `Err` variant prints a descriptive message.
   > - In `main`, call `run` with a valid list, a list containing a bad token, and an empty string.
2. `cargo run`.
3. Provoke exhaustiveness: add `ParseError::Overflow` without updating the `match` in `run` — the compiler must complain. That is the demonstration.
4. Use `?` in a function `fn sum(input: &str) -> Result<i32, ParseError>` that calls `parse_csv(input)?` and returns the sum.

**Definition of Done (DoD):**

- [ ] `cargo build` without warnings.
- [ ] A custom `ParseError` enum with at least two variants, one carrying data.
- [ ] The `match` in `run` is exhaustive without a wildcard.
- [ ] Adding a new enum variant produces a compile error in `run` (proven).
- [ ] `?` operator used correctly in `sum`.
- [ ] Commit: `git commit -m "day3: enums, pattern matching, option/result"`.

**Extension (optional):** Build a small state machine `enum Door { Open, Closed, Locked }` with `fn turn_key(&mut self)` / `fn close(&mut self)` that rejects illegal transitions as `Result<(), &'static str>`.
