# Day 18: Rust + TS Interop (Node-API)

**Block:** Block 1: Memory-Safe Mastery · Rust ↔ TS Interop

> **Goal of the day:** You write a native Node.js addon in Rust via `napi-rs`, call it from TypeScript in a type-safe way, and know the trade-offs vs. WASM.

---

## 📖 Theory

### Node-API (formerly N-API) — a stable C-ABI

Node-API is a C interface that is stable across V8 updates (addons do not need recompiling on Node upgrades). Instead of hand-writing C, we use **`napi-rs`**, which maps Rust traits onto Node-API.

### `napi-rs` — ergonomic Rust

```rust
use napi_derive::napi;

#[napi]
pub fn add(a: i32, b: i32) -> i32 { a + b }

#[napi]
pub fn fib(n: u32) -> u64 {
    let (mut a, mut b) = (0u64, 1u64);
    for _ in 0..n { let t = a + b; a = b; b = t; }
    a
}
```

`#[napi]` generates the C wrapper function + type conversion. Building via `napi build --release` produces `.node` files per platform (Linux/macOS/Windows × x64/arm64).

### Async functions

```rust
#[napi]
pub async fn fetch_data(url: String) -> Result<String, napi::Error> {
    // blocks the Rust thread, but Node's event loop stays free
    Ok(format!("got {url}"))
}
```

`async` in `napi-rs` returns a JS promise. Internally a Tokio task is spawned.

### TS type generation

`napi build` automatically generates a `.d.ts` file with the TypeScript types of the exported Rust functions. That gives the JS side full type inference — no manual annotation.

### WASM vs. Node-API — when to use what?

| Criterion | WASM | Node-API |
|-----------|------|---------|
| Platform | Browser, edge, Node, everywhere | Only Node (and Bun, partially) |
| Setup | `wasm-pack`, `.wasm` import | Native `.node` per platform, prebuild distribution |
| File/net access | Limited (WASI) | Full (Node-API) |
| Performance | Very similar; primitives free | Very similar; FFI call slightly more expensive |
| Code size | Small | Larger (dynamic lib) |
| Deployment | Browser + edge | Server + CLI in Node |

For pure compute functions that must run everywhere → WASM. For Node-only backends with full system access → Node-API.

### Why this matters

`napi-rs` is the basis for high-performance Node modules in Rust: `@swc/core`, `napi-rs/prisma-engines`, `@parcel/css`. In Block 3 you will build AI agent runtimes that move performance-critical paths into Rust.

### Pitfalls

- Native addons must be compiled per platform. Use `@napi-rs/cli`'s prebuild workflow (`napi prepublish`) for cross-platform npm packages.
- `#[napi]` functions must not panic — wrap in `Result<_, napi::Error>` and convert.
- Thread safety: Rust types that are not `Send` cannot go into async tasks. `napi-rs` has `#[napi(thread_safe_function)]` for callbacks.
- Buffers: use `napi::Buffer` instead of `Vec<u8>` for zero-copy.

## 🛠️ Practice

**Task:** Write a `napi-rs` module with `sha256_hex(input: String) -> String` and `fib(n: u32) -> u64`, build it, and call it from TS.

**Step by step:**

1. Setup:

   ```bash
   npm create @napi-rs/app day18
   cd day18
   npm i
   ```

2. `Cargo.toml` (generated by the template):

   ```toml
   [lib]
   crate-type = ["cdylib"]

   [dependencies]
   napi = { version = "2", features = ["napi8"] }
   napi-derive = "2"
   sha2 = "0.10"
   hex = "0.4"
   ```

3. Implement the following in `src/lib.rs`:

   > **Hints:**
   > - `use napi_derive::napi` and `use sha2::{Sha256, Digest}`. Annotate each public function with `#[napi]`.
   > - `fib(n: u32) -> u64`: iterative loop with two `u64` accumulators swapping `t = a + b` each step, returning `a`.
   > - `sha256_hex(input: String) -> String`: create a `Sha256` hasher, `h.update(input.as_bytes())`, then `hex::encode(h.finalize())`. The `#[napi]` macro generates the C wrapper + automatic `.d.ts` types.
   > - Functions must not panic — keep them infallible here (the `Result` pattern comes in later days).
4. Build + generate TS: `npm run build` (calls `napi build`).
5. Write `test.ts` to call the native addon and verify results:

   > **Hints:**
   > - Import `fib` and `sha256_hex` from `"."` (the generated entry that re-exports the `.node` addon).
   > - Print `fib(40)` (expect `102334155`) and `sha256_hex("hello")`.
   > - Print the expected SHA-256 hex of `"hello"` for comparison: `2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824`. The import should be fully type-inferred (no `any`) thanks to the generated `.d.ts`.
6. `npx tsx test.ts` (or via `tsc && node`).

**Definition of Done (DoD):**

- [ ] `npm run build` produces a `.node` file + `.d.ts`.
- [ ] `fib(40) === 102334155`.
- [ ] `sha256_hex("hello")` matches the expected hex string.
- [ ] The TS import has type inference (no `any` for the two functions).
- [ ] You can name 2 reasons WHEN to choose Node-API vs. WASM.
- [ ] Commit: `git commit -m "day18: rust + ts interop via napi-rs"`.

**Extension (optional):** Use `napi::Buffer` for a `sha256_buf(input: Buffer) -> Buffer` and measure the speedup vs. `String` marshalling for 1MB inputs.
