---

## 📖 Theory

### WASM — portable bytecode, sandboxed

WebAssembly is a compact, fast bytecode standard that runs in browsers, Node.js, Deno, Cloudflare Workers, edge runtimes. Rust can compile natively to `wasm32-unknown-unknown` — WASM is *not* JavaScript, but a second, sandboxed runtime target.

### `wasm-bindgen` — the bridge to the JS world

`wasm-bindgen` generates JS/cohesion code that translates Rust types into JS types:

```rust
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn add(a: i32, b: i32) -> i32 { a + b }

#[wasm_bindgen]
pub fn count_words(text: &str) -> usize {
    text.split_whitespace().count()
}
```

After `wasm-pack build --target nodejs` you get a `pkg/` directory with `.wasm` + `.js` glue that you import in Node.

### Marshalling — where time is lost

- **Primitives** (`i32`, `f64`): direct, free.
- **Strings:** must be copied (UTF-16 ↔ UTF-8 conversion + memory copy). Expensive for large texts.
- **Vec<u8>:** copied, except with `js_sys::Uint8Array` via a `wasm-bindgen` memory view (zero-copy possible).
- **Objects:** via `js_sys::Object`/`serde-wasm-bindgen`, require serialization.

That is why pure compute functions (number crunching, crypto, image processing) are the sweet spot for WASM — not I/O.

### WASI — the "server WASM"

`wasm32-wasip1` (formerly `wasi`) is a system interface that gives WASM modules file/network access (sandboxed). Useful for CLI tools that run identically everywhere.

### Memory model

WASM has linear memory (one big `ArrayBuffer`). Rust allocates inside it via `dlmalloc`/`wee_alloc`. JS can access the memory directly via `wasm.memory.buffer` — the basis for zero-copy patterns.

### Why this matters

WASM is the foundation for: edge compute (Cloudflare, Fastly), in-browser code editors (VS Code, Zed), crypto libraries (Age, ML-KEM implementations), ML inference (ONNX Runtime, wasmtime). In Block 4 you will deploy PQC in WASM.

### Pitfalls

- String marshalling often dominates runtime — prefer `&[u8]` over `&str` when possible.
- The `wasm-bindgen` `externref` feature is new and not yet stable for all patterns.
- Panics in WASM become JS exceptions, but stack unwinding costs code size. Use `console_error_panic_hook` for more readable messages.
- A file system in browser WASM does *not* exist — only in WASI targets.
- Crate dependencies that use `std::fs`/`std::net` do *not* compile for `wasm32-unknown-unknown`. Set lockfiles and features accordingly.

## 🛠️ Practice

**Task:** Write a Rust function `fib(n: u32) -> u64`, compile it to WASM, call it from Node.js, and compare performance against a native JS implementation.

**Step by step:**

1. Prepare the Rust toolchain:

   ```bash
   rustup target add wasm32-unknown-unknown
   cargo install wasm-pack
   ```

2. Project:

   ```bash
   cargo new --lib day16_wasm
   cd day16_wasm
   ```

3. `Cargo.toml`:

   ```toml
   [package]
   name = "day16_wasm"
   version = "0.1.0"
   edition = "2024"

   [lib]
   crate-type = ["cdylib"]

   [dependencies]
   wasm-bindgen = "0.2"
   ```

4. Implement the following in `src/lib.rs`:

   > **Hints:**
   > - `use wasm_bindgen::prelude::*` and annotate each public function with `#[wasm_bindgen]`.
   > - `fib(n: u32) -> u64`: an iterative loop maintaining two `u64` accumulators `(a, b)` starting at `(0, 1)`, swapping `t = a + b; a = b; b = t` each iteration, returning `a`.
   > - `count_words(text: &str) -> usize`: split on whitespace and count (`text.split_whitespace().count()`). The `&str` marshalling is the costly part — note it for the DoD discussion.
5. Build: `wasm-pack build --target nodejs`.
6. Write `test.mjs` to call the WASM module from Node and benchmark it:

   > **Hints:**
   > - Import `fib` and `count_words` from `"./pkg/day16_wasm.js"` (the glue produced by `wasm-pack`).
   > - Time `fib(40)` with `performance.now()` before/after, print the result and elapsed ms.
   > - Write a JS `BigInt` Fibonacci (`jsFib`) for comparison and time it the same way so you can compute the WASM-vs-JS ratio.
   > - Call `count_words("hello world from wasm")` and print the result (expect 4).
7. `node test.mjs`.

**Definition of Done (DoD):**

- [ ] `wasm-pack build --target nodejs` without errors.
- [ ] `fib(40) === 102334155` in Node.
- [ ] `count_words("a b c") === 3`.
- [ ] You note the performance ratio WASM vs. JS (likely 1.5–4× faster for pure number loops).
- [ ] You can explain why string parameters are more expensive than number parameters (marshalling).
- [ ] Commit: `git commit -m "day16: rust + ts interop via wasm"`.

**Extension (optional):** Implement `sha256(input: &[u8]) -> [u8; 32]` in Rust-WASM via the `sha2` crate, and pass a 1MB `Uint8Array` from JS without copying via `js_sys::Uint8Array::view`. Measure the speedup vs. `crypto.subtle.digest`.
