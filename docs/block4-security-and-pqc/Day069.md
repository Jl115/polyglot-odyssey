# Day 69: CI/CD Zero Trust

**Block:** Block 4: Security & PQC · Supply Chain Security

> **Goal of the day:** You can harden a CI/CD pipeline by zero-trust principles — least-privilege tokens, ephemeral runners, signed secrets, workload identity — and recognize why the classic "long-lived PAT in GitHub Actions" anti-pattern is today the most common supply-chain attack vector.

---

## 📖 Theory

**Zero trust** is not a product but a principle: *"Never trust, always verify"* — every step re-authenticates and re-authorizes every other step, as if the network were hostile. For CI/CD this means: runners have no long-term secrets, builds are isolated, every step attests its identity.

### The classic anti-pattern landscape

```text
❌ Anti-pattern 1: Long-lived Personal Access Token (PAT) in repo secrets
  → Compromise = compromise of all the owner's repos. (Codecov 2021)

❌ Anti-pattern 2: Runner with SSH keys to the prod server
  → Compromise of the runner = prod server. (Hipocampo 2023)

❌ Anti-pattern 3: `pull_request_target` workflow that exposes secrets to forks
  → Malicious PR leaks all secrets. (Many CVEs 2021–2024)
```

### Zero-trust CI building blocks

| Building block | Classic | Zero-trust |
| --- | --- | --- |
| Outbound auth | PAT (years) | **OIDC tokens** (10 min) via `id-token: write` |
| Cloud auth | access key in a secret | **workload identity federation** (AWS/GCP/Azure): OIDC token → short-lived cloud creds |
| Runner | persistent VM with cache | **ephemeral runner** (GH-hosted, self-hosted with auto-destroy) |
| Secrets | base64 in YAML | **secret manager** (Vault, AWS SM) + just-in-time fetch |
| Build-artifact trust | "trustme" | **Sigstore signature + SLSA provenance** (Day 67/68) |
| Network egress | open | **egress allowlist**, block metadata service |

### Workload identity federation (the foundation)

```text
GitHub Action ──OIDC token (10-min, signed by GitHub)──> Cloud STS
                                                          │
Cloud STS ──validates OIDC issuer + subject-claim ──> short-lived AWS creds (15 min)
                                                          │
AWS Action ──uses creds──> S3/ECR/etc.
```

No `AWS_ACCESS_KEY_ID` in repo secrets. The AWS trust policy checks: `issuer == actions.githubusercontent.com` AND `subject == repo:org/repo:ref:refs/heads/main` — only main can deploy.

### Workflow hardening rules

1. **`permissions:` minimal** — never `write-all`, but declare per job (`contents: write`, `id-token: write`, `attestations: write`).
2. **Avoid `pull_request_target`** — it has access to secrets *and* checks out the PR branch. Prefer `pull_request` with `continue-on-error` for non-confidential checks.
3. **Pin third-party actions** to a commit hash, not to `@v1` (tags can be moved):

   ```yaml
   - uses: actions/checkout@a5ac7e51b41094c92402c325a5b6f7e6c0e2c2c2  # not @v4
   ```

4. **Runner isolation**: no self-hosted runners for public repos (cross-repo attack surface).
5. **Egress filter**: block `169.254.169.254` (cloud metadata) at the runner level — otherwise a build can steal the host's cloud identity.

### Why this matters

Codecov breach (2021), Hipocampo (2023), the 2022 CodeCov PR-exfil epidemic — all came via long-lived CI credentials. Zero-trust CI is the direct implementation of the "assume compromise" question from the threat model (Day 59) for the pipeline itself. Without it, Day 67/68 are worthless — a signed build from a compromised runner is only signed damage.

### Pitfalls

- **`pull_request_target` with `actions/checkout@v2` without a ref** — checks out PR code that has secret access → disaster. Never use `pull_request_target` for non-admin builds.
- **Self-hosted runner on a dev VM** — the VM has dev keys, SSH configs, history; a build script can exfiltrate them.
- **OIDC trust policy too wide** — `"sub": "*"` allows any GH repo to get AWS creds. Always restrict to `repo:org/repo:ref:refs/heads/main`.
- **Reusable workflows without review** — `uses: ./.github/workflows/deploy.yml@main` pulls code from main; whoever does not review main implicitly has trust over everything.
- **Build cache from untrusted sources** — cache poisoning can survive a binary backdoor. Either don't use cache or use signed cache.

## 🛠️ Practice

**Task:** Harden a GitHub Action pipeline for `pqc-tool` with: OIDC → AWS IAM role (simulated via OIDC dump), minimal permissions, hash-pinned actions, egress-restricted runner, Sigstore signature.

**Step by step:**

1. Write `.github/workflows/release.yml` yourself:

   > **Hints:**
   - Trigger on version tags (`on: push: tags: ['v*']`); set `permissions:` to `contents: read`, `id-token: write` (for OIDC), `attestations: write`.
   - Set `AWS_EC2_METADATA_DISABLED: "true"` in the job env to block metadata-service exfiltration.
   - Pin every `uses:` to a **commit hash**, not a floating `@v4` tag (checkout, rust-toolchain, cosign-installer, attest-build-provenance).
   - Build with `cargo build --release --locked --offline`.
   - Add a step that dumps the OIDC token (via `ACTIONS_ID_TOKEN_REQUEST_TOKEN` / `ACTIONS_ID_TOKEN_REQUEST_URL` with `audience=sigstore`) — demo only, never in prod.
   - Add `actions/attest-build-provenance@v1` for SLSA provenance and `sigstore/cosign-installer` + `cosign sign-blob --yes --bundle` for keyless signing.

2. **AWS trust policy** — write `docs/iam-trust-policy.json` yourself:

   > **Hints:**
   - This is an IAM role trust policy (not a permission policy). `Effect: Allow`, `Action: sts:AssumeRoleWithWebIdentity`.
   - `Principal.Federated` = the ARN of the GitHub OIDC provider (`arn:aws:iam::ACCOUNT:oidc-provider/actions.githubusercontent.com`).
   - `Condition.StringEquals` must restrict `actions.githubusercontent.com:sub` to exactly `repo:your-org/pqc-tool:ref:refs/heads/main` — **never** `"*"`.
3. **Audit**: a script `audit-workflow.sh` that checks all `uses:` for non-pinned tags:

   ```bash
   grep -rE "uses: .*@(v[0-9]+|main|master)" .github/
   # every match → manually switch to a commit hash
   ```

4. Write `docs/zero-trust.md` with a checklist: which building blocks are implemented, which are open, risks per open item.

**Definition of Done (DoD):**

- [ ] The `permissions:` block is minimal (not `write-all`), only the necessary per job.
- [ ] All `uses:` are pinned to a commit hash (the audit script finds 0 floating tags).
- [ ] The OIDC token dump shows `sub: repo:your-org/pqc-tool:ref:refs/heads/main`.
- [ ] The AWS trust policy is restricted to exactly one repo + branch (not `*`).
- [ ] `AWS_EC2_METADATA_DISABLED=true` is set (defense in depth against metadata exfil).
- [ ] `docs/zero-trust.md` has a checklist ≥8 points, each with status ✅/❌.
- [ ] You can explain in 2 sentences why OIDC-based WIF is better than long-lived access keys.
- [ ] Commit: `git commit -m "day69: zero-trust ci/cd (oidc, minimal perms, hash-pinned actions)"`.

**Extension (optional):** Set up **Hashicorp Vault** with JWT auth (GitHub OIDC → Vault → Vault issues AWS creds just-in-time for 5 minutes) — that is the enterprise variant of WIF.
