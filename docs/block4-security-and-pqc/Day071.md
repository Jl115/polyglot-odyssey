# Day 71: Rust Verification with Prusti

**Block:** Block 4: Security & PQC · Formal Verification

> **Goal of the day:** You can use **Prusti** (Rust verifier based on Viper) to specify and verify a simple Rust function with `requires`/`ensures` contracts — and you understand the difference between testing (shows absence of bugs for concrete inputs) and verification (shows absence of bugs for *all* inputs).

---

## 📖 Theory

Testing finds bugs. Formal verification proves the *absence* of bug classes. For critical code paths (crypto, memory management, auth) this is the qualitative leap that makes the difference between "probably secure" and "proven correct".

### Prusti vs. testing vs. type system

| Method | What is proven | Effort | Guarantee |
| --- | --- | --- | --- |
| Unit tests | For inputs in the test cases | low | only those inputs |
| Type system (Rust borrow check) | memory safety, no data races | medium | all inputs |
| **Prusti** | user-defined contracts (`requires`/`ensures`) | high | all inputs, within the scope of the contracts |
| **Kani** (Day 72) | properties via `proof_harness` | medium-high | bounded model check |

### Prusti contracts

Prusti uses Rust attributes that the normal compiler ignores but Prusti interprets as specs:

```rust
#[requires(x <= i32::MAX / 2)]          // precondition: only for inputs satisfying this
#[ensures(result == x * 2)]             // postcondition: guarantee of the return
fn double(x: i32) -> i32 {
    x * 2
}
```

Prusti derives the Hoare calculus for the function and proves: *"For all x satisfying the precondition, the postcondition holds after execution."* If the function had a bug (e.g. `x * 3`), Prusti would throw a counter-example error.

### What Prusti can / cannot do

**Can:**

- Integer-overflow avoidance (`requires(x <= MAX/2)`).
- Slice bounds (`requires(i < v.len())`, `ensures(result == v[i])`).
- Memory properties (`ensures(*result == old(*x))` for mutable refs).
- Loop invariants (manually via `#[invariant(...)]`).

**Cannot (practically):**

- Crypto properties (Prusti cannot prove "AES is secure").
- Complex heap-aliasing situations (too much reasoning effort).
- Floating-point exactness.

### Loop invariants — the core

Loops are the hardest specs because you must give the verifier an invariant that holds before, during, and after the loop:

```rust
#[requires(n <= 1000)]
#[ensures(result == n * (n + 1) / 2)]
fn sum_to(n: u32) -> u32 {
    let mut sum = 0;
    let mut i = 0;
    #[invariant(sum == i * (i + 1) / 2)]
    #[invariant(i <= n)]
    while i < n {
        i += 1;
        sum += i;
    }
    sum
}
```

Find the right invariant and Prusti checks: (1) holds before the loop, (2) stays true at every iteration step, (3) together with the loop exit it yields the postcondition. That is the Hoare calculus for while loops.

### Why this matters

Crypto libraries, auth logic, memory allocators — where bugs can be life-threatening — benefit enormously. OpenSSL's "constant-time patch" class could have been proven with Prusti specs ("no branch depends on secret data"). Prusti is still academic, but the trend toward verified Rust is one of the most important Rust research directions (with RustBelt and Verus).

### Pitfalls

- **Contracts too weak** — `#[ensures(result >= 0)]` is true for `fn double` (because `x*x >= 0` for all x), but not useful. Specs must express the *actual* desired property.
- **Loop-invariant search is hard** — wrong invariant → Prusti does not verify; too weak → verification fails; often iterative.
- **Performance** — verifying large functions takes minutes; use incrementally.
- **Only source properties** — Prusti does not check whether libc calls are correct. Rust bindings to C remain C verification's job.
- **"Verified" ≠ "secure"** — verified against *your* specs. If the specs do not specify the bug, it is not covered. Specs are the real engineering.

## 🛠️ Practice

**Task:** Install Prusti, verify three functions with contracts (overflow-safe double, slice index, sum loop), and deliberately break the spec to see the verifier error.

**Step by step:**

1. Install (current path via nightly toolchain):

   ```bash
   # Current instructions see prusti-dev/prusti
   # Simplified:
   rustup install nightly
   git clone https://github.com/viperproject/prusti-dev.git
   cd prusti-dev
   ./x.py install   # or via released binary
   # prusti-rustc is then in PATH
   ```

2. Project:

   ```bash
   cargo new day71 --bin
   cd day71
   ```

3. Functions with specs — implement these three in `src/main.rs` yourself:

   > **Hints:**
   - `double_safe(x: i32) -> i32`: add `#[requires(x <= i32::MAX / 2)]` (precondition prevents overflow) and `#[ensures(result == x * 2)]` (postcondition). Body is just `x * 2`.
   - `get_or_panic(v: &[i32], i: usize) -> i32`: `#[requires(i < v.len())]` and `#[ensures(result == v[i])]`. Body: index `v[i]`.
   - `sum_to(n: u32) -> u32`: `#[requires(n <= 1000)]` and `#[ensures(result == n * (n + 1) / 2)]`. Use a `while` loop with two `#[invariant(...)]` attributes — one for `sum == i * (i + 1) / 2` and one for `i <= n`.
   - Add a `main` that calls all three with safe inputs so you can observe output.
   - Remember: the `#[invariant]` attributes go on the `while` loop, not the function.
4. Verify: `prusti-rustc src/main.rs` (or `cargo-prusti run`).
5. **Break-the-spec test**: change `double_safe` to `x * 3` → Prusti shows "Postcondition might not hold" with a counter-example.
6. **Loop-invariant challenge**: remove `#[invariant(sum == i * (i + 1) / 2)]` → Prusti cannot prove it, fails. Add it back → ok.
7. Write `docs/prusti-notes.md` with: what worked, what did not, what you learn about specs.

**Definition of Done (DoD):**

- [ ] Prusti is installed; `prusti-rustc --version` returns a version.
- [ ] All three functions verify successfully ("verification successful").
- [ ] The break-the-spec test shows the verifier error with a message.
- [ ] You can explain in 2 sentences why verification ≠ testing (quantified over inputs).
- [ ] `docs/prusti-notes.md` lists at least 1 spec you had to adjust iteratively.
- [ ] Commit: `git commit -m "day71: prusti formal verification with hoare contracts"`.

**Extension (optional):** Verify a small **constant-time** property for a `u8` comparison function (`fn ct_eq(a: &[u8], b: &[u8]) -> bool`): spec "runtime independent of the value of the inputs" — that is hard, but Prusti can work with `#[invariant(...)]` over branch conditions (advanced!).
