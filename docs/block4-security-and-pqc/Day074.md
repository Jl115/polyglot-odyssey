# Day 74: TEE & OP-TEE

**Block:** Block 4: Security & PQC · Hardware-Security

> **Goal of the day:** You know the architecture of a **Trusted Execution Environment (TEE)** — how it isolates from the normal OS, how enclaves guarantee code integrity + confidentiality — and can sketch a minimal trusted application with OP-TEE (Open Portable TEE, ARM TrustZone). You know why TEEs are not a panacea (Spectre, side channels).

---

## 📖 Theory

A **TEE (Trusted Execution Environment)** is a hardware-isolated area in the processor where code and data stay secret from the rich OS (Linux) — even under root compromise of the host OS. Applications: DRM, biometric authentication, hardware keys, mobile payment, confidential computing.

### The three trusted-compute pillars

| Property | What it means | Contrast with normal OS |
| --- | --- | --- |
| **Integrity** | Code in the TEE cannot be altered by the host OS | Host OS can patch a binary |
| **Confidentiality** | The TEE's memory is invisible to the host OS | Host OS can dump memory |
| **Attestation** | The TEE can remotely prove it is running genuine code | Host OS cannot identify itself |

### TrustZone (ARM) vs. SGX (Intel) vs. SEV-SNP (AMD)

| TEE | Architecture | Strength | Weakness |
| --- | --- | --- | --- |
| **ARM TrustZone** | separate "secure world" (S-mode) | ubiquitous, mobile devices | secure-world code = kernel attack surface |
| **Intel SGX** | enclaves in user space | per-process isolation | Spectre/Meltdown broke confidentiality |
| **AMD SEV-SNP** | VM isolation with encrypted memory | whole VMs encrypted | more complex TCB |
| **Confidential VM (Google/Azure)** | SEV/SGX wrapped | managed service | vendor lock-in |

### OP-TEE — the open-source implementation for TrustZone

**OP-TEE** (Linaro, 2013+) is an open-source TEE OS for ARM TrustZone. Trusted applications (TAs) run in the secure world and communicate with the rich OS via the **GlobalPlatform TEE Client API**.

```text
┌──────────────────────────────────┐
│ Normal World (Linux)             │
│   App ── TEE Client API ──────────┼──┐
│                                   │  │  SMC call
└──────────────────────────────────┘  │
                                      ▼
┌────────────────────────────────────────────┐
│ Secure World (OP-TEE)                      │
│   OP-TEE Core (kernel)                     │
│   Trusted Application (TA)                 │
│     - code signed by trusted root          │
│     - memory encrypted & isolated          │
└────────────────────────────────────────┬───┘
                ▲                            │
                │  Attestation               │
                └────────────────────────────┘
```

### Trusted Application (TA) — minimal

A TA is a C program running in the secure world. It has entry points for `TA_CreateEntryPoint`, `TA_OpenSessionEntryPoint`, `TA_InvokeCommandEntryPoint`. Signed with a key that lives in the OP-TEE root of trust.

```c
// trusted_app/ta_main.c (simplified)
#include <tee_ta_api.h>
#include <string.h>

TEE_Result TA_InvokeCommandEntryPoint(void *session, uint32_t cmd,
                                        void *params, size_t len) {
    switch (cmd) {
        case 1: // CMD_ENCRYPT
            return crypto_aes_gcm_encrypt(params, len);
        case 2: // CMD_DECRYPT
            return crypto_aes_gcm_decrypt(params, len);
        default:
            return TEE_ERROR_BAD_PARAMETERS;
    }
}
```

### The side-channel danger

TEEs protect *logically*, not *physically* — side channels bypass the isolation:

- **Spectre / Meltdown** (2018): SGX enclave secrets leaked from user space via speculative execution.
- **Cache timing**: an attacker shares L2 cache with the enclave, measures accesses.
- **Power analysis**: on IoT devices power consumption can leak secrets.
- **Rowhammer**: bit flips in neighboring memory cells.

OP-TEE's documentation warns explicitly: TEEs are **not** complete protection against a local attacker with physical access. They are *remote-attestable isolation*, not a cryptographic fortress.

### Why this matters

Mobile payment (Apple Pay, Google Pay), Android Keystore, FIDO2 keys — all run in TEEs. PQC migration (Day 64) affects TEEs: PQC algorithms must run in TA form in the secure world if the keys are to be hardware-protected. Hardware key storage + PQC is an open research field. Anyone taking Block 4 seriously cannot avoid TEEs.

### Pitfalls

- **"A TEE is unbreakable"** — wrong. TEEs have a **TCB (Trusted Computing Base)** that is itself attackable (OP-TEE core bugs, firmware-update mechanisms, bootloader).
- **TA code is part of the TCB** — every bug in the TA is a TEE bug, not "just an app bug". Minimal code, formally verified (Day 71/72) where possible.
- **Forgotten Spectre variant** — TEEs are vulnerable to speculative-execution attacks; mitigations (`-mindirect-branch-throttle`) in TA builds.
- **Bypassing attestation verification** — the client must validate the TA report, otherwise you only have a "trust me" TEE without proof.
- **TA signing key in dev repos** — if the TA signing key leaks, anyone can load a "TA" into the secure world. HSM mandatory (Day 58).

**Task:** Create a minimal OP-TEE TA project skeleton (code + signature workflow), without necessarily deploying it on hardware — focus on architecture understanding. Alternative: use QEMU-ARM with an OP-TEE image.

**Step by step:**

1. **Option A — QEMU + OP-TEE (real test)**:

   ```bash
   git clone https://github.com/OP-TEE/optee_os.git
   git clone https://github.com/OP-TEE/optee_examples.git
   # Build with the QEMU-virt board
   # See optee_os/README.md → QEMU build
   # Start: make run-qemu-virt
   # In QEMU Linux: optee_example_hello_world
   # → "TA invoked with cmd 0, Response: Hello World!"
   ```

2. **Option B — skeleton without hardware** (if QEMU is too heavy):
   - Create `day74/ta_skeleton/` with:
     - `ta/main.c` — TA entry points (template above).
     - `ta/ta.lds` — linker script.
     - `ta/Makefile` — OP-TEE build flags.
     - `host/main.c` — client that calls `TEEC_InitializeContext`, `TEEC_OpenSession`, `TEEC_InvokeCommand`.
     - `keys/ta_pub.pem`, `keys/ta_priv.pem` — demo signing keys (demo, prod = HSM).
     - `docs/architecture.md` — architecture diagram + trust boundaries.
   - Code must be syntactically valid against `tee_ta_api.h` (not runnable without OP-TEE, but reviewable).
3. **Architecture document** — write `docs/architecture.md` yourself with these sections:

   > **Hints:**
   - **Trust Boundaries**: describe the two boundaries — (1) Normal-World App → Secure-World TA via TEE Client API (threat: MitM on IPC; mitigation: OP-TEE core verifies TA signature), and (2) TA-code signature verification (threat: forged TA; mitigation: signing key must be HSM-protected).
   - **TCB (Trusted Computing Base)**: list OP-TEE core (~10k LOC), your TA code, and the bootloader (U-Boot + ATF).
   - **Attestation**: explain that the TA report contains a SHA-256 of the TA code + secure-boot-key hash, and that the remote verifier must check it against the manufacturer's public key.
   - **Known Gaps**: document Spectre variant 2 (TA build uses retpoline) and cache-timing (TA code should not branch on user-input dependencies).
4. If QEMU: load your own TA in QEMU, invoke it, observe the log output.
