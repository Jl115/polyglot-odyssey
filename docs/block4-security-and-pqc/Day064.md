# Day 64: Migration Planning

**Block:** Block 4: Security & PQC · Post-Quantum Cryptography

> **Goal of the day:** You know the phases of a PQC migration (inventory → crypto agility → hybrid → pure PQC) and can write a migration plan for a fictional company that accounts for criticality, data-confidentiality horizons, and compatibility — the output is a plan document, not code.

---

## 📖 Theory

PQC migration is **not** a "swap cipher suite" — it is a 5–15-year program with discovery, interop tests, compatibility matrices, and rollback plans. NIST + BSI recommend phase models.

### Phase 1 — Cryptographic agility (prerequisite)

Before introducing PQC, the system must be **crypto-agile**: algorithms are not hard-coded but exchangeable via configuration/provider/negotiation. Anyone who today has X25519 hard-wired in 1000 code locations cannot roll out PQC.

Indicators of missing agility: hardcoded algorithm strings, calling `rsa::sign()` directly instead of a `signer::trait` abstraction, no algorithm IDs in the protocol.

### Phase 2 — Inventory (crypto census)

Where is crypto used? List everything: TLS endpoints, storage at-rest, code signing, JWT signatures, internal API auth, backup encryption. Per entry:

- **Algorithm** (X25519, RSA-2048, AES-256-GCM…)
- **Key location** (KMS, file, HSM)
- **Data-confidentiality horizon** (data that must stay secret for 30 years → highest priority; transient session → lowest)
- **Exposure** (public internet, internal-only, embedded)

Tooling: `tls-attacker` scans, `crypto-audit` scripts, `sbom` (Day 66) for libraries.

### Phase 3 — Roll out hybrid

Start with **hybrid X25519MLKEM768** for all TLS endpoints that are public. Compatible with classical clients (they ignore the PQC extension). Low risk.

### Phase 4 — Pure PQC (cautiously)

Longer term: pure PQC certificates (ML-DSA) for internal systems where you control both endpoints. For external: stay on hybrid longer until the ecosystem matures.

### Phase 5 — Sunset classical

When PQC is established, remove classical (attack-surface reduction). But a long transition phase — ensure downgrade protection.

### Why this matters

"Harvest now, decrypt later" forces **prioritization by confidentiality horizon**, not by convenience. Data with a >20-year horizon (health records, IP, diplomatic cables) must get PQC **now**, because today's TLS traffic is being recorded. Companies that ignore this will have a data leak in 15 years from today's traffic.

### The Mosca model (when must you migrate?)

Mosca's question: **When must you migrate, if data must stay secret for X years, quantum computers arrive in Y years, and migration takes Z years?**

```text
Migration needed when:  X + Z > Y   (data horizon + migration duration > quantum-computer arrival time)
                        ──────────────────────────────────────
                        Data recorded today → still sensitive in X years
                        Quantum computer real in Y years
                        Migration takes Z years
```

Example: IP data with a 20-year horizon (X=20), quantum computer in 15 years (Y=15), migration 5 years (Z=5): 20+5 > 15 → migrate today.

### Pitfalls

- **"We use TLS 1.3 with X25519, that's post-quantum-secure"** — wrong, X25519 is *not* PQC-secure, TLS 1.3 is only the vehicle.
- **Skipping crypto agility** and implementing hybrid directly → you have to rebuild everything at the next algorithm switch.
- **Forgetting long-lived signatures** — root CAs are valid 10–25 years; a root certificate issued today with RSA-2048 will still be in circulation in 2040, but then quantum-attackable.
- **Ignoring interop tests** — PQC TLS breaks with middleboxes that strip ClientHello extensions. A real showstopper in enterprise networks; test with real middlebox-vendor setups.
- **No rollback plan** — if the PQC implementation has a bug, you must be able to fall back to classical quickly. Feature flags, not hard-wired.

## 🛠️ Practice

**Task:** Write a PQC migration plan for a fictional company "Acme Health" (hospital IT) with: 3 public web apps, 50 internal microservices, 1000 IoT patient devices, 10-year archive data. Output: `migration-plan.md`.

**Step by step:**

1. Create `docs/migration-plan.md` with these sections:
   > **Required sections (you write the content — no template to copy):**
   > - **1. Scope & Inventory** — a table with columns: Asset | Algorithm | Key-Location | Confidentiality-Horizon | Exposure. Populate it for patient-portal, IoT heart monitors, code-signing, and the rest (≥10 entries).
   > - **2. Crypto-Agility Status** — per system component, mark whether algorithms are exchangeable via config/provider (✅) or hard-coded (❌). TLS via rustls is agile; hardcoded JWT signing is not.
   > - **3. Mosca Analysis** — a table with columns: Asset-Category | X (Horizon) | Z (Migration) | Y (Quantum) | Action. Apply the rule `X + Z > Y` → "migrate today".
   > - **4. Phase Roadmap** — numbered phases with time windows: (1) establish crypto agility + finish inventory, (2) hybrid TLS for public endpoints, (3) ML-DSA code signing + internal PQC, (4) sunset classical.
   > - **5. Risks** — list the top risks: legacy IoT crypto, middleboxes stripping PQC extensions, vendor support gaps, rollback strategy per endpoint.
2. Per inventory entry: a Mosca assessment.
3. Identify the **three** most critical migration items (highest X+Z-Y delta) and justify.
4. Define a **rollback config flag** per endpoint (e.g. `tls.pqc = "hybrid" | "classic" | "pqc"`).

**Definition of Done (DoD):**

- [ ] `migration-plan.md` with an inventory table ≥10 entries.
- [ ] Mosca table with ≥5 categories, each X/Z/Y/Action.
- [ ] At least 3 entries marked "migrate today" with justification.
- [ ] Crypto-agility status assessed per system component (✅/❌).
- [ ] Rollback strategy defined per endpoint (feature flag, not hard-wired).
- [ ] You can explain in 2 sentences why "harvest now, decrypt later" dictates the urgency.
- [ ] Commit: `git commit -m "day64: pqc migration plan (mosca, agility, roadmap)"`.

**Extension (optional):** Write a **crypto-agility audit script** (shell/Rust) that scans a code repo for hardcoded algorithm strings (`rsa::`, `ecdsa::`, `x25519::`) and marks each finding as `agile ❌` — the basis for phase-1 work.
