# Day 58: Key Management & HSMs

**Block:** Block 4: Security & PQC · Crypto Fundamentals

> **Goal of the day:** You know the life phases of a key (generation → distribution → rotation → destruction), know when an HSM / KMS / TPM is the right choice, and can implement an envelope-encryption scheme in Rust that keeps large amounts of data secure at rest.

---

## 📖 Theory

The strongest AES-256-GCM implementation is useless if the key lives in `config.yaml` in git. **Key management** is often the weakest point — not the algorithm. A key goes through phases:

1. **Generation** — with a cryptographically secure RNG (`OsRng`, `/dev/urandom`), *never* `rand::thread_rng()` for production keys.
2. **Distribution** — to the user without leaking (asymmetric, HSM-wrapped, or KMS API).
3. **Storage** — never in cleartext on disk; HSM/TPM/KMS or envelope encryption.
4. **Usage** — minimal exposure, in memory only as briefly as possible.
5. **Rotation** — regularly and on suspicion; archive old keys for decrypting legacy data.
6. **Destruction** — secure deletion (not just `unlink`, but overwrite + destroy in HSM).

### The three "protection" tiers

| Tier | Where is the key | Protects against | Example |
| --- | --- | --- | --- |
| **Software** | file/env | no, only policy | `.env` — *dev only* |
| **KMS** (Key Management Service) | behind an API, never exportable | disk leak, but not memory dump of the KMS | AWS KMS, GCP KMS, Vault Transit |
| **HSM** (Hardware Security Module) | in the chip, non-exportable | memory dump, since the key never leaves the chip | YubiHSM2, AWS CloudHSM, Thales |
| **TPM** | chip on the device, attested | local software attacks | Windows BitLocker |

### Envelope encryption — the workhorse pattern

Per file a **DEK (Data Encryption Key)** that encrypts the data; this DEK is wrapped with the **KEK (Key Encryption Key)** from the KMS → you store only `(ciphertext, wrapped_dek)`. Advantage: the KMS never sees GB of data (expensive per API call), and the DEK rotates per file for free.

```text
┌──────────────────────────────┐
│ KMS / HSM (KEK never exfiltrable) │
└──────────────┬───────────────┘
               │ KMS.Encrypt(KEK, DEK) / KMS.Decrypt(KEK, wrapped)
┌──────────────▼───────────────┐
│ Application (briefly in RAM)     │
│   DEK → AES-256-GCM(file)        │
└──────────────┬───────────────┘
               │ ciphertext + wrapped_dek land in DB/S3
```

### Rotation — versioning instead of deletion

Keys get versions (`v1`, `v2`…). New encryption uses the latest version; old ciphertexts carry a version tag so the decryptor knows which version to invoke. This way you can rotate without re-encrypting the entire database.

### Why this matters

About 90% of real crypto incidents are key-management failures (key in git, key in logs, key not rotated after personnel changes), not algorithm breaks. Cloud KMS design is an everyday task for security engineers; envelope encryption is the standard for every cloud-encrypted-at-rest feature.

### Pitfalls

- **`rand::thread_rng()` instead of `OsRng`** for keys — the PRNG seed can be guessed. For crypto always use `rand::rngs::OsRng` / `ring::rand::SystemRandom`.
- **Keys in memory** are not automatically zeroed after drop — Rust only zeroes `Zeroizing` wrappers (`zeroize` crate), otherwise a memory dump can find them.
- **HSM "backup"**: exporting keys from a FIPS 140-3 Level 3 module contradicts its certification — instead wrap-keys are exported encrypted with *other* HSM keys (M-of-N).
- **AWS IAM `kms:Decrypt` without `Condition`**: if every IAM principal can decrypt, you have no isolation — restrict with resource policies.
- **Don't abuse KMS as a "free encryption API"** — one call per 4 KB is expensive and slow. Envelope encryption is the way.

## 🛠️ Practice

**Task:** Implement envelope encryption in Rust: a local mock KMS (KEK in memory, generated with `OsRng`) encrypts files via a DEK, storing `wrapped_dek` alongside the ciphertext. Rotation as a bonus.

**Step by step:**

1. Project + dependencies:

   ```toml
   [dependencies]
   aes-gcm = "0.10"
   rand = "0.8"
   zeroize = { version = "1", features = ["zeroize_derive"] }
   serde = { version = "1", features = ["derive"] }
   serde_json = "1"
   base64 = "0.22"
   ```

2. Core logic (`src/main.rs`):
   > **Hints:**
   > - Define a `Kms` struct holding a `[u8; 32]` KEK; generate it with `rand::rngs::OsRng.fill_bytes` (never `thread_rng` for keys). `wrap` encrypts the DEK with AES-256-GCM under the KEK (nonce || ct), `unwrap` reverses it.
   > - `encrypt_file`: generate a fresh DEK with `OsRng`, AES-256-GCM encrypt the plaintext under the DEK, then `kms.wrap(&dek)` to get the `wrapped_dek`. Call `dek.zeroize()` immediately after wrapping.
   > - Serialize the output as JSON with `serde_json`: fields `wrapped_dek`, `nonce`, `ct` — all `base64`-encoded. No cleartext DEK should ever touch disk.
   > - For `decrypt_file`: load the JSON, `kms.unwrap` the wrapped DEK, then AEAD-decrypt. Import the `Zeroize` trait and call `.zeroize()` on the DEK and session key once decryption is done.
3. CLI with `encrypt <file>` / `decrypt <file>`, persist the KEK in `~/.day58-kek` (demo only — prod would be a KMS API).
4. Roundtrip: encrypt → decrypt → `sha256sum` identical.
5. **Memory hygiene check**: build a small test that searches the stack for the `dek` variable via an `unsafe` pointer after `encrypt_file` — empty with `zeroize`, still present without `zeroize` (demo only, not a production test).

**Definition of Done (DoD):**

- [ ] `cargo build` without warnings; all crypto randomness via `OsRng`.
- [ ] `sha256sum` original vs. decrypt output identical.
- [ ] DEK is wiped with `zeroize` after wrapping (`zeroize` crate in use).
- [ ] No cleartext DEK on disk, only `wrapped_dek` (`grep -a DEK file.json` empty).
- [ ] You can explain in 2 sentences why you do *not* make a KMS call per file (cost/latency + DEK exposure).
- [ ] Commit: `git commit -m "day58: envelope encryption with mock kms"`.

**Extension (optional):** Implement **key versioning** — `Kms` holds a `HashMap<Version, KEK>`, the ciphertext header carries `key_version`, rotation creates a new version, the old one remains for decryption.
