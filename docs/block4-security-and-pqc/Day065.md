---

## 📖 Theory

This mini-capstone consolidates Day 56, 58, 61, 63 into one binary. It is the "drop-in" version of PQC migration for file encryption — a realistic building block a migration engineer could ship.

### CLI design

```text
pqc-tool keygen [--out <dir>]                    # generates keypub.bin / keysec.bin
pqc-tool encrypt <file> --pubkey keypub.bin      # → <file>.pqc (hybrid PQC)
pqc-tool decrypt <file>.pqc --seckey keysec.bin  # → <file>
```

### `.pqc` file format (binary, versioned)

```text
+------------+-------------+----------------+----------+----------+------------------+
| magic (4B) | version (1B)| x25519_pub (32B)| kem_ct   | nonce (12B)| aead_ct + tag   |
| "PQC1"     | 0x01        |                | (1088B)  |          | (rest)           |
+------------+-------------+----------------+----------+----------+------------------+
```

- **magic + version**: forward-compatible; the parser can reject or convert old files.
- **x25519_pub**: classical public key of the recipient (static in the demo; in production ephemeral + cert).
- **kem_ct**: ML-KEM-768 ciphertext (~1088 bytes).
- **AEAD**: AES-256-GCM, nonce + ciphertext + tag.

### Security model

- **Hybrid**: classical + PQC shared → HKDF → AES key. An attacker must break **both**.
- **At-rest**: files can be archived; the recipient secret key is long-term (not ephemeral).
- **Not covered** (accepted): sender authenticity (who encrypted) is missing — that would be a signature (Day 67). For this tool only confidentiality.

### Why a mini-capstone here?

Small, finished tools with a clear CLI are the realistic output of an "I learned PQC" engineer. It shows that you can not only do theory but produce a **shippable binary** with a format spec, tests, README. That is the difference between tutorial knowledge and engineering output.

### Pitfalls

- **Key files readable in git** — `keysec.bin` MUST be in `.gitignore` (Day 68 SLSA topic).
- **Ignoring the version byte** — reading older `.pqc` files with a newer binary → either stay compatible or clearly reject with an error, never "accidentally" decrypt.
- **Hardcoded HKDF info string** — `b"hybrid-v1"`; change on version change (v2), otherwise cross-protocol attacks.
- **No `zeroize` on secret keys after loading** — a memory dump leaks them.
- **Buffer sizes**: ML-KEM-768 CT is ~1088 bytes; use static arrays (`[u8; 1088]`) instead of `Vec` for stack/heap clarity.

## 🛠️ Practice

**Task:** Implement `pqc-tool` as a Rust binary with three subcommands, a roundtrip test, and a tamper test. Extend Day 63's code into a real CLI.

**Step by step:**

1. Project + deps (`Cargo.toml`):

   ```toml
   [package]
   name = "pqc-tool"
   version = "0.1.0"
   edition = "2024"

   [dependencies]
   clap = { version = "4", features = ["derive"] }
   x25519-dalek = "2"
   pqcrypto-kyber = { version = "0.8", features = ["kyber768"] }
   pqcrypto-traits = "0.3"
   hkdf = "0.12"
   sha2 = "0.10"
   aes-gcm = "0.10"
   rand = "0.8"
   zeroize = { version = "1", features = ["zeroize_derive"] }
   anyhow = "1"
   ```

2. CLI struct:
   > **Hints:**
   > - Use `clap` with the `derive` feature. Annotate an `enum Cli` with `#[derive(clap::Parser)]`.
   > - Three variants: `Keygen` (optional `--out` path), `Encrypt` (positional `file` + `--pubkey` path), `Decrypt` (positional `file` + `--seckey` path). Each path field is `std::path::PathBuf`; use `#[arg(long)]` for the flag options.
   > - `keygen`: generate a static `(x25519_secret, kyber768_secret)` pair; write `keypub.bin` as `x25519_pub || kyber_pub` and `keysec.bin` as the concatenated secret. Set the secret file to `chmod 600`.
   > - `encrypt`/`decrypt`: load the relevant key, then reuse Day 63's hybrid flow — ephemeral X25519 + ML-KEM encapsulate, HKDF(`b"hybrid-v1"`) → AES-256-GCM. Write/read the `.pqc` frame per the format spec above (magic `PQC1`, version, x25519_pub, kem_ct, nonce, aead_ct). `zeroize()` secrets after use.
3. `keygen`: generates `(x25519_static_secret, kyber768_secret)` and writes `keypub.bin` (concat: x25519_pub | kyber_pub) and `keysec.bin`. Secret-key file with `chmod 600`.
4. `encrypt`: loads the recipient public, does ephemeral X25519 + ML-KEM encapsulate, HKDF → AES-256-GCM, writes the `.pqc` frame per the spec above.
5. `decrypt`: loads the secret key, extracts x25519_pub + kem_ct from the frame, does DH + decapsulate, HKDF, AEAD decrypt.
6. Tests:

   ```bash
   cargo run -- keygen --out keys/
   echo "top secret" > msg.txt
   cargo run -- encrypt msg.txt --pubkey keys/keypub.bin
   cargo run -- decrypt msg.txt.pqc --seckey keys/keysec.bin
   diff msg.txt msg.txt.dec
   # tamper:
   dd if=/dev/urandom of=msg.txt.pqc bs=1 count=1 seek=50 conv=notrunc
   cargo run -- decrypt msg.txt.pqc --seckey keys/keysec.bin  # → error
   ```

7. README `day65/README.md` with CLI docs, format spec, security model, known limitations.

**Definition of Done (DoD):**

- [ ] `cargo run -- keygen/encrypt/decrypt` works; roundtrip `diff` is empty.
- [ ] `keysec.bin` is in `.gitignore` and has `chmod 600` (verifiable with `ls -l`).
- [ ] `.pqc` frame starts with the `PQC1` magic (visible with `xxd file.pqc | head -1`).
- [ ] Tampered file → decrypt fails, no panic, no silent partial.
- [ ] Secret keys are `zeroize()`d after use (code inspection).
- [ ] README contains the format spec + security-model list.
- [ ] You can explain in 2 sentences how this tool *concretely* supports PQC migration (file at-rest with hybrid).
- [ ] Commit: `git commit -m "day65: pqc-tool mini-capstone (hybrid kem + aead cli)"`.

**Extension (optional):** Add `pqc-tool sign <file> --seckey …` and `verify` (ML-DSA / Dilithium3) — this adds sender authenticity that the base tool lacks. Anticipates Day 67.
