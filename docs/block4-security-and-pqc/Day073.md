# Day 73: Hardware-Security: ARM MTE

**Block:** Block 4: Security & PQC · Hardware-Security

> **Goal of the day:** You understand **ARM Memory Tagging Extension (MTE)** as a hardware-based memory-safety mechanism, know how it detects use-after-free / buffer-overflow in a running program, and can build a small C program so that MTE catches a bug that ASan (software) only finds with high overhead.

---

## 📖 Theory

Memory-safety bugs (use-after-free, out-of-bounds, double-free) make up ~70% of all CVEs in C/C++. Software solutions like **ASan** (Address Sanitizer, 2× memory overhead, ~2× slowdown) are only usable for tests. Hardware solutions promise detection in production with <5% overhead. ARM MTE (Cortex-A from v8.5, 2018) is the first broadly available hardware memory safety.

### How MTE works — tagging

ARMv8.5 introduces 4-bit tags per 16-byte granule. Every memory region gets a random 4-bit tag (0–15). Pointers carry the same tag in their top 4 bits (TBI = Top-Byte-Ignore). Before every read/write access the CPU compares the pointer tag with the memory tag — if they do not match → trap (SIGSEGV with `SEGV_MTEAERR`).

```text
┌──────────────────────────┐     ┌──────────────────────────┐
│ Pointer 0x0A0040_XXXX    │     │ Memory @ 0x0040_XXXX      │
│  Tag = 0xA (top nibble)  │     │  Tag in Metadata = 0xA    │  ← match ✅
└──────────────────────────┘     └──────────────────────────┘

After free: Memory-Tag = 0xB (a different random tag)
┌──────────────────────────┐     ┌──────────────────────────┐
│ Dangling ptr 0x0A0040_XX  │     │ Memory Tag = 0xB          │  ← mismatch ❌
│  Tag = 0xA                │     │  (changed by free)        │
└──────────────────────────┘     └──────────────────────────┘
   → access → SIGSEGV (MTE-AERR)
```

### MTE modes

| Mode | Behavior | Use case |
| --- | --- | --- |
| **Synchronous** | Immediate trap on mismatch | Debug — precise bug localization |
| **Asynchronous** | Trap before the next syscall | Production — performance |
| **Asymmetric** | Read sync, write async | Compromise |

In production mostly async — the CPU collects "tag failures" and signals at the next syscall entry. Performance overhead ~5%, memory overhead ~3% (1 bit per 16-byte granule).

### What MTE detects

- **Use-after-free**: free sets the tag to a new (different) value → dangling-pointer mismatch.
- **Out-of-bounds buffer overflow** (granule-aligned, 16-byte): the neighbor tag is different.
- **Stack-buffer-overflow**: stack-frame tags differ between frames.
- **Double-free**: after the first free the tag is different → second free mismatches.

### What MTE does *not* detect

- **Sub-granule overflows** (within 16 bytes) — granularity is limited.
- **Type confusion** (correct tag, wrong type).
- **Init bug**: accesses to uninitialized memory with a coincidentally matching tag.

### MTE vs. ASan vs. Rust

| Mechanism | Where | Overhead | Detected | Production-ready |
| --- | --- | --- | --- | --- |
| ASan (Clang) | Software, compiler | 2–3× mem, 2× slow | UAF, OOB, sub-granule | no (debug only) |
| **MTE** | Hardware (ARM) | ~5% | UAF, OOB ≥16B | yes |
| Rust ownership | Compiler | 0 | all memory safety | yes (only Rust code) |

MTE is complementary: for legacy C/C++ code (e.g. OpenSSL, libxml2) that you cannot port to Rust. Rust code does not benefit (it does not need MTE).

### Why this matters

Google rolled out MTE for Pixel Android (2021+) and reduced memory-safety CVEs by ~75% for MTE-tagged components. Apple's M-Macs have it (M1+) as well. Chrome uses it for the renderer. Hardware memory safety is the next line of defense for C/C++ code you cannot get rid of — and complementary to Rust (which prevents such bugs in the compiler already).

### Pitfalls

- **Sub-granule bug escapes** — 16-byte granularity lets bugs within 16 bytes through. For precise detection you need HWASan (ARM v8.3, a different technique).
- **Tag collision** (1/16 probability) — an attacker can coincidentally have a matching tag → bug not detected, only probabilistically.
- **Async mode loses bug localization** — the stacktrace shows only "sometime in the last syscall interval", not the exact line. Production triage is hard.
- **Only on ARM v8.5+** — Intel x86 has no equivalent (Intel LAM is only ASLR, not MTE).
- **Libraries must be built with `-fsanitize=mte`** — MTE is not transparent for old code; you need a rebuild.

## 🛠️ Practice

**Task:** Enable MTE on an ARM Mac or Linux-aarch64 (Raspberry Pi 5, Graviton), write a small C program with a use-after-free, and observe how MTE (async mode) catches the bug in a syscall. If no MTE hardware is available → simulate with ASan and compare.

**Step by step:**

1. Hardware check:
   ```bash
   uname -m                # aarch64?
   cat /proc/cpuinfo | grep -o 'mte' | head -1   # Linux: MTE support?
   # macOS: sysctl machdep.cpu | grep MTE  (not yet stable)
   ```
2. If MTE is available (Linux/Graviton/Pi5):
   ```bash
   # C code with use-after-free
   cat > day73.c <<'EOF'
   #include <stdlib.h>
   #include <stdio.h>
   #include <string.h>

   int main() {
       char *p = malloc(32);
       strcpy(p, "secret");
       free(p);
       // Use-after-free:
       printf("UAF: %s\n", p);   // MTE traps here
       return 0;
   }
   EOF
   # Compile with MTE
   clang -arch arm64 -fsanitize=memtag -march=armv8.5-a+memtag day73.c -o day73
   PRCTL_MTE_MODE=async ./day73
   # Expected: SIGSEGV with si_code = SEGV_MTEAERR (asynchronous)
   ```
3. If no MTE hardware → use ASan (software equivalent):
   ```bash
   clang -fsanitize=address day73.c -o day73_asan
   ./day73_asan
   # → ASAN report with stacktrace, "heap-use-after-free"
   ```
4. Compare in `docs/mte-vs-asan.md`:
   - Overhead: ASan 2× slowdown; MTE 5% (literature).
   - Precision: ASan exact; MTE async imprecise (syscall interval).
   - Production-ready: MTE yes; ASan no.
5. Read [Google's Pixel-MTE blog post](https://security.googleblog.com/2023/08/memory-tagging-and-beyond.html) and note the ~75% CVE reduction.

- [ ] Either MTE is enabled and the C program traps with `SEGV_MTEAERR` (or, if no MTE hardware, an ASan report "heap-use-after-free").

- [ ] You name at least 3 bug classes MTE detects, and 2 it does not detect.
