# Day 62: liboqs & OpenSSL Provider

**Block:** Block 4: Security & PQC · Post-Quantum Cryptography

> **Goal of the day:** You have installed `liboqs` and the `oqs-provider` for OpenSSL, can generate PQC certificates with `openssl`, and perform a TLS 1.3 handshake with `X25519Kyber768` (or `dilithium3`) against a local server — i.e. PQC in the toolchain, not just on paper.

---

## 📖 Theory

`liboqs` is the reference C library for PQC algorithms (Open Quantum Safe), maintained by the OQS project. To get PQC into existing infrastructure, there are two paths:

### Path A — OpenSSL Provider (`oqs-provider`)

OpenSSL 3+ has a **provider architecture**: algorithms come from dynamically loadable modules. `oqs-provider` plugs in ML-KEM / ML-DSA / SLH-DSA as additional algorithms, so `openssl`, `nginx`, `curl` (with OpenSSL) speak PQC without code changes.

```text
OpenSSL core ── loads ──> oqs-provider.so ── calls ──> liboqs.so ──> ML-KEM / ML-DSA
```

Provider strings in the CLI:
- `OPENSSL_CONF=openssl-oqs.cnf` activates PQC suites.
- Certificates: `openssl req -new -x509 -newkey dilithium3 -keyout …` generates an ML-DSA certificate.

### Path B — liboqs directly (Rust bindings)

For applications without OpenSSL: `liboqs-rust` (official bindings) or `pqc_crypto` crates. Direct C-ABI call, smaller, but you build TLS yourself (not recommended for production — prefer `rustls` with a PQC provider).

### TLS 1.3 PQC hybrid suites (IETF draft)

The IETF draft `draft-ietf-tls-hybrid-design` defines named groups:
- `x25519_kyber768` (old Cloudflare variant, deprecated)
- `X25519MLKEM768` (standardized 2024–2025) — this is the currently recommended hybrid group.

The handshake stays the same as in Day 57, except that the `key_share` extension now contains *two* public keys (X25519 + ML-KEM-768) and the shared secret is the concatenation of both bilaterally derived secrets.

### Why a provider and not the library directly?

Providers enable **drop-in migration** — existing tools (`openssl`, `nginx`, `curl`, `haproxy`) gain PQC without recompiling. That is why OpenSSL 3 is the standard vector for broad PQC rollout.

### Pitfalls

- **oqs-provider is academic**, not FIPS-certified — for production only in hybrid mode and with a risk assessment.
- **Provider order in `openssl.cnf`**: if `default` comes before `oqs`, classical algorithms can shadow PQC tests. Check the config file.
- **Certificate chain length** — ML-DSA certificates are ~2–3 KB (vs. RSA 2048 ~1 KB); TLS handshake packets can blow up the MTU → fragmentation, performance issues.
- **liboqs API is unstable** — version jumps break the ABI. Pin the version.
- **Constant-time not guaranteed** — `liboqs` is not side-channel-resistant by default. Production needs hardened implementations (e.g. AWS's `aws-lc` with PQC).

## 🛠️ Practice

**Task:** Install `liboqs` + `oqs-provider` (or use the official Docker image) and generate an ML-DSA-certificate-based TLS server that you connect to with `openssl s_client` against `dilithium3`.

**Step by step:**

1. **Build liboqs + oqs-provider** (Linux/macOS). Fastest path: official Docker image.
   ```bash
   docker pull openquantumsafe/openssl3:latest
   docker run -it --rm -p 4433:4433 openquantumsafe/openssl3:latest
   # inside the container:
   openssl list -providers         # shows "oqsprovider"
   openssl list -signature-algorithms | grep -i dilithium
   ```
2. **Generate a PQC certificate** (inside the container):
   ```bash
   openssl req -x509 -new -newkey dilithium3 -keyout dilithium3.key -out dilithium3.crt -nodes -subj "/CN=localhost" -days 30
   openssl x509 -in dilithium3.crt -noout -text | grep -E "Signature Algorithm|Public Key Algorithm"
   # → Signature Algorithm: dilithium3
   ```
3. **Start a PQC TLS server**:
   ```bash
   openssl s_server -cert dilithium3.crt -key dilithium3.key -www -accept 4433 \
     -groups dilithium3 -tls1_3
   ```
4. **Connect from a second terminal**:
   ```bash
   docker exec -it <id> openssl s_client -connect localhost:4433 -groups dilithium3 -tls1_3
   # Output: Peer signature type: dilithium3, Protocol=TLSv1.3
   ```
5. **Hybrid variant** — replace `-groups dilithium3` with `-groups x25519_kyber768` (or `X25519MLKEM768`) and observe that the handshake now has *two* key shares in the ClientHello extension.

**Definition of Done (DoD):**

- [ ] `openssl list -providers` shows `oqsprovider` as loaded.
- [ ] Generated certificate shows `Signature Algorithm: dilithium3` in `openssl x509 -text`.
- [ ] `openssl s_client` connection to the local PQC server shows `Peer signature type: dilithium3` (or hybrid group).
- [ ] You noted the public-key size of the ML-DSA certificate in bytes (e.g. `wc -c dilithium3.crt`).
- [ ] You can explain in 1 sentence why OpenSSL 3 providers make PQC migration so simple (drop-in).
- [ ] Commit: note the setup in `README.md` under `day62/`; `git commit -m "day62: liboqs + oqs-provider tls 1.3 pqc handshake"`.

**Extension (optional):** Configure `nginx` with `ssl_provider oqsprovider;` and `ssl_ecdh_curve X25519MLKEM768;` and measure the handshake overhead vs. pure X25519 (`openssl s_time -connect`).
