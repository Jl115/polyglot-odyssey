# Day 70: Mini-Capstone: Secure Pipeline

**Block:** Block 4: Security & PQC · Supply Chain Security

> **Goal of the day:** You build an end-to-end hardened release pipeline for `pqc-tool` that unites all Block 4 components: SBOM (66), Sigstore signature (67), SLSA provenance (68), zero-trust CI (69), and a verification script that a third party can run to independently check the entire trust chain.

---

## 📖 Theory

This mini-capstone is the integration of all the supply-chain parts so far into a pipeline that an independent verifier can check without any further trust assumption — only with public keys and public logs. This is the industry gold standard (Kubernetes, npm, PyPA practice similarly).

### The full trust chain

```text
[Source git commit]
        │
        ▼
[GH Actions Runner] ── oidc ──> [Fulcio CA] (10-min cert)
        │                            │
        │  cargo build --release ──  │
        │  --locked --offline        │
        │                            │
        │  syft sbom (CycloneDX)      │
        │  grype scan → VEX           │
        │  cosign sign-blob           │
        │  cosign attest (SLSA)        │
        │                            ▼
        │                       [Rekor Log]  (public, append-only)
        ▼
[GitHub Release]
   ├── pqc-tool (binary)
   ├── pqc-tool.sig (cosign bundle)
   ├── pqc-tool.intoto.json (SLSA attestation)
   ├── sbom.cyclonedx.json
   └── security-report.md
        ▲
        │ verify
[Third-party Verifier]
   1. cosign verify-blob --certificate-identity your@email --oidc-issuer github \
        --bundle pqc-tool.sig pqc-tool
   2. gh attestation verify pqc-tool --repo your-org/pqc-tool \
        --predicate-type https://slsa.dev/provenance/v1
   3. grype sbom:cyclonedx-json --file sbom.cyclonedx.json  → 0 criticals
   4. Rekor log lookup of the cert serial (transparency)
```

### Defense in depth — the 5 layers

| Layer | Protection | Tool |
| --- | --- | --- |
| Source integrity | only merged via reviews, branch protection | GitHub settings |
| Build isolation | ephemeral runner, hermetic | GH-hosted, `--offline` |
| Identity binding | OIDC, Fulcio certificate | Sigstore |
| Provenance | signed attestation | SLSA + Rekor |
| Verifiability | public log, public keys | Rekor, Fulcio root |

Each layer alone does not break the system — at least two must fall together.

### Why this is a capstone

Building a hardened pipeline *and* proving with a verification script that third parties can check without trusting you is the transition from "I know tools" to "I deliver auditable security artifacts". That is what distinguishes senior security engineers from mid-level.

### Pitfalls

- **Verification script not committed** — without it no one can independently check; the script itself must live in the repo and be tested in CI.
- **Identity regexp too wide** — `--certificate-identity '*@your-domain.com'` allows every employee to sign everything. Restrict to the CI identity.
- **SBOM not signed** — an unsigned SBOM can be swapped → CVE scan falsifiable. Sign the SBOM as an attestation (`cosign attest --type cyclonedx`).
- **Rekor offline** — the verifier needs an online lookup; commit the bundle in the release asset.
- **"It runs, all good"** — a successful build is not proof of security; the verification must *actively* run and fail on mismatch.

## 🛠️ Practice

**Task:** Create `.github/workflows/secure-release.yml` (unites Day 66–69) AND a `verify-release.sh` that independently checks the entire trust chain. Simulate the build locally if no GitHub setup exists.

**Step by step:**

1. **Workflow** — create `.github/workflows/secure-release.yml` yourself (unites Day 66–69):

   > **Hints:**
   - Trigger on version tags (`on: push: tags: ['v*']`); `permissions:` needs `contents: write`, `id-token: write`, `attestations: write`.
   - Set env: `AWS_EC2_METADATA_DISABLED: "true"` and `SOURCE_DATE_EPOCH` for reproducibility.
   - Pin every `uses:` to a **commit hash** (checkout, rust-toolchain, cosign-installer, scan-action, attest-build-provenance).
   - Steps in order: checkout → install Rust → `cargo build --release --locked --offline` → `sha256sum` of the binary → generate a CycloneDX SBOM (`cyclonedx --all-features --format json`) → CVE scan with `grype`/`anchore/scan-action` → cosign `sign-blob --yes --bundle` (keyless) → `actions/attest-build-provenance@v1` for SLSA → create the GitHub release.

2. **Verification script** — write `verify-release.sh` yourself:

   > **Hints:**
   - Start with `set -eu`; accept a `VERSION` argument and define `BINARY`, `IDENTITY`, `ISSUER` variables.
   - Step 1: `cosign verify-blob` with `--certificate-identity`, `--certificate-oidc-issuer`, `--bundle`, `--certificate`, and the binary path.
   - Step 2: `gh attestation verify` with `--repo` and `--predicate-type https://slsa.dev/provenance/v1`.
   - Step 3: `grype sbom:cyclonedx-json --file sbom.cyclonedx.json`.
   - Step 4: Extract the Rekor UUID from the cosign output (grep for `uuid:`), then `rekor-cli get --uuid … | jq .`.
   - End by printing a success message — the script must **actively fail** on any mismatch.
3. **Local simulation** (if no GitHub setup): build in a hermetic Docker container, sign with a local cosign key (demo only), generate the SBOM and run `verify-release.sh` against your local artifacts.
4. **Documentation**: write `docs/secure-pipeline.md` with an architecture diagram, trust-chain description, known gaps, upgrade roadmap (e.g. "L4 via a second build service").

**Definition of Done (DoD):**

- [ ] Workflow file committed; syntax-checked with `actionlint` (`brew install actionlint && actionlint .github/workflows/*.yml`).
- [ ] `verify-release.sh` runs successfully against your (locally simulated or real) release artifacts.
- [ ] On a deliberately tampered binary, Sigstore verify fails (demonstrated in the README).
- [ ] The SBOM is in the release-artifact list.
- [ ] `docs/secure-pipeline.md` shows the trust chain as a diagram + gaps roadmap.
- [ ] You can explain to an auditor in 3 sentences how a third party without trust in you verifies the binary.
- [ ] Commit: `git commit -m "day70: secure release pipeline (sbom+sigstore+slsa+zero-trust)"`.

**Extension (optional):** Add **policy-as-code** (`cue` or `opa`) that automatically checks `verify-release.sh`'s output against rules: "identity must be in the allowlist", "SBOM must have no critical CVE", "SLSA level ≥ 3" → blocks the release on mismatch. That is the production extension.
