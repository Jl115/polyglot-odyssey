# Day 66: SBOMs & Dependency Scanning

**Block:** Block 4: Security & PQC · Supply Chain Security

> **Goal of the day:** You can generate an **SBOM (Software Bill of Materials)** in SPDX and CycloneDX format, scan dependencies for CVEs with `cargo audit`, and know why SBOMs are legally required from 2025 for US federal and EU products.

---

## 📖 Theory

Most modern CVEs are **supply-chain CVEs** — a vulnerable library deep in the dependency tree, not your own code (Log4Shell, xz-utils backdoor, left-pad). Defense: transparency over the entire supply chain.

### What is an SBOM?

An **SBOM (Software Bill of Materials)** is a machine-readable list of all components of an artifact — including transitive dependencies, licenses, versions, hashes, PURLs (package URLs). Without an SBOM you do not know that you have a vulnerable `libxml2-2.9.4` in your container.

Two dominant formats:

- **SPDX** (ISO/IEC 5962:2021) — Linux Foundation, JSON/RDF/tag-value.
- **CycloneDX** (OWASP, 1.5+) — JSON, focused on security metadata, VEX (Vulnerability Exploitability eXchange).

```json
// CycloneDX excerpt
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "components": [
    { "type": "library", "name": "openssl", "version": "3.0.12",
      "purl": "pkg:generic/openssl@3.0.12", "bom-ref": "pkg:generic/openssl@3.0.12" }
  ]
}
```

### Dependency scanning: three layers

1. **CVE scan**: `cargo audit` against the RustSec advisory DB, `npm audit`, `trivy fs .`.
2. **License compliance**: `cargo about` generates a license list — GPL in a closed-source product? Stop.
3. **Provenance**: where does the dependency come from? Rekor/Sigstore log entries (Day 67) or git-pin with hash, not `^1.2` floating.

### Legal reality

- **US Executive Order 14028** (2021) + **M-22-18** + **M-23-09**: SBOM mandatory for software delivered to US federal agencies.
- **EU Cyber Resilience Act (CRA, 2024)**: manufacturers must ensure vulnerability and component transparency; SBOMs are the standard path.
- **NTIA Minimum Elements**: component name, version, supplier, dependency relationship, SBOM author, timestamp.

### Tool map

| Language | SBOM generator | Audit |
| --- | --- | --- |
| Rust | `cargo cyclonedx`, `cargo about`, `cargo sbom` | `cargo audit` |
| Node | `cyclonedx-bom`, `npm sbom` (Node 20+) | `npm audit` |
| Container | `syft`, `trivy` | `grype`, `trivy image` |

### Why this matters

Log4Shell could have been found weeks earlier if every container image had an SBOM and a CVE feed automatically scanned against it. SBOMs are the basis for everything else in Block 4: Sigstore signing (Day 67), SLSA levels (Day 68), zero-trust pipeline (Day 69). Gaps here mean you cannot close the chain.

### Pitfalls

- **Floating version locks** (`^1.2` in `package.json`, `1.*` in Cargo) → the SBOM is stale the next day. Strict pinning + commit `Cargo.lock`.
- **SBOM without PURL** — without a package URL the component is not uniquely identifiable (e.g. "log4j" alone is ambiguous).
- **Forgetting transitive deps** — some generators list only direct deps. Always scan with `--all-features` or `--workspace`.
- **Missing VEX** — "CVE-2023-XYZ is in a dep, but not exploitable because feature X is not enabled" must be a VEX statement in the SBOM, otherwise CVE scanners are unnecessarily noisy.
- **Stale SBOM** — an SBOM is a *snapshot*. Regenerate on every build, verify in CI.

## 🛠️ Practice

**Task:** Generate SBOMs (SPDX + CycloneDX) for `pqc-tool` (Day 65), run `cargo audit`, and write a small script that matches the SBOM against a CVE feed.

**Step by step:**

1. Install SBOM tools:

   ```bash
   cargo install cargo-audit cargo-cyclonedx cargo-about
   # syft for container/filesystem:
   brew install syft grype
   ```

2. CycloneDX SBOM for `pqc-tool`:

   ```bash
   cd days/day65  # or wherever your pqc-tool lives
   cargo cyclonedx --all-features --format json --output-cdx
   # → bom.json
   jq '.components | length' bom.json   # e.g. 47 components
   jq '.components[] | .name + "@" + .version' bom.json | head
   ```

3. SPDX SBOM via `syft`:

   ```bash
   syft dir:. --output spdx-json > sbom.spdx.json
   jq '.packages | length' sbom.spdx.json
   ```

4. CVE scan:

   ```bash
   cargo audit
   # Output shows e.g. "RUSTSEC-2024-XXXX: vulnerability in crate X"
   ```

5. CVE-vs-SBOM match via `grype`:

   ```bash
   grype sbom:cyclonedx-json --file bom.json
   # or directly: grype dir:.
   ```

6. Write `scan.sh` that generates the SBOM + scans and produces a Markdown report `security-report.md`:
   > **Hints:**
   > - Start with `#!/bin/bash` and `set -e` so the script aborts on any tool failure.
   > - Call `cargo cyclonedx --all-features --format json --output-cdx` to produce `bom.json`, then `cargo audit` (redirect to a file), then `grype sbom:cyclonedx-json --file bom.json` (redirect to a file).
   > - Build `security-report.md` with a heredoc or `echo` block: a `# Security Report` header with `$(date)`, a `## SBOM` section using `jq '.components | length' bom.json`, a `## Cargo Audit` section that cats the audit output, and a `## Grype` section that cats the grype output.
   > - The script should exit non-zero if any scan reports a vulnerability, so it can gate CI later.
7. Deliberately add a vulnerable dep (`Cargo.toml`: `openssl = "=0.10.40"`, a version with a known RUSTSEC), run `scan.sh` — see how it lands in the report.

**Definition of Done (DoD):**

- [ ] `bom.json` (CycloneDX) and `sbom.spdx.json` (SPDX) generated, both validatable with `jq`.
- [ ] `cargo audit` shows 0 vulnerabilities for your project (or justified VEX statements).
- [ ] `grype` output shows components + any matches.
- [ ] `scan.sh` runs end-to-end and produces `security-report.md`.
- [ ] Every component in the SBOM has a `purl` field (verifiable with `jq '.components[].purl' bom.json`).
- [ ] You can explain in 2 sentences why an SBOM is needed for EU-CRA-conformant products.
- [ ] Commit: `git commit -m "day66: sbom (spdx+cyclonedx) + cargo audit + grype pipeline"`.

**Extension (optional):** Write a **VEX document** (`vex.json`) for a found CVE that explains why it is not exploitable (e.g. "function is not called"). Grype can consume VEX to suppress false positives.
