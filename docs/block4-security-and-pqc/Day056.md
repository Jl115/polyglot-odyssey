# Day 56: Symmetric vs Asymmetric Crypto

**Block:** Block 4: Security & PQC · Crypto Fundamentals

> **Goal of the day:** You can cleanly distinguish between symmetric and asymmetric cryptography, know the current "go-to" algorithms for each (AEAD, Ed25519, X25519, BLAKE3), and can encrypt and restore a file in Rust with AES-256-GCM — with integrity verification.

---

## 📖 Theory

Cryptography solves three problems: **confidentiality** (only the recipient may read), **integrity/authenticity** (the message was not altered and comes from the claimed sender), and **non-repudiation** (the sender cannot later deny having sent it). Different building blocks cover these differently.

### Symmetric cryptography — one key for both sides

Sender and receiver share **the same secret key**. Fast (~GB/s), but the key-exchange problem remains unsolved — how do you get the key securely to the recipient?

- **Block ciphers** (e.g. AES) alone are *insecure* — identical plaintext blocks produce identical ciphertext blocks → patterns are visible.
- **AEAD (Authenticated Encryption with Associated Data)** combines encryption + MAC in one step: ciphertext + tag. It optionally authenticates "associated data" (e.g. headers) in cleartext.
  - **AES-256-GCM** — the standard, hardware-accelerated (AES-NI), ~3–5 GB/s.
  - **ChaCha20-Poly1305** — software-optimized, constant-time, often faster on devices without AES-NI. Preferred as a fallback in TLS 1.3.
- **Nonce/IV**: **never reuse** with the same key — otherwise security breaks completely (XOR of two ciphertexts = XOR of the plaintexts). 96-bit for GCM; either a counter or random.

### Asymmetric cryptography — two keys, public/private

Everyone has a **key pair**: public key (distributable) + private key (secret). Solves the exchange problem and enables signatures.

- **Key agreement / KEM** (key exchange): X25519 (Elliptic-Curve Diffie-Hellman / Curve25519) — modern, fast, security-equivalent to ~3000-bit RSA.
- **Signatures**: **Ed25519** (Edwards curve) — deterministic, fast, small signatures (64 bytes), resistant to nonce leaks (unlike ECDSA). RSA-PSS still widespread, but requires 2048+ bits.
- **Hash functions**: SHA-256 (proven), SHA-3 (Keccak, different construction), **BLAKE3** (very fast, parallelizable, XOF).

### The combination — hybrid encryption

In practice (TLS, GPG, age): exchange asymmetrically → derive a shared symmetric key → encrypt symmetrically. Best of both worlds.

```text
Alice                            Bob
  |--- X25519(PublicA) --------->|
  |<-- X25519(PublicB) ----------|
  both sides: HKDF(ECDH-Shared) => 32-byte session key
  |===== AES-256-GCM(sessionkey) =====>  (many GB, fast)
```

### Why this matters

Asymmetric crypto is ~1000× slower than symmetric — so never encrypt large amounts of data directly with RSA. Hybrid is the foundation of TLS, SSH, Signal, age. Anyone who has not understood this relationship builds inefficient or insecure systems.

### Pitfalls

- **"Don't roll your own crypto."** Always use vetted libraries (RustCrypto, ring, OpenSSL). Home-made AES is almost always timing-vulnerable.
- **Nonce reuse** with GCM is *catastrophic* — it leaks the hash key and allows ciphertext modification. Count strictly upward for counter nonces; for random nonces mind the 96-bit collision probability.
- **RSA without OAEP/PSS** (i.e. "textbook RSA") is insecure — padding-oracle attacks (Bleichenbacher).
- **ECDSA with nonce reuse** → private key recovered (PS3 hack 2010). Ed25519 avoids this via deterministic nonces.
- **SHA-1 is dead** (Shattered 2017) — use only SHA-256+/SHA-3/BLAKE3.

## 🛠️ Practice

**Task:** Build a small file encryptor in Rust with **AES-256-GCM** that encrypts a file (`*.enc`) and decrypts it again, with an integrity check via SHA-256.

**Step by step:**

1. Create the project: `cargo new day56 --bin` and in `Cargo.toml`:

   ```toml
   [dependencies]
   aes-gcm = "0.10"
   sha2 = "0.10"
   rand = "0.8"
   hex = "0.4"
   ```

2. Encryption logic (`src/main.rs` core):
   > **Hints:**
   > - Use `Aes256Gcm` from the `aes-gcm` crate; bring in the `Aead` and `KeyInit` traits. Construct the cipher with `Key::<Aes256Gcm>::from_slice(key)`.
   > - Generate a fresh 12-byte nonce per encryption with `rand::thread_rng().fill_bytes(&mut nonce_bytes)` — 96 bits is the GCM nonce size; **never reuse** it with the same key.
   > - `encrypt_file`: call `cipher.encrypt(nonce, plain)`, then build the output as `nonce_bytes || ct` (the nonce is not secret; the AEAD ciphertext already includes the 16-byte tag at the end).
   > - `decrypt_file`: `split_at(12)` the blob to recover the nonce and ciphertext, then `cipher.decrypt(...)`. On a tampered tag this returns an error — propagate it so the CLI aborts rather than emitting partial plaintext.
3. CLI wrapper: arguments `enc <file>` / `dec <file> <key-hex>`, key from `hex::decode`. Write `<file>.enc` and `<file>.dec` respectively.
4. Test: `printf 'secret message' > plain.txt && cargo run -- enc plain.txt`, then decrypt and `diff plain.txt plain.txt.dec` — must be empty.
5. Verify integrity: `sha256sum plain.txt plain.txt.dec` → identical hashes.
6. Tamper test: `dd if=/dev/urandom bs=1 count=1 seek=20 of=plain.txt.enc conv=notrunc` (flip 1 byte in the ciphertext) → `cargo run -- dec plain.txt.enc …` must abort with `decrypt failure` (tag check).

**Definition of Done (DoD):**

- [ ] `cargo build` without warnings.
- [ ] `sha256sum` of original and `dec` output are **identical**.
- [ ] Ciphertext starts with the 12-byte nonce (verifiable with `xxd plain.txt.enc | head -1`).
- [ ] Tampered ciphertext → decryption fails (no silent failure).
- [ ] You can explain why the key is symmetric and how you would exchange it in practice (→ Day 57 X25519).
- [ ] Commit: `git commit -m "day56: aes-256-gcm file encryptor with integrity check"`.

**Extension (optional):** Replace AES-GCM with `chacha20poly1305` (same AEAD API from `aead`) and compare speed with `cargo bench` on your machine — on M1/without AES-NI, ChaCha is often faster.
