## 📖 Theory

**Kani** is a Rust model checker from AWS, based on **CBMC** (C Bounded Model Checker). Unlike Prusti (deductive, Hoare logic), Kani is **bounded**: it turns the function into a Boolean constraint system and hands it to a SAT/SMT solver — finds a counter-example in finite time if the bounds are small enough.

### Kani vs. Prusti

| Property | Prusti (Day 71) | Kani |
| --- | --- | --- |
| Method | Deductive (Hoare logic, Viper) | Bounded model check (SAT/SMT) |
| Loop handling | Manual invariants needed | **Auto-unrolling** up to a bound |
| Specs | `requires`/`ensures` attributes | `proof_harness` macro + `kani::assert` |
| Array safety | Difficult (aliasing) | **Strong** (CBMC loves arrays) |
| Complexity | Medium (writing contracts) | Lower (assertions instead of contracts) |
| Counter-examples | Sometimes unreadable | Concrete, with variable values |
| Bounds | Unbounded (in spec) | Bounded (loop depth, array size) |

Rule of thumb: **Kani for "find bugs in all branches of this small function", Prusti for "prove this property for all inputs"**.

### `proof_harness` — the Kani method

```rust
#[kani::proof]
fn check_double_safe() {
    let x: i32 = kani::any();          // symbolic input — "some i32"
    kani::assume(x <= i32::MAX / 2);   // precondition as an assumption
    let result = double_safe(x);
    kani::assert(result == x * 2, "double returns x*2");
}
```

Kani searches over all possible `x` values (symbolically) for one that violates the `assert`. If it finds one → a counter-example with a concrete value. If it finds none within the bounds → success.

### What Kani is especially good at

1. **Array bounds**: `kani::assert(i < v.len(), "index in bounds")` — CBMC's specialty.
2. **Integer overflow**: `kani::assert(result >= 0)` over all inputs — finds overflow paths.
3. **Enum exhaustiveness**: checks that all `match` arms are correct, including edge cases.
4. **Unsafe-Rust properties**: e.g. that `unsafe` pointer deref only happens after a bounds check.

```rust
#[kani::proof]
fn check_get_or_panic() {
    let v: [i32; 5] = kani::any();
    let i: usize = kani::any();
    kani::assume(i < 5);
    let result = v[i];  // should never panic per the assumption
    kani::assert(result == v[i], "consistent");
}
```

### Bounds — the limitation

Kani's strength (bounded) is also its weakness: loops over arrays of size 1000 explode into `2^N` paths. Solution: parametrize the size for verification (`const N: usize = 10`) and verify real code paths with a smaller size, then hope for generalization.

```rust
#[cfg(kani)]
#[kani::proof]
fn check_sum_loop() {
    const N: usize = 10;  // small bound for verification
    let v: [u32; N] = kani::any();
    let mut sum = 0u32;
    for &x in &v {
        sum = sum.wrapping_add(x);
    }
    kani::assert(sum <= u32::MAX, "no overflow on sum");  // realistic for N=10
}
```

### Why this matters

AWS uses Kani internally for Firecracker (VM monitor), s2n-tls, and the Rust standard library. It is **production-ready** in contrast to many academic verifiers. For security-critical Rust code (auth, crypto wrappers, parsers) Kani is the current "go-to". Combined with Prusti the two cover almost all security-property classes.

### Pitfalls

- **State explosion** — arrays >100 elements or nested loops → timeout. Keep bounds small.
- **`kani::any()` for complex types** — works poorly for `Vec`; use arrays with `const N`.
- **Side effects not modeled** — I/O, network, random are modeled as nondeterministic → the result can be useless. Isolate functions.
- **"Bounded" is forgotten** — verification for N=10 is no proof for N=10000. Generalization is an extra argument.
- **Assertions too weak** — `kani::assert(true, …)` is worthless; the assertion must state the *actual* property.

## 🛠️ Practice

**Task:** Install Kani, write three `proof_harness` functions (overflow, array bounds, enum-match exhaustiveness), and deliberately find a bug in the code that Kani detects.

**Step by step:**

1. Install:

   ```bash
   # via rustup
   rustup install nightly
   cargo install kani-verifier
   kani --version
   # or: https://github.com/model-checking/kani/releases
   ```

2. Project + deps (`Cargo.toml`):

   ```toml
   [dependencies]
   kani = { version = "0.55", optional = true }

   [features]
   kani = ["dep:kani"]
   ```

3. Code with a bug — implement three functions in `src/lib.rs` yourself:

   > **Hints:**
   - `safe_add(a: u32, b: u32) -> u32`: guard against overflow with `if a <= u32::MAX - b { a + b } else { 0 }`. **Deliberately** return `0` on overflow (this is the bug Kani will find — silently returning 0 instead of an error).
   - `safe_get(v: &[i32], i: usize) -> Option<i32>`: use `i.checked_rem(v.len())` to decide `Some(v[i])` vs `None`.
   - `to_rgb(c: Color) -> [u8; 3]`: define `enum Color { Red, Green, Blue }` and `match` on it. Introduce a non-exhaustive `match` (use a `_` wildcard or forget an arm) to see how the compiler/Kani handles it.

4. Proof harnesses — write these in `src/lib.rs` (under `#[cfg(kani)]`) yourself:

   > **Hints:**
   - `check_safe_add`: create symbolic inputs with `let a: u32 = kani::any(); let b: u32 = kani::any();`, call `safe_add(a, b)`, then in the overflow branch (`a > u32::MAX - b`) assert `kani::assert(false, "overflow should not silently return 0")` — Kani will flag the bug.
   - `check_safe_get_inbounds`: create a `[i32; 5]` and a symbolic `i: usize`, `kani::assume(i < 5)`, call `safe_get(&v, i)`, and assert the returned value equals `v[i]`.
   - Each harness needs `#[kani::proof]` (and `#[cfg(kani)]` to gate it).
5. Run: `kani --output-format=json` → finds the bug in `safe_add` with a counter-example.
6. Fix the bug: `pub fn safe_add(a: u32, b: u32) -> Option<u32> { a.checked_add(b) }` → re-verify → success.
7. Write `docs/kani-vs-prusti.md` with your observation: what was easier, what harder?

**Definition of Done (DoD):**

- [ ] `kani --version` returns a version; install ok.
- [ ] Kani finds the deliberate `safe_add` bug with a counter-example (`a=u32::MAX, b=1`).
- [ ] After the bugfix: Kani verifies `safe_add` successfully.
- [ ] `check_safe_get_inbounds` verifies successfully for array size 5.
- [ ] You can explain in 2 sentences when Kani vs. Prusti (Day 71) is better.
- [ ] `docs/kani-vs-prusti.md` compares the two methods from your experience.
- [ ] Commit: `git commit -m "day72: kani model checker with proof harnesses"`.

**Extension (optional):** Verify a **nonce-counter monotonicity** property for a small chat state machine: "counter always increases, never back" — a typical property Kani covers very well.
