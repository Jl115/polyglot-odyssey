# Day 68: SLSA & Reproducible Builds

**Block:** Block 4: Security & PQC · Supply Chain Security

> **Goal of the day:** You know the SLSA levels (1–4), can generate a SLSA provenance attestation for your `pqc-tool`, and explain how reproducible builds (bit-for-bit) act as an independent verification path — the output is a traceable build provenance.

---

## 📖 Theory

**SLSA (Supply-chain Levels for Software Artifacts)** is a Google-initiated framework that specifies "build provenance" in four ascending levels. It answers the question: *"How do I know that this binary was produced from exactly this source code?"* — a question that was unanswered for SolarWinds.

### SLSA levels

| Level | Requirement | Protects against |
| --- | --- | --- |
| **L1** | Build system documents the build (provenance file present) | no deception |
| **L2** | Build runs in a *managed* build service (not a local dev machine); provenance with signed metadata | modification after build |
| **L3** | Build is *isolated* (no network access during build, no cache modification); provenance tamper-evident | build-server compromise |
| **L4** | Reproducible builds (two build services produce bit-identical artifacts); personnel isolation | build-service compromise (2-of-2) |

In Rust terms: L1 = `cargo build && cargo provenance-gen`. L2 = GitHub Actions runner, not dev laptop, with `actions/attest-build-provenance`. L3 = hermetic container builds without network. L4 = `cargo build --locked` reproducible in two separate CI services.

### Provenance attestation format (in-toto)

```json
{
  "_type": "https://in-toto.io/Statement/v0.1",
  "subject": [{ "name": "pqc-tool", "digest": { "sha256": "abc..." } }],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildType": "https://github.com/.../workflow.yaml@v1",
    "buildStartedOn": "2025-06-20T10:00Z",
    "builder": { "id": "github-actions-runner-..." },
    "materials": [
      { "uri": "git+https://github.com/you/pqc-tool@<commit-sha>" },
      { "uri": "pkg:cargo/aes-gcm@0.10.3", "digest": { "sha256": "..." } }
    ]
  }
}
```

Signed with Sigstore (Day 67), entered in Rekor → publicly verifiable.

### Reproducible builds — the L4 promise

A build is **reproducible** if two builds from the same source in different environments produce bit-identical binaries. Then any third party can pull the source, rebuild, compare hashes — if it matches, you know the shipped binary contains no backdoor (or both build systems would be compromised).

Sources of non-reproducibility in Rust:

- **Timestamps** in the binary (`env!("CARGO_PKG_VERSION")`, build time).
- **Random-order hashes** (HashMap iteration order).
- **Absolute paths** (`file!()` macro).
- **Build-ID** via `cargo` can be nondeterministic.

Solutions: set `SOURCE_DATE_EPOCH` env, `--locked` for `Cargo.lock`, deterministic sortings, `cargo build --locked --offline` in a hermetic container.

### Why this matters

L4 is the gold standard for critical infrastructure (Linux distros, Bitcoin, Tor). Debian's "Reproducible Builds" project proves that a large ecosystem can be L4-compatible. PQC migration (Day 64) demands reproducibility, because otherwise you lose evidence about build provenance for PQC implementations — a compromised liboqs in the build can secretly weaken PQC keys.

### Pitfalls

- **SLSA level not verified** — an L3 label without checking is just marketing. The verifier must signature-check the provenance.
- **Materials incomplete** — if only the `git commit` but not the dependencies are in the materials, you cannot trace a vulnerable dependency back.
- **Build cache as a trust vector** — at L3 the cache must be established before the build and not modified by the build process.
- **`cargo build` without `--locked`** — minor updates can change the binary → non-repro. Always `--locked` in CI.
- **"We have Sigstore"** — Sigstore signs *the binary*, SLSA attests *the provenance*. Both together are the chain; a signature without provenance does not say it was built from safe source.

## 🛠️ Practice

**Task:** Set up a SLSA-L3 GitHub Action for `pqc-tool` (or simulate locally) that generates a provenance attestation and attempt a reproducible build in two environments.

**Step by step:**

1. **Reproducibility test** (locally, first):

   ```bash
   cd days/day65
   cargo clean
   SOURCE_DATE_EPOCH=1718889600 cargo build --release --locked --offline
   sha256sum target/release/pqc-tool > hash1.txt
   cargo clean
   SOURCE_DATE_EPOCH=1718889600 cargo build --release --locked --offline
   sha256sum target/release/pqc-tool > hash2.txt
   diff hash1.txt hash2.txt    # → must be identical
   ```

2. If non-repro: investigate with `diffoscope pqc-tool-build1 pqc-tool-build2` what differs (paths, timestamps). Fix per finding.
3. **SLSA provenance via GitHub Action** — create `.github/workflows/release.yml` yourself:

   > **Hints:**
   - Trigger the workflow on version tags (`on: push: tags: ['v*']`).
   - Declare minimal `permissions:` — you need `contents: write`, `id-token: write` (for OIDC/keyless), and `attestations: write`.
   - Steps: checkout the repo, install a Rust toolchain (e.g. `dtolnay/rust-toolchain`), then `cargo build --release --locked`.
   - Generate the provenance with `actions/attest-build-provenance@v1`, passing `subject-path: target/release/pqc-tool`.

   `actions/attest-build-provenance` uses Sigstore keyless internally + writes the attestation to GH attestation storage.
4. **Verify** (locally, against a release):

   ```bash
   gh attestation verify target/release/pqc-tool \
     --repo your-org/pqc-tool \
     --predicate-type https://slsa.dev/provenance/v1
   ```

5. Write `docs/slsa.md`: your current level, gaps (e.g. "build not hermetic, network active"), roadmap to L3/L4.

**Definition of Done (DoD):**

- [ ] `sha256sum` of two builds with `--locked --offline` + `SOURCE_DATE_EPOCH` is identical.
- [ ] GitHub Action workflow committed; on `git tag v0.1.0 && git push --tags` a provenance attestation is generated.
- [ ] `gh attestation verify` shows "verified" for the provenance.
- [ ] `docs/slsa.md` lists the current level + roadmap to L3 (hermetic, isolated, tamper-evident).
- [ ] You can explain in 2 sentences why SLSA + reproducible builds together are stronger than alone (trust chain + cross-check).
- [ ] Commit: `git commit -m "day68: slsa provenance + reproducible build for pqc-tool"`.

**Extension (optional):** Build in a **hermetic Docker container** (`docker run --rm -v $PWD:/src -w /src rust:slim cargo build --release --locked --offline`) and compare the hash with the GitHub Action build — should match (cross-service reproducibility = L4 indicator).
