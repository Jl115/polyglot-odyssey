---

## 📖 Theory

TLS (Transport Layer Security) is the protocol behind HTTPS, SMTPS, LDAPS. It provides **confidentiality** (AEAD stream), **integrity** (MAC, today inside AEAD), and **authenticity** (certificates/PKI). Version 1.3 (RFC 8446, 2018) is the radical simplification: fewer round trips, fewer cipher suites, forward secrecy by default.

### The TLS 1.3 handshake (1-RTT)

```text
Client                              Server
  |--- ClientHello ------------------>|  supported_versions=key_share(X25519)
  |<-- ServerHello -------------------|  key_share(X25519) → both derive shared secret
  |<-- {EncryptedExtensions          |
  |     Certificate, CertVerify      |   from here on EVERYTHING encrypted (handshake keys)
  |     Finished}--------------------|
  |--- {Finished}------------------->|
  |===== application data ===========|   (derived from handshake secret via HKDF)
```

**Key generation** via X25519 (Diffie-Hellman on Curve25519): the client sends its public key, the server sends its public key, both compute the same shared secret → **HKDF** derives all session keys from it. This is called **forward secrecy**: even if the server's private key leaks later, old traffic remains decryptable only if the attacker *also* has the ephemeral session keys.

### Cipher suites in TLS 1.3

Only AEAD remains: `TLS_AES_256_GCM_SHA384`, `TLS_AES_128_GCM_SHA256`, `TLS_CHACHA20_POLY1305_SHA256`. No CBC, no 3DES, no static RSA handshake. The MAC is implicit in AEAD.

### What was broken in TLS 1.2 and older

- **RSA key-transport handshake** (no DHE): client generates a pre-master secret, encrypts with the server's public key → no forward secrecy.
- **CBC mode**: padding-oracle attacks (POODLE, Lucky13).
- **Renegotiation** → MitM (CVE-2009-3555), later fixed via extension.
- **RC4, SHA-1 MACs** → insecure.

### Certificates & PKI

The server authenticates itself with an X.509 certificate signed by a CA. Chain of trust: root CA (self-signed, in the OS trust store) → intermediate → leaf. Validation checks: signature chain, expiry date, hostname (SAN entry), revocation (OCSP/CRL).

```bash
openssl s_client -connect www.cloudflare.com:443 -tls1_3 -servername www.cloudflare.com
# Output shows: Protocol=TLSv1.3, Cipher=TLS_AES_256_GCM_SHA384,
# Peer certificate chain, ALPN negotiated (h2)
```

### Why this matters

TLS is the layer the entire web sits on. PQC migration (Day 61–65) attacks *here*: X25519-Kyber hybrid is already deployed in Chrome/Cloudflare. Anyone who does not understand TLS cannot evaluate PQC migration.

### Pitfalls

- **Forgetting the hostname check** is the most common TLS bug — certificate valid, but for the wrong domain.
- **TLS 1.3 "middlebox compatibility mode"** (empty ChangeCipherSpec records) fools boxes — do not misread it as real encryption.
- **Self-signed certs in prod** = vulnerable; acceptable only for internal dev.
- **0-RTT (early data)** is **replayable** — do not use for non-idempotent requests.
- **Downgrade attacks**: ClientHello supports 1.2 + 1.3 → attacker strips 1.3 extensions → client downgrades. TLS 1.3 uses `supported_versions` instead of the `version` field + a `downgrade_sentinel` in ServerRandom to detect this.

## 🛠️ Practice

**Task:** Inspect three real TLS connections with `openssl s_client` and compare cipher, protocol, certificate chain, and key share. Then build a minimal TLS 1.3 server in Rust.

**Step by step:**

1. Inspect connections:

   ```bash
   echo | openssl s_client -connect www.cloudflare.com:443 -servername www.cloudflare.com -tls1_3 2>/dev/null \
     | grep -E "Protocol|Cipher|Server Temp Key|Verification"
   ```

2. Repeat for `www.google.com` and `expired.badssl.com` (the latter: deliberately expired — `verify error:num=10:certificate has expired`).
3. Look at the certificate: `openssl x509 -in <(openssl s_client -connect www.cloudflare.com:443 -showcerts </dev/null 2>/dev/null | sed -n '/BEGIN/,/END/p' | head -1) -noout -text | grep -E "Subject:|Issuer:|DNS:|Not After"`.
4. Minimal TLS 1.3 server in Rust (`Cargo.toml`):

   ```toml
   [dependencies]
   tokio-rustls = "0.26"
   rustls = "0.23"
   rcgen = "0.13"          # generate self-signed cert
   tokio = { version = "1", features = ["full"] }
   ```

   `src/main.rs`:
   > **Hints:**
   > - Use `rcgen::generate_simple_self_signed(vec!["localhost".into()])` to produce a self-signed cert; feed `cert.cert.der()` and `cert.key_pair.serialize_der()` into `rustls::pki_types::CertificateDer` / `PrivateKeyDer`.
   > - Build a `rustls::ServerConfig` via the builder: `.with_no_client_auth().with_single_cert(certs, key)`; wrap it in `Arc` and construct a `TlsAcceptor`.
   > - Bind a `tokio::net::TcpListener` on `127.0.0.1:8443`; in the accept loop `tokio::spawn` each connection, call `acceptor.accept(sock)` to get a TLS stream.
   > - Read with `AsyncReadExt::read` into a buffer, then write back an echo with `AsyncWriteExt::write_all`.
5. Start `cargo run`, then `openssl s_client -connect 127.0.0.1:8443 -tls1_3` → type something, see the echo.

**Definition of Done (DoD):**

- [ ] `openssl s_client` shows for Cloudflare `Protocol: TLSv1.3`, `Cipher: TLS_AES_256_GCM_SHA384`, and `Server Temp Key: X25519, 253 bits`.
- [ ] `expired.badssl.com` shows a verify error because of the expiry date (not just because of self-signed).
- [ ] Rust server responds over TLS 1.3 (verified with `openssl s_client`).
- [ ] You can mark at which point in the handshake forward secrecy arises (answer: at the key-share extension exchange, not at the cert).
- [ ] Commit: `git commit -m "day57: tls 1.3 handshake inspection + minimal rustls server"`.

**Extension (optional):** Use `curl -v https://localhost:8443 --cacert cert.pem` against your server and explain why `curl` rejects (self-signed) — and how to extend the trust store with `SSL_CERT_FILE`.
