---

## 📖 Theory

### The problem: Shor vs. RSA/ECC

A sufficiently large **quantum computer** can solve integer factorization and discrete logarithms in **polynomial time** with Shor's algorithm. This breaks RSA, DH, ECDH, ECDSA — all the asymmetric methods dominant today. For *symmetric* crypto the damage is small: **Grover's algorithm** square-roots the brute-force complexity, AES-256 → ~2^128 quantum operations. Concretely: AES-256 stays secure (SHA-256 only needs to switch to SHAKE-256/SHAKE-512 output), X25519 dies.

### The solution: lattice cryptography

Lattice schemes are based on problems for which **no** known quantum algorithm provides a sub-exponential speedup. NIST standardized three algorithms in 2024 after an 8-year competition:

| Standard | Algorithm | Purpose | Predecessor name |
| --- | --- | --- | --- |
| **FIPS 203** | ML-KEM | Key exchange (KEM) | CRYSTALS-Kyber |
| **FIPS 204** | ML-DSA | Signatures | CRYSTALS-Dilithium |
| **FIPS 205** | SLH-DSA | Stateful-hash signatures (fallback) | SPHINCS+ |

### Lattice intuition (without deeper mathematics)

Imagine a grid in n-dimensional space — a **lattice** `L(b1, b2, …, bn)` is the set of all integer combinations of the basis vectors. Three problems are relevant:

1. **SVP (Shortest Vector Problem):** find the shortest non-trivial vector in the lattice. NP-hard to approximate.
2. **LWE (Learning With Errors):** you see many `(a_i, b_i)` pairs where `b_i = a_i · s + e_i (mod q)` and `e_i` is small error noise. Without the "noise" `e_i` it would be linear algebra — trivially solvable. The noise makes it hard because exact solutions would ignore the error possibility.
3. **Ring-LWE / Module-LWE:** instead of vectors you use polynomial rings (faster, more compact), the error structure stays the same.

**Important:** the "+ error" is the key — it is *not* an implementation bug but the source of hardness. Anyone who computes "without error" builds an insecure system.

```text
LWE (simplified):  b = A · s + e   (mod q)
                      ^   ^
                      public vector    secret key + small noise
  without e  → exact solution via Gaussian reduction  → trivially attackable
  with e     → noise "smears" the solution → LWE is considered quantum-resistant
```

### Why three algorithms?

- **ML-KEM** — fast, compact (~800-byte public key), but **only confidentiality**. Not for signing.
- **ML-DSA** — fast, moderate sizes, for code signing and TLS.
- **SLH-DSA** — **slow, large signatures (~50 KB)**, but a completely different assumption (hash-based). Recommended as a "hedge": if lattices ever get broken, SLH-DSA remains.

### Hybrid schemes — the migration standard

Nobody rolls out *only* ML-KEM. Risk: if an undiscovered lattice attack exists, everything breaks. Solution: **hybrid** = classical + PQC. Both keys must be broken to decrypt the session.

```text
X25519Kyber768Draft  =  X25519  +  ML-KEM-768
  shared_secret = HKDF( x25519_shared  ||  kyber_shared )
```

Browsers (Chrome) and Cloudflare have been doing this since 2023+. OpenSSL 3.4+ has provider support.

### Why this matters

"Harvest now, decrypt later" — attackers store TLS traffic today and decrypt it in 10–15 years with the then-ready quantum computer. Anyone with data that must stay confidential for >10 years (health records, state secrets) **must** migrate today. The migration duration for large organizations is estimated at 10–15 years — better to start now than later.

### Pitfalls

- **"NIST standardized PQC, we're secure"** — no, ML-KEM is FIPS 203, but **hybrid** is the industry consensus. Pure PQC is still considered risky.
- **Lattice decapsulation failure**: ML-KEM has a tiny decryption-failure probability (FIPS-conformant). Side-channel attacks use this as an oracle (timing differences on failure). Implementations must be constant-time.
- **Key sizes** — ML-KEM-768 public key ~1184 bytes (vs. X25519 32 bytes). Bandwidth engineering, buffer sizing, and protocol layouts must be adapted.
- **Only signing ≠ only encryption** — ML-DSA is not for KEM, ML-KEM is not for signatures. They are **not** interchangeable.
- **"Quantum-resistant" ≠ "quantum-safe forever"** — crypto is asymptotic; new algorithmic attacks can change everything. SLH-DSA as a hedge is not paranoia.

**Task:** Implement a small LWE library sketch in Rust that demonstrates how the "error noise" makes an exact solution impossible — and read the NIST standard summary. No production crypto!

**Step by step:**

1. Project: `cargo new day61 --bin`, dependencies `ndarray = "0.16"`, `rand = "0.8"`.
2. Demonstration code (mini-LWE, *didactic*, not for production):
   > **Hints:**
   > - Use `ndarray` (`Array1`, `Array2`) for vectors/matrices and `rand::Rng` for sampling. Pick a small modulus `q` (e.g. 17) and dimension `N` (e.g. 40).
   > - Generate a random `A` (`N×N`, values in `0..q`) and a secret vector `s` (`N`, values in `0..q`). Compute `b_clean = (A · s) mod q` — this is the *no-error* case that is trivially solvable.
   > - Compute `b_noisy` by adding a small error `e ∈ {-2,-1,0,1,2}` per component and reducing mod `q` with `rem_euclid`. Print both and observe that `b_noisy ≠ b_clean` — that noise is what makes exact recovery impossible.
   > - In `notes.md`, identify what plays the role of public key (`A` + `b`), secret (`s`), and ciphertext (an `(u, v)` pair).
3. Run it, observe how `b_noisy` deviates from `b_clean` — that is the noise.
4. Read [NIST FIPS 203 — ML-KEM](https://csrc.nist.gov/pubs/fips/203/final) introduction + Section 1–2 (about 10 pages).
5. Sketch in `notes.md`: what would be the public key, the secret, the ciphertext in your mini-LWE? (Answer: `A` + `b` are public, `s` is secret, the `(u, v)` pair is the ciphertext.)
