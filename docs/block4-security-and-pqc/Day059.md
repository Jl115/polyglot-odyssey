# Day 59: Threat Modeling

**Block:** Block 4: Security & PQC · Crypto Fundamentals

> **Goal of the day:** You can model a system with STRIDE + a data-flow diagram, derive threats systematically, and know which of the top-4 mitigations (validate input, least privilege, defense in depth, logging) helps for which class.

---

## 📖 Theory

**Threat modeling** is the *systematic* attempt to find attacks *before* the system is built — not only after the bug bounty. It is cheap insurance: a 2-hour workshop replaces weeks of patching. Adam Shostack's four-question framework:

1. **What are we building?** (model the system)
2. **What can go wrong?** (find threats)
3. **What are we going to do about it?** (mitigation)
4. **Did we do a good job?** (verification)

### Step 1 — Model with a Data-Flow Diagram (DFD)

A DFD shows **processes** (circles/rectangles), **data stores** (double-struck lines), **external entities** (rectangles), and **data flows** (arrows). Every flow is divided by a **trust boundary** (dashed line) as soon as data crosses trust zones (e.g. user network → backend). Trust boundaries are the most important spots: that is where the attacker is.

```text
[User] --(HTTPS)--> [API Gateway] --(gRPC)--> [Auth Service] --SQL--> [(DB)]
                          |                        |
                       Trust Boundary            Trust Boundary
```

### Step 2 — Find threats with STRIDE

STRIDE is a mnemonic that maps each of the 6 security properties to a threat class:

| Letter | Threat | Property violated | Typical example |
| --- | --- | --- | --- |
| **S**poofing | forge identity | authenticity | JWT with alg=none, weak passwords |
| **T**ampering | alter data | integrity | SQL injection, JSON manipulation |
| **R**epudiation | deny action | non-repudiation | missing audit log |
| **I**nformation Disclosure | leak info | confidentiality | verbose error stacktrace, IDOR |
| **D**enial of Service | kill availability | availability | regex ReDoS, unbounded alloc |
| **E**levation of Privilege | widen rights | authorization | IDOR on `/admin/*`, SSRF to metadata endpoint |

Go through all 6 categories per trust-boundary crossing. This forces you to think not only about "external hackers" but also about *insiders* and *misconfigured* systems.

### Step 3 — Mitigations

| Threat | Example mitigations |
| --- | --- |
| Spoofing | OAuth/OIDC, MFA, mutual TLS, short token TTL |
| Tampering | AEAD/MAC, input validation (whitelist), prepared statements |
| Repudiation | immutable audit logs (append-only, signed), timestamps |
| Info Disclosure | principle of least privilege, output encoding, rate limit |
| DoS | rate limit, backpressure, timeouts, cap alloc size |
| EoP | RBAC/ABAC, deny-by-default, resource isolation |

### Step 4 — Verification

Review against real CVEs of the components in use, fuzzing, penetration tests. Do not push threats aside with "will never happen" — if the mitigation is cheaper than the risk, mitigate.

### Why this matters

Threat modeling forces engineering teams to think about attack surfaces *before code*. Most real CVEs (Log4Shell, SolarWinds backdoor, MOVEit) were in architectures whose DFD interfaces were not modeled. PQC migration (Day 61+) without a threat model only produces "new algorithm, old risk".

### Pitfalls

- **Forgetting the "attacker profile"**: "internal threat" (dev with prod access) is its own persona, not only "skilled external hacker".
- **Boil the ocean**: all 6 STRIDE for *every* line of the DFD → 2000 threats. Focus on trust boundaries and critical data stores.
- **"We use TLS, so we're secure"**: TLS protects *only* transport, not at-rest, not against auth bugs *behind* TLS.
- **Skipping the assume-compromise model**: "What if the attacker is *inside* the network?" — zero trust emerges from this.
- **Risk acceptance without owner**: every accepted risk needs a named owner and a review date.

## 🛠️ Practice

**Task:** Threat-model the mini-capstone "Secure Chat" (Day 60) *before* building it — draw the DFD, produce a STRIDE list, define the top-5 mitigations. Output is a Markdown document, not code.

**Step by step:**

1. Sketch the DFD of the secure-chat architecture (Client A ↔ Server ↔ Client B, message store, auth service). Use [draw.io](https://app.diagrams.net/) or Mermaid (`graph TD`). Mark trust boundaries as dashed lines.
2. Write a Markdown `docs/threat-model.md` with these sections:
   > **Required sections (you write the content — no template to copy):**
   > - **1. System Overview** — embed your Mermaid/DFD diagram (or ASCII). Show Client A ↔ Server ↔ Client B, message store, auth service.
   > - **2. Assets & Trust Boundaries** — list what is valuable (messages, identities) and where trust changes (Client→API public internet; API→Auth internal).
   > - **3. STRIDE per Trust-Boundary-Crossing** — a table with one row per data flow and columns S/T/R/I/D/E. Cover at least 2 flows × 6 categories (≥12 entries).
   > - **4. Top-5 Mitigations** — number them, each referencing a concrete tool/standard (e.g. Ed25519 JWT, AEAD at-rest, token-bucket rate limit, append-only hash-chained audit log, RBAC).
   > - **5. Accepted Risks** — every accepted risk gets a named owner and a review date.
3. For each threat, find a real CVE comparison (e.g. JWT alg=none = CVE-2015-9235).
4. Discuss with yourself: "Assume the attacker sits *inside* the internal network" — what breaks? That is the zero-trust follow-up task.

**Definition of Done (DoD):**

- [ ] DFD in `threat-model.md` with at least 2 trust boundaries.
- [ ] STRIDE table covers at least 2 flows × 6 categories (≥12 entries).
- [ ] Top-5 mitigations with reference to tools/standards (Ed25519, AEAD, token bucket).
- [ ] At least 1 accepted risk with owner and review date.
- [ ] You can explain in 1 sentence why STRIDE is per trust boundary, not per line of code.
- [ ] Commit: `git commit -m "day59: threat model for secure chat (STRIDE)"`.

**Extension (optional):** Turn the mitigations into **OWASP ASVS L1** checklist items and mark which ones your design fulfills — this gives you an auditable compliance artifact.
