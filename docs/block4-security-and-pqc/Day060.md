# Day 60: Mini-Capstone: Secure Chat

**Block:** Block 4: Security & PQC · Crypto Fundamentals

> **Goal of the day:** You build an end-to-end-encrypted chat in Rust (Tokio + rustls) in which the server only forwards messages as ciphertext, keys are negotiated client-side via X25519-DH, and all messages are AEAD-authenticated. Connects Day 56–59 into a working system.

---

## 📖 Theory

This mini-capstone unites the building blocks so far. The core idea: **end-to-end encryption (E2EE)** means *only the clients* can decrypt the messages — the server is a "blind relay" that sees only random bytes. This is the model of Signal, WhatsApp, age.

### Architecture

```text
Alice (client)                Server (relay)              Bob (client)
   |                              |                          |
   |--- X25519 public -----------|-------------------------->|  (1) Alice's pub to Bob
   |<-- X25519 public -----------|--------------------------|  (2) Bob's pub to Alice
   |   both derive: shared_secret = X25519(myPriv, theirPub)
   |   session_key = HKDF(shared_secret, "chat-v1")
   |                              |                          |
   |--- AEAD(session_key, msg) -->|-- forwarded as-is ------>|  (3) Bob decrypts, displays
```

**Important:** The server sees *only* public keys and ciphertext. Even under server compromise, old messages stay secure (forward secrecy via ephemeral DH keys).

### Component recap from Block 4

- **X25519** (Day 57): key agreement, ephemeral per session.
- **AES-256-GCM / ChaCha20-Poly1305** (Day 56): AEAD for messages, nonce as a counter.
- **Key lifecycle** (Day 58): ephemeral DEK, rotates on reconnect.
- **Threat model** (Day 59): we accepted that server compromise only exposes ciphertext.

### Message format

Each message is a binary frame: `[1B version][8B counter-nonce][N B AEAD-ciphertext+tag]`. The counter is the nonce (12-byte with padding) and prevents replay — Bob discards counters ≤ the last one seen.

### Why this matters

Anyone who has built an E2EE system once immediately understands why Signal's "safety numbers", OMEMO's per-device keys, and PQC hybrid encryption (Day 61) are variations of the same patterns. It is the "Hello World" of real crypto applications.

### Pitfalls

- **The nonce counter must stay in sync on *both* sides** — out-of-order messages need window tolerance (e.g. ±16), otherwise the chat breaks on packet reordering.
- **Public-key authenticity is missing here** — an active MitM can replace both public keys during the first key exchange. Production solution: a safety-number fingerprint (SHA-256 of both public keys) that the user compares. In this mini exercise we accept the risk.
- **The server does not store keys, but metadata** (who talks to whom, when, how many bytes) leaks → metadata resistance needs mix networks/padding (extra day).
- **Forgetting replay protection** is the most common bug — without a counter, nothing is rejected, the attacker replays a "delete" command.
- **Key wipe on disconnect**: the ephemeral `shared_secret` must be erased after deriving the session keys, otherwise forward secrecy is pointless.

## 🛠️ Practice

**Task:** Implement `secure-chat`: a server binary (`server`) and a client binary (`client`) in one workspace. The client connects via TLS (self-signed for local), sends its X25519 pub to the server which forwards it to the partner; then AEAD-encrypted messages go back and forth.

**Step by step:**

1. Create the workspace:

   ```bash
   cargo new day60 --bin
   cd day60
   ```

   `Cargo.toml`:

   ```toml
   [dependencies]
   tokio = { version = "1", features = ["full"] }
   tokio-rustls = "0.26"
   rustls = "0.23"
   rcgen = "0.13"
   x25519-dalek = "2"
   aes-gcm = "0.10"
   hkdf = "0.12"
   sha2 = "0.10"
   serde = { version = "1", features = ["derive"] }
   serde_json = "1"
   zeroize = "1"
   ```

2. Client logic core:
   > **Hints:**
   > - **DH**: `EphemeralSecret::random()` from `x25519-dalek`, then `PublicKey::from(&secret)`. Send your public key over TLS to the server (which forwards it to the partner), and receive the partner's `PublicKey`. Compute `secret.diffie_hellman(&partner_pub)` → `SharedSecret`.
   > - **KDF**: feed the shared secret through `Hkdf::<Sha256>::new(None, shared.as_bytes())`, then `hk.expand(b"chat-v1", &mut session_key)` to get a 32-byte AES key.
   > - **Encrypt**: construct `Aes256Gcm` from the session key. Build a 12-byte nonce where `nonce[4..12]` holds the counter as big-endian bytes (`counter.to_be_bytes()`). Call `cipher.encrypt(nonce, msg.as_bytes())` and concatenate `nonce || ct`.
   > - **Wipe**: `zeroize()` the `shared_secret` and `session_key` after derivation so forward secrecy is real, not theoretical.
3. The server is a **blind relay** — reads frames, forwards unchanged. Knows no keys.
4. Start two clients (`cargo run --bin client -- alice` and `-- bob`), type messages, see them in the other window — but a `tcpdump` on the connection shows only ciphertext.
5. Tamper test: `printf '\xff' | nc -p 9999 127.0.0.1 8443` (change one byte) → receiver aborts with `decrypt error`; replaying an old frame (same counter) → rejected.

**Definition of Done (DoD):**

- [ ] Two clients can chat encrypted; the server source contains **no** access to plaintext (provable: `grep -i plaintext src/server.rs` empty).
- [ ] Counter replay is rejected (same frame 2× → 2nd time rejected).
- [ ] `shared_secret` and `session_key` are `zeroize()`d after derivation.
- [ ] Forward-secrecy thought experiment: if the server is compromised — can it decrypt *old* recorded frames? (Answer: no, because of ephemeral DH.) Note this in the README.
- [ ] The threat-model document (Day 59) is referenced — which accepted risks are now real?
- [ ] Commit: `git commit -m "day60: e2ee secure chat (x25519 + aes-gcm, blind relay)"`.

**Extension (optional):** Implement a **safety-number fingerprint** — SHA-256 of the sorted bilateral public keys, displayed as 6×8 digit groups. The user compares whether both sides see the same fingerprint → detects MitM.
